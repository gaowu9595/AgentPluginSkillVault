## 前置条件

- 交互稿摘要已落盘（`.ai/*-摘要.md`）
- 如无摘要 → 先执行 `/design-session:analyze`

## 执行流程

```
步骤1 输入就绪 → 步骤2 确认范围 → 步骤2.5 现有能力扫描 → 步骤3 功能点拆分 → 步骤4 逐点编写 → 步骤5 交互覆盖度自检 → 步骤6 DFX → 步骤7 完成
```

---

### 步骤 1：输入就绪检查

1. 读 `<项目>/.ai/context.md` — 确认当前阶段和已有决策
2. 读对应模块的交互稿摘要（`.ai/<模块>-摘要.md`）
3. 确认摘要中有"交互规则汇总"章节（§四）
   - 如果没有（旧格式摘要）→ 从摘要全文中手动提取交互规则列表
4. 读 `<项目>/.ai/corrections.md` — 避免重蹈覆辙

**缺少摘要 → 暂停，告知用户需要先分析交互稿。**

### 步骤 2：确认写作范围

询问用户：
- 哪个模块的系统需求？
- 全新编写 vs 重写/补充？
- 是否有已确认的决策需要纳入？

### 步骤 2.5：现有能力扫描（自动）

> **目的**：避免把已有功能当成新增功能写进系统需求。交互稿不区分"已有功能展示"和"新增功能设计"，需要对照代码确认。

**执行条件**：目标模块在代码仓库中已有对应目录。如果是全新模块（目录不存在），跳过此步。

**流程**：

1. **定位代码目录**：从 `context.md` 中的代码路径约定（如 `现有代码参考` 章节）或项目 CLAUDE.md 中的仓库映射，找到目标模块的代码路径
2. **判断是否存在**：目录不存在 → 全新模块，跳过扫描，进入步骤 3
3. **扫描路由层**：
   - 找到模块的 controller / router / blueprint 注册文件
   - 提取已有 API 端点列表（方法 + 路径 + 一句话功能描述）
   - **只读路由层**，不深入 service/db（控制 token 消耗）
4. **产出对照表**：将交互稿摘要中的页面/操作 与 已有端点做初步匹配
5. **展示给用户确认**：

```
## 现有能力扫描结果

目标模块代码路径：`<path>`
已有 API 端点：N 个

| 交互稿页面/操作 | 匹配的已有端点 | 判断 |
|---------------|--------------|------|
| 客户列表 | POST /customer/customer_list | 已有 |
| 新增客户 | POST /customer/customer_create | 已有 |
| 服务详情-设备列表 | （无匹配） | 新增 |
| ... | ... | ... |

请确认以上判断是否正确，以及是否有需要补充的信息。
```

6. **用户确认后**，将功能点分为三类：
   - **已有**：代码已完整实现，系统需求中只写一行汇总
   - **增强**：已有基础但需扩展，系统需求只写增量部分
   - **新增**：完全没有，按完整模板展开

**注意事项**：
- 路由存在不代表功能完整（可能是空壳），但大多数情况下路由+handler 存在即表示功能已实现
- 如果用户指出某个端点虽然存在但实现不完整，按"增强"处理
- 交互稿中属于其他系统的参考界面（如 MSSW 截图），在此步骤也可能被识别为"无匹配端点"——用户确认时应标注为"非本系统范围"而非"新增"

### 步骤 3：功能点拆分

基于摘要内容，拆分功能点：

1. 从摘要的"页面清单"识别主要页面/操作
2. 每个独立的用户操作 = 一个功能点
3. 系统自动行为也是功能点（如定时任务、自动生成）
4. **结合步骤 2.5 扫描结果，标注每个功能点的分类**：已有 / 增强 / 新增 / 非本系统范围
5. 输出功能点清单给用户确认

**功能点拆分原则**（防止评审时讲不清楚）：

- **每个功能点必须代表一个独立的、需要新开发的交付物**。如果无法回答"这个功能点要写什么新代码"，就不应该是独立功能点
- **已有功能不拆为功能点**：只在"已有功能"汇总表中列出，或在依赖处引用（如"数据来源：积分流水记录"）
- **附带效果合并到主功能点**：如果 B 是 A 的自然产物（A 写了数据，B 只是查询时多返回一个字段），B 不应独立成功能点，而是作为 A 的约束条件
- **判断标准**：向产品/项目经理讲述时，能否用一句话说清"这个功能点交付什么用户可感知的价值"？不能 → 合并或删除

**命名规则**：`<模块缩写>-NN`（如 BILL-01、CUST-01）

**功能点清单输出格式**：

```
| 编号 | 功能点 | 分类 | 说明 |
|------|--------|------|------|
| CUST-01 | 客户列表 | 已有 | POST /customer/customer_list |
| CUST-07 | 服务总览 | 新增 | 无匹配端点 |
| CUST-10 | 新增授权 | 增强 | 已有审批流程，新增 MSSW 推送 |
```

### 步骤 4：逐点编写

#### 4.0 写作深度规则（基于步骤 3 分类）

| 分类 | 写作深度 | 说明 |
|------|---------|------|
| **已有** | 汇总表一行 | 端点 + 一句话说明，不展开详细描述 |
| **增强** | 只写增量部分 | 标注已有基础，详细描述新增/变更的部分 |
| **新增** | 完整模板展开 | 按 4.2 模板完整编写 |
| **非本系统范围** | 不写 | 在文档头部说明排除原因 |

#### 4.3 编写禁止项（内嵌核心规则）

| 禁止写法 | 原因 | 正确做法 |
|---------|------|---------|
| "写入 invoice 表" | 技术实现，读者不懂 | "生成账单记录" |
| "调用 xxx 接口" | 技术实现 | "发送邮件通知" |
| "性能不下降" / "快速响应" | 无法量化验证 | 给出具体 RT 数值 |
| "待定" / "后续明确" | 评审无法通过 | 写"不涉及"并说明原因，或标注 ❓ 待确认 |
| 只写主流程不写交互规则 | 后续设计会遗漏 | 每个弹窗/表单必须有"交互规则"表格 |
| 角色差异只在文字中提一句 | 容易忽略 | 用表格明确列出 |
| 状态枚举只列名称 | 不完整 | 每个状态：英文 code + 含义 + 触发条件 |
| 遗漏"不可操作"规则 | 开发会漏实现 | 显式写出"XX不可删除""XX不可编辑" |
| 只写接口字段，不写页面状态 | 前端无法据此完整实现 | 每个前端功能点必须覆盖加载/空态/提交中/成功/失败 |
| 把原型视觉稿直接当需求 | 原型可能缺少异常和状态规则 | 标注原型证据等级，并以已确认业务规则和代码事实校正 |
| 前后端分别描述同一规则但口径不同 | 联调时产生歧义 | 在功能点内写统一字段语义、错误语义和刷新策略 |

### 步骤 5：交互覆盖度自检（**强制，不可跳过**）

写完所有功能点后，执行覆盖度检查：

1. 从摘要中提取所有交互规则（§四 交互规则汇总，或全文中带"注释""规则""约束"的条目）
2. 逐条在系统需求中搜索对应描述
3. 输出覆盖度报告：

```
## 交互覆盖度自检

摘要交互规则总数：N 条
系统需求已覆盖：M 条
遗漏：K 条

### 遗漏清单
| 规则 | 摘要位置 | 应补充到 |
|------|---------|---------|
```

4. **遗漏项 > 0 → 必须补充后才能进入步骤 6**

**14 个检查维度**：

| 维度 | 搜索关键词 | 应出现在 |
|------|-----------|---------|
| 默认值/自动行为 | "默认""自动""填充" | 约束条件 |
| 不可操作规则 | "不可""禁止""不允许""不能" | 约束条件 |
| 条件可见性 | "隐藏""展示""仅""点击后" | 约束条件或正常场景 |
| 角色差异 | "仅厂商""仅渠道""PSM""渠道" | 角色差异表 |
| 操作-状态关联 | "状态""操作""按钮""允许" | 状态-操作对应表 |
| 双品牌差异 | "Forenova""Sangfor""欧洲""东南亚""模板" | 约束条件 |
| 快捷操作 | "一键""填入""快捷""全部" | 正常场景或约束条件 |
| 页面入口与返回 | "入口""返回""关闭""取消" | 前端交互要求 |
| 表单联动与校验 | "必填""校验""联动""重新计算" | 前端交互要求 |
| 加载与空态 | "加载""无数据""空态""骨架" | 前端交互要求 |
| 提交过程 | "提交中""禁用""重复提交""超时" | 前端交互要求 |
| 成功与异常反馈 | "成功""失败""错误码""重试""刷新" | 前端交互要求或异常场景 |
| 展示格式 | "单位""精度""舍入""时区""枚举文案" | 前端交互要求或约束条件 |
| 兼容与可用性 | "中英文""响应式""溢出""焦点""键盘" | 前端交互要求或 DFX |

### 步骤 6：DFX 编写

> 到此步骤时，Read 加载插件内部参考文件（见顶部"按需加载索引"表格）获取详细格式。

**内嵌核心结构**（不需要读文件就能写的部分）：

```markdown
## 3. 非功能性需求

### 3.1 性能分析
#### 链路概述
[数据流转说明]
#### 响应时间（RT）
| 接口/操作 | 平均 RT | P99 RT | 说明 |
[超过 1s 基线的必须解释原因]
#### 吞吐量（TPS）
| 场景 | TPS | 说明 |
#### 容量预估
| 指标 | 当前值 | 3年预估 | 设计容量 |
#### 性能分析总结 ⭐
| 维度 | 结论 | 说明 |
**关键结论**：1. xxx 2. xxx

### 3.2 可靠性
#### 故障场景与可靠性目标
| 故障场景 | 可靠性目标 | 设计措施 |
#### 可靠性总结 ⭐
| 维度 | 结论 | 说明 |
**关键结论**：1. xxx 2. xxx

### 3.3~3.6 其他
[可维护性/开放性/安全性/可测试性，按需展开]

涉及前端时，DFX 还必须明确：
- 首屏和关键交互的性能目标、重复请求和慢请求处理；
- 浏览器兼容范围、响应式或最小视口要求；
- 中英文文案、数字/日期/时区显示规则；
- 自动化测试所需的稳定控件标识和前后端 Mock 能力。
```

**每个 DFX 子章节必须有总结表格 + 关键结论**。
