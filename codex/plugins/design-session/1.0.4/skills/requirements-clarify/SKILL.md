# Requirements Clarify

## 目标

在编写系统需求之前，把不完整或互相冲突的规划材料整理成两部分：

1. 用非技术语言说明用户要完成什么、系统每一步产生什么效果，以及流程完成后的业务结果。
2. 只提出改变业务结果、且无法由明确结论或现有代码回答的关键产品问题。

本技能不是系统需求、概要设计、接口设计、数据库设计或任务拆分。未闭合的业务决策必须标记待确认，不得自行补全；研发可基于兼容性决定的实现细节不得反向抛给产品。

## 与 analyze 的边界

- `analyze` 用于理解和沉淀某份原始材料：页面、角色、流程、字段、交互和原文证据。
- 本技能用于判断系统到底要做什么：结合原始材料和代码重建用户旅程，解释业务效果，消解伪问题，留下关键产品决策。
- 不要求用户先运行 `analyze`。已有摘要只是索引；关键结论必须回看原始材料，发现冲突或证据不足时主动回溯。

## 核心判定

### P0 判定公式

一个问题只有同时满足以下条件，才能进入产品 P0 清单：

```text
P0 = 属于本次范围
     AND 存在两个或以上会产生不同业务结果的方案
     AND 产品明确结论、原始证据和现有代码均不能决定
     AND 不回答就无法写出可验收的系统需求
```

只影响接口字段名、事务写法、定时表达式、重试次数、幂等键、表结构或代码组织的问题，默认属于系统设计，不是产品 P0。若技术选择会改变用户可见结果、资金、服务状态或业务责任，再把它改写成业务问题。

### 问题价值原则

- 问题数量不是完整性的指标。优先删除伪问题，不追求编号多或覆盖所有模块。
- 先讲清用户旅程，再提出旅程中尚未闭合的分叉。
- 先给代码事实和开发建议，再让产品确认；不要把无边界的开放题交给产品。
- 已有能力默认复用。只有新材料明确要求改变，或复用会产生不同业务结果时，才询问是否变更。

## 工作流程

### 步骤 1：先拆分需求边界

读取项目 `context.md`、`corrections.md`、当前迭代原始输入、已有摘要和相关代码。先建立范围矩阵：

| 候选事项 | 用户旅程 | 适用区域/对象 | 是否独立需求 | 与本次关系 | 依据 |
|---|---|---|---|---|---|

同一份 AI 材料中出现多个菜单、角色或业务结果，不代表它们属于同一个需求。按“是否拥有独立触发、完成效果和验收口径”判断是否拆分。

产品已经明确的区域、对象和排除项直接写成范围事实，不得换一种说法重新询问。相邻需求只记录接口边界和数据交接，不展开其状态、页面、模板、角色或异常问题。

### 步骤 2：检查摘要是否可靠

摘要只能作为索引。对每个可能进入旅程或问题清单的结论，回到原始材料核验：

- 文字、表格、页面和状态是否完整；
- HTML 脚本行为是否与文字描述一致；
- PDF 或截图中的标注、箭头、字段关系是否被遗漏；
- 不同材料是否描述了不同的时点、金额、状态或权限。

资金、计费、权限、外部数据、状态和事务一致性出现冲突时，必须重读或渲染原始材料。原型金额、日期、状态名和内存假数据默认是示例，不得直接升格为规则。

### 步骤 3：建立现有系统事实基线

只分析当前旅程涉及的 controller、service、entity、状态定义、定时任务、价格、权限和外部对接。记录：

- 现有用户入口和角色；
- 申请、审批、资金或积分变化的实际时点；
- 本地事务与外部异步动作的边界；
- 已有价格、数量、账单、模板、状态和异常能力；
- 新需求明确要求改变的部分。

代码已确定的行为写入“无需产品再确认”。如果新需求没有要求改变，就形成复用基线，不再问产品“现有是否继续”。

### 步骤 4：先写清楚用户旅程

至少完成：

1. **一句话目标**：为谁解决什么问题。
2. **范围矩阵**：本次、相邻需求和排除项。
3. **主流程**：每一步的角色、用户动作、系统反应、用户可见结果和业务效果。
4. **完成效果**：授权、账户、账单或服务分别变成什么状态。
5. **异常分支**：只展开属于本次范围、且会改变业务结果的异常。

产品版旅程优先使用短编号列表或六列以内表格。证据状态、代码位置和内部判断放内部版，不让产品从七八列宽表中寻找主线。

### 步骤 5：形成候选缺口池

从以下来源收集候选缺口，但暂时不要直接生成问题：

- 两份材料相互冲突；
- 材料与代码行为冲突；
- 新旅程出现现有模型没有的业务结果；
- 资金、计费起止、业务数据口径、服务结果或责任归属未定义；
- 原型只画成功态，失败后用户不知道发生了什么。

为每个候选项记录“它阻塞哪一步旅程”和“不同答案会产生什么不同业务结果”。写不出来的候选项通常不是 P0。

### 步骤 6：通过五道问题过滤门

按顺序过滤每个候选项：

1. **范围门**：是否属于本次独立旅程？相邻需求的问题移交，不留在本清单。
2. **事实门**：产品是否已明确，代码或现有模块是否已有答案？有答案则写入事实基线。
3. **责任门**：这是产品决定业务结果，还是研发决定实现？纯研发问题转为设计约束或待技术对接。
4. **影响门**：不同答案是否会改变用户可见结果、资金、服务、计费、权限或验收？不会则删除。
5. **可理解门**：不读代码的人能否在读完背景后直接选择或填写？不能则重写，不要把抽象术语原样抛出。

过滤后为所有未进入产品清单的候选项给出处置：`已由代码确定 / 已由产品确认 / 拆至相邻需求 / 转系统设计 / 视觉细节由开发设计`。

### 步骤 7：把问题写成可决策卡片

每个问题使用以下顺序：

1. 旅程中的具体事件；
2. 当前代码事实或材料冲突；
3. 为什么会产生不同业务结果；
4. 开发建议及理由；
5. 产品可直接选择的方案或逐项填写表；
6. 若不确认，阻塞哪条系统需求或验收。

一个标题只表达一个核心业务决策；同一生命周期内紧密关联的子项可放一张表，不要拆成多个抽象问题。

复合问题中的每个子项也必须单独通过 P0 判定公式。不能因为“允许哪些业务对象进入流程”是有效 P0，就顺带询问沿用现有的角色、按钮权限、通知方式或技术校验。

外部数据未知时，产品先确认业务口径和数据责任人；接口字段、幂等键、拉取方式和重试协议由开发与数据方继续确认，除非产品本人就是该数据契约负责人。

### 步骤 8：执行问题清单反审

提交前逐题反问：

- 如果答案是“沿用现有”，是否无需产品回答也能保守实现？若是，删除并记录复用现状。
- 是否因为看到了新页面，就误以为要重做现有模块？先检查已有能力。
- 是否在向产品询问事务、幂等、重试、字段映射或代码算法？改写为业务结果或转系统设计。
- 是否重复询问了已确认的范围、区域或排除项？直接删除。
- 是否用“激活失败、资金动作、在线数据、正式价格”等词，却没说明具体事件和用户影响？重写。
- 新功能是否只是挂在现有入口并复用现有审批动作？若材料未要求新增角色或改变职责，权限沿用现有，不询问角色矩阵或“谁可以操作”。
- 一个问题是否混入了未通过过滤门的子问题？逐项删除，不以“顺便确认”为由保留。

P0 超过 7 个是范围或过滤不足的强烈信号，必须重新执行步骤 1 和步骤 6。不要机械限制为 7 个；只有逐题通过 P0 判定公式后才能保留。

### 步骤 9：判断是否可以写系统需求

仅当以下条件全部满足时，才标记“可进入系统需求”：

- 主流程能从触发条件走到完成效果；
- 每个关键步骤都有用户动作、系统反应和可见结果；
- 资金、状态、数据来源、权限和异常分支无关键缺口；
- 材料冲突已消除或明确了目标规则；
- 所有 P0 已有答案并记录为决策；
- 相邻需求边界和交接数据已明确。

否则输出“尚不可写系统需求”，但不要生成看似完整的接口、数据库或任务拆分。

## 输出形式

代码核查和证据较多时，拆成两份：

1. **内部事实基线**：保留全部证据、代码位置、材料冲突、排除项和候选问题处置。
2. **产品确认清单**：只包含本次范围、一句话目标、可复述的用户旅程、无需再问的代码事实和最终 P0。

产品确认清单必须可独立阅读，不能依赖内部版才能看懂问题。优先控制在 5 至 7 个高价值 P0；若确有更多，按生命周期分组并说明为何不能继续合并。

按需读取 `references/output-template.md`。

## 快速分类

| 候选内容 | 处理方式 |
|---|---|
| 产品已直接确认的范围 | 写入事实，不再询问 |
| 现有代码已经实现且新需求未要求改变 | 复用基线，不再询问 |
| 现有入口、审批动作和角色职责未改变 | 沿用现有权限，不询问角色矩阵 |
| 相邻独立需求的页面、角色、状态或模板 | 拆出，只保留交接边界 |
| 事务、幂等、重试次数、字段名、定时表达式 | 转系统设计 |
| 会改变收费、资金、服务或用户结果的分叉 | 产品 P0 |
| 外部业务数据口径未知 | 产品选择口径/责任人，开发续接数据契约 |
| 纯视觉和常规交互细节 | 开发按现有设计系统补齐 |

## 改写示例

不推荐：

> 激活失败后如何恢复？

推荐：

> 本地审批完成后，外部平台可能稍后才开通成功。首期费用从本地审批通过开始，还是从外部平台实际开通成功开始？开发建议按实际开通成功起算，避免服务不可用期间收费。请确认采用哪个起算点。

不推荐：

> 在线数量的数据契约是什么？

推荐：

> 每期费用需要确定按多少席位收费。现有申请保存的是用户手工填写的授权席位，材料要求的是外部平台期末实际活跃席位，两者会产生不同费用。请确认采用哪一个；若采用外部数据，请指定数据负责人，开发再与其确认接口字段和补录方式。

## 质量门槛

- 非技术读者能复述“谁在什么时候做什么，最后得到什么结果”。
- 每个 P0 都能指向一条无法编写或验收的系统需求。
- 每个 P0 都先说明代码事实、材料冲突或业务背景。
- 已确认范围、代码已有答案和纯研发问题没有进入产品清单。
- 相邻需求没有被原始 AI 文档重新混回本次范围。
- 产品问题有建议、有边界、可直接选择或逐项填写。
- 如果读者需要根据问题反推“到底要做什么”，先重写旅程，不要继续增加问题。
