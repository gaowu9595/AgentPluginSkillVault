## 1. 严重级别和通过门槛

| 级别 | 判定 | 典型问题 |
|---|---|---|
| P0 | 会造成错误资金动作、错误数据归属、数据丢失、安全破坏或不可恢复迁移 | 重复扣款、跨渠道串账、无法对账、不可逆错误回填 |
| P1 | 设计不能被接受或不能可靠实现 | 过度设计、重复事实源、关键约束缺失、生命周期歧义、表或字段无法解释 |
| P2 | 不阻塞编码的可维护性改进 | 命名改进、非关键索引优化、解释补强 |

只有同时满足以下条件才能判定 `passed`：

- P0 数量为 0；
- P1 数量为 0；
- 所有新增、修改、复用和删除表都有结论；
- 所有新增或修改字段都有审核记录；
- 所有真实查询路径都有索引结论；
- 所有敏感数据写入都有事务、幂等和对账结论；
- 两个独立 Agent 均完成只读审核；
- 每条 Agent 发现都有主 Agent 裁决；
- 冷读解释性检查通过；
- 证据包没有未解决的阻塞假设。

不得用平均分、通过比例或 P2 改进数量掩盖任何 P0/P1。

## 2. 证据与覆盖率

审核只接受四类证据：

| 类型 | 含义 | 使用规则 |
|---|---|---|
| `CODE-FACT` | 已核验的 DDL、migration、ORM、Entity、DAL、Service、测试或运行约束 | 记录精确文件和位置；与设计冲突时必须显式处理 |
| `REQ-FACT` | 已确认的系统需求、产品决定、合同或验收规则 | 记录来源、版本和适用范围 |
| `DECISION` | 当前设计作出的技术决策 | 可以质疑；必须说明备选方案和取舍 |
| `ASSUMPTION` | 尚未证实但审核暂时需要的假设 | 不得支撑 `passed`；影响正确性时返回 `blocked` |

表覆盖率计算：`已完成结论的变更表数 / 全部变更表数`。

字段覆盖率计算：`已完成审核的新增或修改字段数 / 全部新增或修改字段数`。

两项都必须为 100%。删除表、复用现有表以及只改约束或索引的表同样纳入表清单。证据冲突不能靠投票解决；主 Agent 必须回到来源核验。

覆盖率必须能从报告中的逐表和逐字段清单重新计数。只给“10/10”“128/128”或百分比而不列出对应项时，覆盖结论无效并记为 P1；如果报告因只读或写入失败不能落盘，最终回复必须内联同等的紧凑清单。

## 3. 逐表审核

对每张新增、修改、复用或删除表逐项填写：

| 检查项 | 必须回答 |
|---|---|
| 保存的事实 | 这张表保存哪个业务事实，粒度是什么 |
| 事实类型 | 当前状态/不可变流水/计算快照/可重建投影/配置 |
| 创建方 | 哪个用户动作、接口、消息或任务创建记录 |
| 更新方 | 谁能更新哪些列，什么事件触发 |
| 读取方 | 哪些接口、任务、对账或报表读取 |
| 终态 | 记录何时结束、是否删除、保留多久 |
| 现有模型不足 | 指出已有表/字段及无法承载的具体失败点 |
| 删除挑战 | 删除该候选表后哪条当前需求会失败 |
| 合并可能 | 能否扩展已有表或与其他候选表合并 |
| 基数 | 与渠道、账户、申请、账单等实体的 1:1/1:N/N:M 关系 |
| 权威来源 | 哪张表拥有该事实，其他副本如何同步和对账 |
| 生命周期示例 | 用一组具体数字走完创建、更新、失败、终态 |

逐表结论只能是：`保留 / 合并 / 扩展现有表 / 删除 / 证据不足阻塞`。不得只写“设计合理”。

## 4. 逐字段审核

对每个新增或修改字段逐项填写：

| 检查项 | 必须回答 |
|---|---|
| 业务含义 | 用业务语言说明，不重复字段名 |
| 数据来源 | 用户输入/外部系统/计算值/其他表/系统生成 |
| 写入方与时机 | 具体接口、任务或事务步骤 |
| 更新规则 | 可变或不可变；允许变化的事件 |
| 读取方 | 具体查询、校验、展示、对账或补偿 |
| 权威性 | 原始事实/派生投影/缓存/快照 |
| 落库理由 | 不能实时计算或关联读取的具体原因 |
| 空值语义 | 分别解释 NULL、0、空字符串和缺失 |
| 默认值 | 新记录和历史回填时的值及理由 |
| 类型与单位 | 范围、精度、单位、舍入位置、时区 |
| 约束 | 唯一、外键、CHECK、枚举、跨行不变量 |
| 生命周期 | 首次赋值、变化、失效和清理 |
| 示例 | 至少一个正常值和一个边界值 |
| 证据 | 对应证据编号和来源位置 |

重点质询以下字段：`last_*`、`current_*`、计数、合计、状态摘要、复制名称、外部标识、JSON、可空外键、通用 `type/status/source/ext_info`、持久化计算值、request ID、operation ID 和重放元数据。

“为了以后扩展”“方便查询”“可能会用到”不能单独构成落库理由。

## 5. 删除挑战与过度设计

无法指出删除表后的具体失败点时，默认不得保留该表。出现以下模式时默认记为 P1，除非有当前业务和代码证据证明必要：

- 为一条流程分别建立 task、scan、claim、error 和 retry 表；
- 只有一个当前消费者，却提前建立跨领域通用持久化模型；
- 同一事实同时保存在主表、明细表和 JSON 中；
- 已有历史流水，又新增含义相同的历史明细表；
- 已有状态字段，又新增状态跟踪表；
- 只为避免 JOIN 复制字段，却没有同步和对账方案；
- 主表和明细表没有声明权威来源；
- 直接根据 AI 生成原型建立数据库字段；
- 表数量明显超过用户旅程中需要持久化的业务事实数量；
- 审计表同时控制业务状态，但没有清晰幂等契约。

通用代码抽象与通用持久化模型必须分开判断。后者需要当前的数据归属、生命周期和消费者证据。

## 6. 关系、事实源和生命周期

- 核对主键、不可变业务键、外键、多态引用、基数和删除行为。
- 为每个业务事实指定唯一权威来源。
- 对冗余投影写明同步时机、失败恢复、延迟容忍和对账方式。
- 区分当前状态、历史过程、计算快照和可重建查询投影。
- 明确父记录未创建、已结束、软删除和永久保留时的子记录行为。
- 用完整事件序列检查每张表在正常、失败、重试和人工修复后的状态。

事实归属不清、主从关系矛盾或终态不明确时记为 P1。

## 7. 类型、约束和状态机

- 核对整数上限、十进制精度、金额或积分单位和溢出策略。
- 明确舍入发生在明细、账单还是账户汇总维度。
- 明确时区、时间戳精度、账期表示和月末截点。
- 分别定义 NULL、0、空字符串和默认值，包含历史回填语义。
- 核对唯一约束、外键、CHECK、枚举和跨行不变量。
- 列出合法状态转换、触发事件、守卫条件和终态。
- 对软删除、级联删除和不可删除资金历史作出明确选择。

ORM 校验不能替代数据库必须守住的唯一性和资金不变量。

## 8. 查询与索引

先列真实查询，再设计索引。每条查询必须包含过滤、连接、排序、分页、预估行数、频率和一致性要求，并映射到候选索引。

随后从每个候选索引反查其服务的查询，核对：

- 唯一性和幂等作用域；
- 联合索引列顺序；
- 选择性；
- 部分索引条件；
- 覆盖索引收益；
- 写入放大和存储成本；
- 与软删除、状态和时间范围的组合；
- 分页排序是否稳定。

有查询无索引结论，或有索引无法关联真实查询，均记为 P1；纯性能优化且不影响可用性时可以降为 P2，但必须给出数据量依据。

## 9. 事务、并发和幂等

为每条写入路径明确：

- 事务开始和提交位置；
- 读取和更新的锁对象；
- 所有路径统一的锁顺序；
- 并发竞争和隔离级别假设；
- 稳定幂等键、唯一约束和作用域；
- 重复请求的返回语义；
- 部分成功的回滚或补偿；
- 超时后结果未知时的查询和恢复；
- 消息重复、任务重跑和人工补偿的边界。

可能重复扣款、释放、退款、还款、预留或生成账单时记为 P0。

## 10. 资金与敏感数据

涉及资金、Credit、账单、配额、库存或授权时必须识别：

- 当前余额或当前状态表；
- 业务归属表；
- 不可变历史流水；
- 计算快照或可重建投影；
- 每个资金动作的稳定幂等键；
- 事务边界和锁顺序；
- 部分成功和结果未知的恢复方案；
- 重复动作防护；
- 溢出、精度和舍入策略；
- 迁移前后的对账验证。

对账公式必须写成可由数据库现有数据独立重算的等式，并定义时间点。例如：

```text
账户当前预留总额 = 所有有效业务预留记录的剩余预留额之和
业务预留初始额 = 累计释放额 + 当前剩余预留额
流水影响额之和 = 账户余额变化量
```

同时定义不一致后的停写范围、告警、修复权限、修复流水和恢复条件。没有明确对账公式的敏感数据设计不能通过。

## 11. 迁移、回滚和容量

- 明确建表、改表、索引和约束的执行顺序。
- 说明历史数据回填、批次大小、失败续跑和幂等。
- 定义新旧版本兼容窗口以及是否双写、双读或延迟启用。
- 提供上线前后行数、唯一性、孤儿记录和敏感数据对账查询。
- 标出不可逆步骤及替代恢复方案。
- 给出初始数据量、月增长、峰值写入、保留期和归档策略。
- 只有达到明确数据量或查询退化阈值时才引入分区。

不可恢复且会破坏正确性的迁移记为 P0；缺少可执行回滚或兼容方案记为 P1。

## 12. ORM、DAL 和 Service 可实现性

- ORM 类型、默认值、索引和约束必须与 DDL 一致。
- DAL 必须声明单行或多行返回基数以及重复数据处理。
- 事务归属只能有一个明确控制方，不能由调用链多层隐式提交。
- Service 必须能在现有技术栈内实现既定锁、幂等、恢复和对账。
- 数据库特性不受当前版本支持时，必须给出兼容实现。
- 应用校验和数据库约束必须说明各自职责，不能只依赖前端或单实例进程锁。

无法映射到现有技术栈或调用链时记为 P1。

## 13. 冷读解释性

每张新增表必须在设计正文中包含：

1. 一句话用途；
2. 现有模型为什么不够；
3. 为什么不是过度设计；
4. 一组具体数据示例；
5. 一次完整生命周期示例；
6. 与相邻表的关系；
7. 最容易误解的字段；
8. 当前状态和历史过程分别由谁保存。

冷读者只能获得设计文档和证据包，不能获得原对话、预期答案或主 Agent 推理。依赖隐藏上下文才能解释时记为 P1。审核报告可以补充细节，但不能替代设计正文的解释责任。

## 14. V2 模式选择、覆盖继承与成本门禁

### 14.1 complete-baseline

完整覆盖基线必须同时保存设计/代码/证据 hash、表字段分母、100% 覆盖明细、独立 Agent 原始输出及 hash、全部发现和主 Agent 裁决。状态可以是 passed 或 failed；failed 只表示仍有问题，不表示既有覆盖证据失效。

### 14.2 change-impact-matrix

| 规则 ID | 输入 | 模式/Agent |
|---|---|---|
| `M1 no-complete-baseline=>full` | 缺 hash、覆盖清单、原始输出或裁决 | full + 双 Agent |
| `M2 failed-complete-baseline+local-check-change=>delta` | failed 基线完整，只修局部 CHECK/NULL/manifest | delta + 受影响 Agent |
| `M3 table-topology-change=>full` | 表新增/删除/合并/拆分 | full + 双 Agent + 冷读 |
| `M4 transaction-topology-change=>full` | 新资金写入路径、跨表原子边界、事实源或统一锁序改变 | full + 双 Agent |
| `M5 explanation-or-format-only=>deterministic-only` | 仅解释、示例、术语、格式 | 无 Agent |

持久化字段新增/删除/重命名改变覆盖分母，执行 full；字段类型、NULL、CHECK、索引和状态转换的局部修订在 complete-baseline 上执行 delta，并按资金影响选择 Agent。

### 14.3 coverage-inheritance

delta 报告必须列出：基线已审核表/字段、当前未变表/字段、受影响表/字段、新增 delta 结论和合并后分子/分母。继承只对 hash 可验证且未被 change manifest 命中的对象有效；禁止只写百分比或笼统写“其余沿用”。

### 14.4 transaction-topology

以下任一变化视为事务拓扑变化并回到 full：新增或删除资金 writer、改变事务控制方、改变跨表原子提交集合、改变账户/业务归属/流水的权威来源、改变所有写路径必须遵守的统一锁顺序。仅在同一 writer 内增加重算校验、收窄函数 ACL 或补充 fencing 谓词属于 delta。

### 14.5 成本门禁

- 开始前报告变更表/字段/不变量、Agent 数和读取文件数。
- delta bundle 不包含未命中的完整设计章节和代码目录。
- 自动修复复审最多一轮；P2 不触发复审。
- 401/402/403、payment/quota/auth/permission 不重试；瞬时传输错误最多缩小范围重试一次。
