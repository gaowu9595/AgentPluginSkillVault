# 概要设计编写指南

> **用途**：AI 编写概要设计时的执行流程指南。配合 `/design-session:write` 使用。
> **适用模板**：SFRD-TS-02-3.6（V3.6），即 `概要设计模板.md`。
> **核心原则**：先思考再动笔 — 把不确定性暴露在写之前，不是写完再改。

---

## 1. 输入就绪检查（写之前必须完成）

> 动笔前检查，缺一不可。缺少的标注为"阻塞项"，等补齐或标注待确认后再写。

| 检查项 | 来源 | 缺失影响 |
|--------|------|---------|
| 系统需求卡片（功能点编号 + 验收条件） | `架构设计/系统需求/` | 阻塞：§2 需求跟踪表无法填写 |
| 交互稿确认（状态机 + 字段 + 业务规则） | `.ai/*-摘要.md` 或 Figma | 阻塞：§3 接口参数不准确 |
| 待确认项已标注 | context.md 待确认问题索引 | 不阻塞写设计，但必须在 §7.2 / §4.7 中列出 |
| 编码规范已加载 | 代码仓库 `.claude/rules/` | 影响 §6 函数列表的命名和结构 |
| 上下文已恢复 | `.ai/context.md` | 影响决策一致性 |

**检查方式**：
1. 读 `.ai/context.md` — 确认当前阶段、关键决策、待确认项
2. `ls 架构设计/系统需求/` — 确认对应系统需求卡片存在
3. `ls .ai/*-摘要.md` — 确认交互稿摘要已落盘
4. 读代码仓库 `.claude/rules/01-project-structure.md` — 确认目录结构和命名规范

## 2. Gap Analysis（写之前的思考阶段）

> **核心原则：输入看起来完整 ≠ 可以直接写。** 系统需求里的 ❓ 待确认项只是显式问题，隐含问题（数据模型缺字段、状态机不完整、外部依赖协议未定）更危险 — 它们会被 AI "填"一个看似合理但未验证的答案，评审时不易发现。

### 执行方法

读完系统需求 + 摘要后，对每个功能点自问四个问题：

| 自问 | 对应章节 | 典型隐患 |
|------|---------|---------|
| 数据模型确定了吗？ | §5 DDL | 字段遗漏、类型不对、关联关系缺失 |
| 状态机确定了吗？ | §5 + §6 | 枚举不全、流转条件模糊、终态未定义 |
| 外部依赖明确了吗？ | §4.5 + §6 | 接口协议未定、超时/降级策略缺失 |
| 双品牌差异处理了吗？ | §4.5 + §6 | Sangfor vs Fornova 逻辑分支遗漏 |

### 输出格式

```
## <模块名> 概要设计 — 待决策清单

### 🔴 阻塞设计（必须先定，影响多个章节）
1. [问题描述]
   → 影响：§X.X [具体章节]
   → AI 建议：[方案 + 理由]
   → 需要你确认：[具体决策点]

### 🟡 可用兜底方案（先按兜底写，后续可调）
2. [问题描述]
   → 兜底方案：[具体方案]
   → 后续调整条件：[什么时候需要改]

### 🟢 不影响设计（记录但不阻塞）
3. [问题描述]
   → 原因：[为什么不影响当前设计]
```

### 判断标准

- **🔴 阻塞**：如果按不同答案来设计，§4.5 流程图或 §5 数据模型会不一样
- **🟡 兜底**：有一个合理的默认方案，后续调整只改局部（不动整体架构）
- **🟢 不影响**：纯实现细节或延后迭代的内容

## 3. 决策会话（用户确认）

> AI 辅助分析利弊，但**决策权在用户**。

对每条 🔴 阻塞项：
- 用户当场能定 → 记录决策结论
- 用户需要外部确认 → 确定兜底方案 + 标注"TBD + 兜底方案"
- 用户说跳过 → 标注"未决，§X.X 暂不展开"

**输出决策表**（最终写进设计文档 §7.2 遗留问题）：

| 问题 | 决策 | 状态 | 影响章节 |
|------|------|------|---------|
| [问题1] | [结论] | ✅ 已定 | §4.5, §6.1 |
| [问题2] | [兜底方案] | ⚠️ TBD | §5.2 |
| [问题3] | 暂不展开 | ❌ 未决 | §6.3 |

## 4. 写作顺序（避免返工）

> **核心洞察**：§6 函数列表会反向影响 §3 接口定义和 §5 数据结构。不要按章节号线性推进。

```
推荐顺序                          原因
──────────                        ──────
步骤1: §2 需求跟踪表              明确范围，自检列留空
步骤2: §4.2 方案选型              核心决策先定，不展开细节
步骤3: §4.3 静态结构草图          子模块 + 依赖关系
步骤4: §4.5 概要流程              Mermaid 时序图，每个核心链路一个
步骤5: §5 数据结构（DDL）         写 DDL 时常发现 §3 的参数缺漏
步骤6: §6 流程设计 + 函数列表     最耗时；写完后回头补 §3
步骤7: §3 对外接口（定稿）        根据 §5/§6 修正参数和返回值
步骤8: §4.6 DFX 特性              对照具体业务场景填写（见下方规则）
步骤9: §4.1 背景 + §4.4 架构影响  此时全貌清晰，写起来准确
步骤10: §7~§10 + Checklist        收尾
```

**关键检查点**：
- 步骤 6 完成后，**必须回查 §3**：函数列表中的参数是否都在接口定义中体现？
- 步骤 7 完成后，**必须回查 §2**：自检列是否全部填上了对应章节号？

## 5. 各章节编写规则

### §2 需求跟踪表

- 每个系统需求功能点（如 BILL-01）对应一行
- 验收条件直接从系统需求卡片复制，不重写
- "自检"列留空，等 §3/§6 写完再回填

### §3 对外接口

- **新增接口**：完整写（路径/参数/返回/错误码）
- **扩展接口**：只列新增/变更部分，注明"现有接口保持不变"
- **错误码**：从 `constant/error.py` 号段分配，列出本模块新增的全部错误码
- **接口路径**：遵循代码规范（全小写+下划线，`strict_slashes=True`）

### §4.2 方案选型

- 只列**有真正技术分歧**的决策点（不要为没有争议的选择凑对比表）
- 每个方案必须有：选择原因（一句话）+ 未选原因（一句话）+ 风险
- 如果只有一种合理方案，直接说明原因，不硬凑对比表

### §4.3 静态结构

- 用 ASCII 画组件图（Mermaid class diagram 在 Typora 显示不稳定）
- 标注子模块之间的依赖方向（谁调用谁）
- 标注与外部服务的交互（如 mss-ums、Redis）

### §4.5 概要流程

- 用 Mermaid `sequenceDiagram`（时序图）或 `graph TD`（流程图）
- **不要用 `flowchart TD`**（Typora 显示异常，见 corrections.md）
- 每个核心链路一个图，不超过 15 个步骤
- 图后附步骤说明文字（图是索引，文字是细节）

### §5 数据结构

- 用 SQL DDL 定义表结构（比 Markdown 表格更精确）
- DDL 后紧跟 Markdown 字段说明表（补充取值范围和业务含义）
- 索引单独列出，说明索引目的
- 唯一约束要标注（防止幂等问题遗漏）

### §6 流程设计

- **每个子模块独立一节**，按 6.x.1~6.x.6 标准格式
- **函数列表是评审核心**（评分权重 40% 的"设计目标达成"主要看这里）
- 每个函数必须有：功能、参数（含类型和方向 [in]/[out]）、返回值、前后置条件
- Service 接口和 DAL 接口分开列（职责不同）
- 遵循 DAL 命名约定：`insert_` / `get_xxx_by_` / `xxx_count` / `update_` / `check_xxx_exists`
- 工作量估算：按子模块估，给出人天数和依据

## 6. DFX 防套话规则

> DFX（Design for X）章节最容易写成模板套话。以下规则确保每条都关联具体业务。

### §4.6.1 安全性 — STRIDE 填写规则

**禁止**：
- ❌ "通过认证鉴权防止未授权访问" — 太泛
- ❌ "不涉及" — 除非真的不涉及，否则必须分析

**要求**：每条必须包含三要素 — **具体威胁** + **涉及组件名** + **具体措施**

| 维度 | 提问方式（对照业务场景） | 填写示例 |
|------|----------------------|---------|
| S 身份欺骗 | 哪些接口如果被未认证用户调用会造成损失？ | "未认证用户调用 repay 接口导致积分误扣 → JWT 中间件 + 角色白名单" |
| T 篡改数据 | 哪些参数如果被篡改会导致跨租户操作？ | "篡改 invoice_id 还款到其他渠道 → 校验 partner_id 归属" |
| R 抵赖 | 哪些操作如果没有审计记录会有纠纷？ | "PSM 否认推送过邮件 → timeline_event 记录操作人+时间" |
| I 信息泄露 | 哪些数据如果暴露会违反隐私要求？ | "渠道 A 看到渠道 B 的账单 → 查询强制注入 partner_id 条件" |
| D 拒绝服务 | 哪些接口如果被大量调用会影响可用性？ | "导出接口被滥用 → 上限 1000 条 + 频率限制" |
| E 权限提升 | 哪些角色如果越权会造成风险？ | "渠道用户调用推送接口 → 角色白名单限 soc_admin+psm" |

### §4.6.2 可靠性 — FMEA 填写规则

**禁止**：
- ❌ 列出所有理论上的失效模式（凑数）
- ❌ 改进措施只写"重试"或"告警"

**要求**：只覆盖**真正会出错且影响用户的场景**，每条必须有具体的检测和恢复方式

| 字段 | 要求 |
|------|------|
| 功能点 | 对应 §2 的需求编号 |
| 失效模式 | 具体描述（不是"服务异常"，而是"PG 写入超时导致部分 partner 账单生成失败"） |
| 失效影响 | 对用户可见的影响（"该 partner 无当月账单"） |
| 失效原因 | 根因（"PG 连接池耗尽"） |
| 改进措施 | **检测**（怎么发现）+ **恢复**（怎么修复）+ **预防**（怎么避免） |

### §4.6.3~4.6.9 其他 DFX

- 每项写 **1~3 条具体措施**，不写泛泛而谈
- 可测试性：列出"测试难点"和"解决方案"对照表
- 可调试性：列出"调试场景"和"诊断工具"对照表
- 可运维性：列出具体的日志前缀、监控指标、告警规则

## 7. 自检清单（写完后执行）

> 对照 Checklist 逐项过，红线项不通过则不提交。

### 步骤

1. **§2.1 自检列回填**：每个需求点的"自检"列是否都填了对应章节号？
2. **接口 ↔ 函数列表对齐**：§3 的每个接口是否在 §6 有对应的函数？§6 的每个 Service 方法是否在 §3 有接口或在定时任务中被调用？
3. **数据结构 ↔ 接口对齐**：§3 返回值中的字段是否都在 §5 表结构中定义？
4. **红线项检查**：§4.6.1（安全）和 §4.6.2（可靠性）是否完整？
5. **测试用例覆盖**：§8 是否至少覆盖每个功能点的主流程 + 关键边界 + 关键异常？
6. **关联分析**：§7.1 是否列出所有受影响的模块和共享文件？
7. **遗留问题**：所有待确认项是否在 §7.2 中列出？

### 常见遗漏

| 遗漏类型 | 检查方法 |
|---------|---------|
| 错误码未分配 | 检查 §3 列出的错误码是否在 error.py 号段内 |
| 共享文件未列 | 检查是否需要改 blueprint_register.py / error.py / application.yml |
| 软删除未处理 | 检查 §5 表结构是否有 is_deleted 字段，查询条件是否过滤 |
| 时间字段格式 | 检查是否统一为 BIGINT 毫秒（不是 TIMESTAMP） |
| 幂等未设计 | 检查写操作（生成/还款）是否有唯一约束或幂等 ID |
| TBD 兜底自洽 | 所有 ⚠️ TBD 项的兜底方案是否自洽？未决项是否标注了"待补充"？ |
| 决策表同步 | §7.2 遗留问题是否包含步骤 3 决策表的全部 TBD + 未决项？ |

## 8. 与 design-session 的协作

本指南在 `/design-session:write` 子命令中自动加载。典型流程：

```
/design-session:resume OverseaPartner       # 恢复上下文
用户: "写 XX 模块概要设计"                    # 明确任务
/design-session:write OverseaPartner        # 进入写作模式
   │
   ├── 1. 输入就绪检查（本指南 §1）
   ├── 2. Gap Analysis（本指南 §2）← 关键：先暴露不确定性
   ├── 3. 决策会话（本指南 §3）← 用户逐条确认
   ├── 4. 按推荐顺序编写（本指南 §4）
   ├── 5. DFX 按规则填写（本指南 §6）
   ├── 6. 自检（本指南 §7）
   └── 7. /design-session:save 落盘进展
```
