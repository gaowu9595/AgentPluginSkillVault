# MSS 平台 DFX 基线指标

> 本文档定义 MSS 平台各服务的 DFX（性能、可靠性、容量等）基线指标，供系统需求编写时引用。
>
> **使用方式**：编写系统需求 DFX 章节时，先查阅本文档确认基线指标，避免臆想或遗漏。

---

## 1、通用性能指标

### 1.1 接口响应时间（公司硬性指标）

| 指标 | 要求 | 适用范围 | 说明 |
|------|------|----------|------|
| **P99 响应时间** | **≤ 1s** | 所有对外/对内 HTTP 接口 | 公司层面硬性指标，无特殊审批不可突破 |

**例外情况**：
- 若接口确实无法满足 1s 要求（如大数据量报表查询），需在系统需求中明确说明原因
- 需走质量审批流程获得豁免

### 1.2 脚本/后台任务性能要求

| 指标 | 要求 | 说明 |
|------|------|------|
| CPU 使用率 | 单进程 ≤ 80%（常态），允许短时峰值 100% | 长期高 CPU 会影响同机其他服务 |
| 内存使用率 | 单进程 ≤ 2GB（常态），峰值需评估 | 超出需在需求中说明并申请资源 |
| 内存泄漏 | 不允许 | 长驻进程必须无内存泄漏 |
| 执行超时 | 需设置合理超时 | 避免脚本卡死占用资源 |

**容量规划基准**：
- 如无详细业务增长计划，按当前容量的 **3 倍**作为设计基线
- 如有业务增长计划，按 **3-5 年**业务增长预估容量

## 2、各服务性能基线

### 2.1 drme-service（智能引擎 - 审核策略）

| 指标 | 基线值 | 说明 |
|------|--------|------|
| 告警处理吞吐量 | **≥ 7 条/秒** | 审核策略进程基础性能要求 |
| 进程敏感度 | **高** | 处理量大，异常会导致告警堆积 |
| Kafka 消费模式 | 批量消费 | 按批次从 Kafka 拉取告警数据 |

**注意事项**：
- 审核策略为高敏感性进程，任何改动不得导致告警堆积
- 新增服务调用必须设置超时，并在函数内部完成异常捕获
- 异常时必须兜底处理，不得抛出异常导致批次处理中断

### 2.2 mss-event-mgr（事件管理）

| 指标 | 基线值 | 说明 |
|------|--------|------|
| 事件详情接口 RT | **≤ 1s**（P99） | 同步 HTTP 请求，Flask 框架 |
| 告警查询重试 | 3 次，指数退避 | AlarmDataSyncSrv 跨服务调用 |

**注意事项**：
- 事件详情为用户直接操作的页面接口，RT 敏感
- 跨服务调用（如查询告警、资产）需计入总 RT
- 现有告警查询已有重试机制（3 次 + 指数退避），新增服务调用需评估对总 RT 的影响

### 2.3 mss-alarm-mgr（告警管理）

## 3、跨服务调用基线

### 3.1 内网服务间调用

| 指标 | 基线值 | 说明 |
|------|--------|------|
| 单次调用 RT | **< 100ms**（P99） | 同机房内网调用 |
| 超时设置 | **≤ 3s** | 避免调用方长时间阻塞 |
| 重试策略 | 视场景决定 | 高敏感进程不建议重试，接口类可适当重试 |

### 3.2 数据库查询

| 数据库 | 指标 | 基线值 | 说明 |
|--------|------|--------|------|
| MongoDB | 单次查询 RT | **< 50ms** | 需有合适索引 |
| PostgreSQL | 单次查询 RT | **< 50ms** | 需有合适索引 |
| ClickHouse | 单次查询 RT | **< 500ms** | 大数据量分析查询 |
| Redis | 单次操作 RT | **< 5ms** | 缓存读写 |

## 4、可靠性基线

### 4.1 异常处理原则

| 场景 | 要求 | 说明 |
|------|------|------|
| 高敏感进程（如审核策略） | 函数内部必须完成异常捕获 | 不得因单条数据异常导致批次处理中断 |
| 接口类服务 | 外层统一异常处理 | 返回规范错误码，不暴露内部异常 |
| 弱依赖服务调用 | 必须有兜底逻辑 | 依赖服务不可用时降级处理，不阻塞主流程 |

### 4.2 服务依赖分级

| 依赖类型 | 定义 | 故障处理 |
|----------|------|----------|
| 强依赖 | 依赖服务不可用时，当前功能无法完成 | 返回错误信息，提示用户 |
| 弱依赖 | 依赖服务不可用时，当前功能可降级完成 | 兜底为默认值，继续主流程 |

## 5、容量基线

### 5.1 规划原则

| 原则 | 说明 |
|------|------|
| 无详细计划时 | 按当前容量 **3 倍**设计 |
| 有增长计划时 | 按 **3-5 年**业务增长预估 |
| 数据模型 | 需说明当前生产数据量、测试环境等比数据、数据准备方式 |

### 5.2 当前生产规模参考

> 数据采集时间：2026-01-26 至 2026-01-30（5天样本）

| 指标 | 日均值 | 峰值估算（3倍） | 说明 |
|------|--------|----------------|------|
| 客户数 | 约 3000 | 9000 | - |
| 日均告警量（alarm） | 约 46 万条 | 138 万条 | mss_usecase 入库 |
| 日均告警量（xdr_alarm） | 约 252 万条 | 756 万条 | mss-xdr 入库 |
| **日均告警总量** | **约 298 万条** | **894 万条** | 两个入口合计 |
| 日均事件量 | 约 6200 条 | 18600 条 | - |

### 5.3 入库性能基线

| 仓库 | 进程名 | 日均处理量 | TPS（平均） | TPS（3倍峰值） | 入库表 |
|------|--------|-----------|------------|---------------|--------|
| mss_usecase | op_alarm_* / hw_alarm_* | 46 万条/天 | 5.3 条/秒 | 16 条/秒 | alarm |
| mss-xdr | ai_alert_access_insert | 252 万条/天 | 29.1 条/秒 | 87 条/秒 | xdr_alarm |
| **合计** | - | **298 万条/天** | **34.4 条/秒** | **103 条/秒** | - |
| mss-event-mgr | 事件生成 | 6200 条/天 | 0.07 条/秒 | 0.21 条/秒 | Event_info |

**设计建议**：
- 告警入库 TPS 设计基线：**≥ 100 条/秒**（覆盖 3 倍峰值）
- 单条告警新增 authorization_type 字段（约 10-20 字节），对入库性能影响可忽略

## 6、编写 DFX 章节的检查清单

编写系统需求 DFX 章节时，按以下清单逐项检查：

### 6.1 性能分析

- [ ] 是否列出所有新增/修改的接口？
- [ ] 每个接口是否有 P99 RT 指标（≤ 1s）？
- [ ] 是否有吞吐量（TPS）要求？
- [ ] 是否有并发量要求？
- [ ] 如涉及脚本/后台任务，是否说明 CPU、内存要求？
- [ ] 是否有容量规划（3-5 年增长）？
- [ ] 是否有性能分析总结表？
- [ ] 总结是否包含关键结论（≥ 3 条）？

### 6.2 可靠性

- [ ] 是否列出所有故障场景？
- [ ] 每个故障场景是否有设计措施？
- [ ] 高敏感进程是否说明异常保护机制？
- [ ] 服务依赖是否分级（强/弱依赖）？
- [ ] 是否有可靠性总结表？

### 6.3 可测试性

- [ ] 是否覆盖四个维度（可理解性、可观察性、可控制性、可追踪性）？
- [ ] 每个维度是否有实现方式和重要性？
- [ ] 是否有可测试性总结表？
