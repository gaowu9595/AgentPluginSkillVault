1）系统需求的安全性项必须参考：

③ 识别是否涉及渠道外网版接口权限点变更。

④ 识别海外版本新增功能要是否涉及海外合规要求；【海外组】

⑤ 如涉及高权重比迭代版本，识别完后需求评审时需邀请SDL小组共同评审（提前通知）

## 3、非功能性需求（DFX）编写要求

为确保需求文档的质量与可测试性，非功能性需求（DFX）部分必须完整、清晰、可量化。请严格遵守以下要求：

### 3.1 基本原则

- **完整性**：本节所有字段均需填写，不允许为空。
- **明确性**：如某项需求确实不适用于当前模块，应明确填写"不涉及"并简要说明原因，避免使用"待定"或"后续明确"等模糊表述。
- **可量化**：所有性能、容量等指标必须提供具体、可测量的数值，作为后续测试验证的基准。

### 3.2 关键内容项细化要求

#### 3.2.1 性能需求

必须包含以下可量化指标，**禁止使用"性能不下降"、"快速响应"等模糊描述**：

**响应时间（RT）**：
- 必须明确分位数要求，例如平均响应时间及P99响应时间小于1s。
- 公司基线要求为1秒内。
- 若因特殊原因无法满足（如原有设计为3秒），必须说明原因并走质量备案流程。

**吞吐量（TPS）**：
- 需定义系统或核心接口在特定压力下每秒可处理的事务数。

**并发能力**：
- 需明确并发用户数或并发请求数。

**容量预估**：
- 新增或修改的服务/接口，需基于业务规划进行容量预估。
- 建议按3-5年的业务增长进行设计。
- 若无详细规划，可简单按当前容量的3倍进行预估
- 示例：基于当前3000客户、150服务经理，预估3-5年达15000客户、500服务经理，即按约5倍容量设计

**数据模型**：

数据模型构建一般包含：
- **限制条件**
- **数据量**：实际生产环境的数据量是多少，在性能测试环境如何的等量代换
- **数据类型**：基础数据、热点数据、缓存数据、特殊数据
- **数据特点**
- **准备方式**：copy真实环境数据、预埋铺底数据、脱敏生产数据等

基础数据也称为铺底数据，比如客户维度的资产数、设备数，服务经理维度的告警数、事件数等；铺底数据目的是与线上保持一致（至少数量分布一致），再结合线上增长率，确认预埋数据量级及预埋方式。涉及到压测时需要校验的数据，包括数据大小、数量、分布。

#### 3.2.2 接口范围

需清晰列出本次版本新增、修改或与之相关的所有内部与外部接口列表（包含服务名、URL、简要功能）。

若接口信息在需求阶段暂无法完全明确，必须在备注中说明，并规定最晚在开发设计阶段终版设计文档中必须补充完整。

### 3.3 其他DFX属性要求

对于可靠性、可维护性、安全性、开放性等，需：

**针对性分析**：
- 结合本模块的特点进行分析，而非简单罗列通用要求。

**明确设计/实现约束**：
- 描述为实现该属性而需要采取的具体技术措施或遵循的规范
- 如：服务多实例部署、日志需包含TraceID、接口入参必须校验等
