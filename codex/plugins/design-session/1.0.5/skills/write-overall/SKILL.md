# write-overall（总体设计编写）

**参数**：`$ARGUMENTS` = `<项目目录>`

**REQUIRED BACKGROUND:** Read `shared/design-session-engine.md` for path conventions.

## 前置条件

当前阶段应为"阶段2 总体设计"。如不确定，先执行 `/design-session:status`。

## 执行流程

```
步骤1 输入就绪 → 步骤2 写作范围 → 步骤3 Gap Analysis → 步骤4 决策会话 → 步骤5 编写 → 步骤6 DFX → 步骤7 自检 → 步骤8 完成
```

> **核心原则：站在架构师评审视角写设计。** 回答"为什么这样设计"比"设计了什么"更重要。

### 步骤 1：输入就绪检查

1. 读 `<项目>/.ai/context.md` — 确认当前阶段和关键决策
2. 检查用户需求 / 技术规划文档是否存在
3. 检查 DFX 基线和安全需求是否已输入
4. 检查前期预研结论是否已落盘（如有预研）

缺少阻塞项 → 暂停，告知用户需要先补齐。

### 步骤 2：确认写作范围

询问用户：
- 主写 §1.1（架构技术需求）还是 §1.2（特性技术需求）还是两者都写？
- DCP 阶段？（DCP2 部分设计 / DCP3 完整设计）
- 哪些模块纳入本次总设范围？

### 步骤 3：Gap Analysis（总设级）

> **目标**：读完输入文档后，输出"待决策清单"，让用户在写之前解决不确定性。
> **不要跳过这一步直接写。** 总设级的架构决策错误会影响所有下游模块。

**执行方法**：

1. 读需求/规划文档，提取核心设计点
2. 对每个核心设计点，自问四个问题：
   - 架构边界确定了吗？（哪些服务在范围内，哪些作为外部依赖）
   - 方案选型有备选吗？（不能只有一个方案）
   - DFX 目标量化了吗？（不能只有定性描述）
   - 长期演进考虑了吗？（不能只看当前版本）
3. 读 context.md 的待确认问题索引
4. **输出待决策清单**（分三级）：

```
## [版本/项目名] 总体设计 — 待决策清单

### 🔴 阻塞设计（必须先定，影响架构方向）
1. [问题描述]
   → 影响：§X.X [具体章节]
   → AI 建议：[方案 + 理由]
   → 需要你确认：[具体决策点]

### 🟡 可用兜底方案（先按兜底写，后续可调）
2. [问题描述]
   → 兜底方案：[具体方案]
   → 后续调整条件：[什么时候需要改]

### 🟢 不影响设计（记录但不阻塞）
3. [问题描述]
   → 原因：[为什么不影响当前设计]
```

5. **等待用户逐条过** — 不要自行假设答案

### 步骤 4：决策会话

> 用户逐条确认待决策清单。AI 辅助分析利弊，但**决策权在用户**。

对每条 🔴 阻塞项：
- 用户当场能定 → 记录决策结论
- 用户需要外部确认 → 确定兜底方案 + 标注"TBD，兜底方案=XXX，确认后可能调整"
- 用户说跳过 → 标注"未决，§X.X 暂不展开，后续补充"

对每条 🟡 兜底项：
- 用户同意兜底 → 确认
- 用户有更好方案 → 更新

**输出决策表**（写进设计文档 §6.3 遗留问题）：

| 问题 | 决策 | 状态 | 影响章节 |
|------|------|------|---------|
| [问题1] | [结论] | ✅ 已定 | §4.1, §1.1.6 |
| [问题2] | [兜底方案] | ⚠️ TBD | §5.2 |
| [问题3] | 暂不展开 | ❌ 未决 | §4.5.2 |

### 步骤 5：按推荐顺序编写

**基于步骤 4 的决策表动笔。** 推荐顺序（不按章节号线性推进）：

1. §2 设计目标（先定"要达到什么"）
2. §1 技术需求设计 + 方案选型（核心决策）
3. §4.1 软件总体架构（五视图）
4. §4.2-§4.3 系统流程（主流程 + 辅助流程，导出模块接口）
5. §4.4-§4.5 数据结构 + 模块设计
6. §5 关键特性设计（DFX）
7. §0 引言 + §3 硬件方案（此时全貌清晰）
8. §6-§8 总结 + 变更 + 修订（收口，§6.3 从决策表填充）

**画图工具选择**：
- 时序图/简单流程图 → Mermaid 内嵌（`sequenceDiagram` / `graph TD`）
- 架构图/部署图/数据流图/模块依赖图 → 使用 draw.io skill 生成 .drawio + 导出 PNG
- 图文件放 `diagrams/` 目录，文档中用 `![](diagrams/xxx.png)` 引用
- 修改 draw.io 图时，读取现有 XML 通过节点 ID 精确修改，不重新生成

**TBD 处理规则**：
- 状态 ⚠️ TBD 的 → 按兜底方案写，文档内标注 `<!-- TBD: 待确认后可能调整 -->`
- 状态 ❌ 未决的 → 该章节写骨架框架，标注"待补充"，不编造内容

### 步骤 6：DFX 防套话

> 总设的 DFX 写"系统级目标和策略"，不是模块级实现细节。但同样不能写套话。

**§5.1 安全性**：每条必须有四要素 — 资产/威胁场景/安全措施/残余风险
- ❌ "通过认证鉴权防止未授权访问"
- ✅ "租户告警数据 → 伪造JWT跨租户查询 → JWT签名验证+租户ID从token提取 → token泄露依赖TTL"

**§5.2 可靠性**：必须有三层 — 目标定义 → 故障场景分析 → 实现方案
- ❌ "采用主备架构保证高可靠"
- ✅ "故障检测率≥95% → MongoDB主节点宕机/写入失败 → 副本集自动选主(10s)+应用层重试(3次)"

**§5.3-§5.9 其他 DFX**：每项必须有四要素 — 目标/场景/机制/验证
- ❌ "支持监控告警"
- ✅ "故障定位<15min → 查询超时需定位根因 → 分布式链路追踪+Grafana分层仪表盘 → 故障注入演练验证"

### 步骤 7：自检

1. **需求承接**：每个关键需求都有承接章节？
2. **目标量化**：§2 每项有数值 + 验证方式？
3. **方案选型**：至少一个核心点有备选比较？准则来自业务特征？
4. **架构完整**：§4.1 五视图覆盖（不涉及写原因）？
5. **DFX 红线**：§5.1 安全 + §5.2 可靠性不是套话？（逐条检查：每条安全措施是否有四要素 — 资产/威胁场景/安全措施/残余风险？缺任一要素 → 打回补充）
6. **流程导出**：§4.2 主流程导出了模块接口？
7. **风险收口**：§6.2 风险有措施？§6.3 遗留有时间+责任人？
8. **TBD 复查**：所有 TBD 兜底方案自洽？未决项标注"待补充"？
9. **章节完整**：无留空章节（不涉及写原因）？
10. **安全架构完整性**（如系统有用户接口）：§5.1 是否覆盖了认证方案、权限模型、数据隔离策略、审计机制？缺失任一项 → 补充

### 步骤 8：完成提醒

建议执行 `/design-session:save` 落盘进展。
