# 接口必要性、源码下钻与可读性检视

本规则用于编写或审核本次新增、扩展、替换的API、内部调用或消息契约。先回答为什么需要，再写全如何使用。沿用设计模板，不新增独立门禁、固定Agent轮次或一套“精简版设计”。

## 1. 确定检查对象和停止边界

先从用户操作/后台任务列出本次调用链，核对设计接口清单与实际调用方。清单包含对外入口及本次依赖的内部调用；不能因为“内部接口”跳过。每项标记新增/扩展/原样复用及唯一详细定义位置。

- 新增/变更接口：检查所有请求、响应及错误字段，含嵌套字段与公共外壳；公共定义只检查一次，其余接口明确引用。
- 原样复用：检查本次使用的字段、过滤条件、权限、失败及容量是否适用；准确旧契约可直接引用，不重审无关字段。
- 只改文字/排版：核对语义未变及链接即可，不强制源码下钻或重新做字段矩阵。
- 首次全量检查后，局部修订只检查变动项及依赖它的消费者、权限、缓存/持久化和测试。若范围扩大，说明新增影响，不悄悄全仓扫描。

报告记录接口总数、各自处置与未覆盖项；不能用“已抽查几个”表示所有接口已审。相同来源、使用步骤和取舍完全一致的普通字段可分组，但须列出准确字段路径；有独立规则的字段单列。

## 2. 先证明接口存在的必要性

对每条新增/变更接口，依次回答并把结果写回对应接口章节：

1. 哪个当前用户动作或后台任务调用它？用户最终得到什么结果？纯技术辅助接口也须关联具体业务链及不可缺少的技术作用。
2. 已有接口/Service能提供哪些能力？列实际方法/路由及关键实现位置，区分本迭代前已存在和本轮拟新增。
3. 直接复用、兼容扩展、专用适配、新增接口中哪些可行？只比较有实际可能的方案，指出差距是数据范围、规则、权限、批量能力、性能还是副作用；没有替代方案时不用凑对比表。
4. 删除或合并该接口后，哪个当前场景会失败？不能仅回答“职责更清晰”“方便扩展”。
5. 选定方案会影响哪些旧调用者和公共行为？接口数量少、改动仓库少都不能单独证明方案更好。

接口章节可用三列表：`选择 | 现有能力及具体缺口 | 采用/不采用的理由与影响`。完整字段表仍只维护一处。

**判定示例**：旧单客查询返回原始明细，新场景要多客户完整分类计数。“已有查询，直接循环”不足以通过；要核实是否每次全量读取、过滤是否一致、并发/调用数能否满足负载。若有满足语义和预算的批量能力则复用；没有时再选择扩展或专用查询。不能预设必须新增。

## 3. 外部依赖按风险下钻到实现

至少串清：`业务调用方 → 客户/实例定位与认证 → 源端入口 → 业务处理 → 实际查询/缓存及转换 → 返回适配 → 页面或后续动作`。跨仓库按这条链找文件，不按仓库目录从头读到尾。

遇到统计/金额/权限、多实例、陌生模块、修改公共功能，或旧能力能否复用不明确时，必须继续读取决定结果的Service、DAL/模型和转换逻辑。仅引用Controller、方法名或注释不能证明结果正确。每个实质结论给文件+符号/行号，并说明该代码证明了什么；源码缺失则指出具体缺哪一段。

| 需要核实的事实 | 操作与必须说明的结果 |
|---|---|
| 数据范围与过滤 | 查看实际WHERE/查询条件、删除/在服/类型过滤、去重、关联基数；给出一个会被纳入或排除的边界例子 |
| 字段及转换 | 对照真实模型、投影和转换函数，核实字段存在、单位、枚举、缺省及null；同名字段不自动视为同义 |
| 缓存/权威来源 | 查看实际读取的是原始表、日统计、缓存还是明细接口；涉及新鲜度时追到写入/刷新机制，不能由update_time猜出完整水位 |
| 完整读取与错误 | 查看分页是在数据库还是读全量后切片、是否截断、失败是否变为空集合；区分真实0和未知/失败 |
| 复用与公共影响 | 查直接调用者和默认行为，比较复用业务函数、专用适配、最小公共扩展；复制规则时说明后续同源验证/维护位置，不为隔离而无控制复制 |
| 跨实例与权限 | 标识在哪个实例内唯一、实例如何选择、结果如何关联、谁核验资源归属；复用已运行认证链，不凭接口名字新增免鉴权或另一套认证 |

数据需与另一页面一致时，写出准确的对照页面/接口/查询条件。概览、列表、缓存统计可能各有口径；“来自同一张表”或“都叫在线数量”不能证明一致。发现旧缺陷时，区分保持兼容和本轮修复，说明用户影响，不顺手修改公共规则。

区分三种证据：**已核实代码事实**、**本期拟实现方案**、**编码后环境验收**。用户负责两端开发时，新增协议是当前设计任务；只有缺失具体业务选择或实现依据才列设计阻塞，不笼统写“等待对方冻结”。真实索引、配置、网络性能待实测不等于接口不能设计；若连关键标识或读取方式都不确定，也不能把它推迟成普通联调任务。

## 4. 逐字段必要性检查

先把字段放入处理步骤，再做取舍。对请求字段问“谁决定、服务端在哪用”，对响应字段问“来源是什么、哪个消费者据此做什么”。页面展示、关联校验、授权、幂等、恢复和审计都可以是具体用途，不能只找UI使用方。

每个字段回答以下五问，答案归入原字段说明或同章节的紧凑取舍表，不另建重复DTO：

1. **来源和决定方**：用户选择、可信服务端身份/配置、外部响应还是计算结果？能由服务端确定的值为何允许客户端传？
2. **使用方和步骤**：写出页面控件/处理函数/流程步骤，以及字段改变的具体判断或输出。“查询用”“校验用”“便于排障”不算完整答案。
3. **删除影响**：假设不传/不返此字段，描述会失败的当前场景或不再能保证的约束；也允许结论是没有影响。
4. **更小替代**：能否合并公共外壳、由已有字段无歧义推导、只留后台或复用既有标识？转移计算会不会使口径分散、丢失失败区别或破坏权限？
5. **最终取舍及兼容**：保留/删除/合并/改名/仅内部/待证据，给具体理由。对已发布字段先检查消费者和兼容承诺，未知消费者不能直接删。安全/幂等必要字段不能因页面没展示而删除。

取舍记录格式：

| 字段路径 | 来源 → 使用方/步骤 | 不提供时的具体影响 | 取舍及兼容依据 |
|---|---|---|---|
| response.result.item_id | 原记录主键 → 点击详情时定位记录 | 只有同名标题无法选中原记录 | 保留，使用既有详情标识 |

不要求删掉固定比例字段；零删除也可通过，但必须有上述依据。接口精简后反查功能是否有缺口，例如异常列表是否也能翻页、未知与0是否仍可区分、重试是否仍可识别原操作。

### 容易空泛的字段：如何判断

| 情况 | 不合格解释 | 合格判断方法 |
|---|---|---|
| version字段 | 以后升级会用到 | 当前是否实际选择不同处理分支、兼容期/消费者是什么？没有分流用途可省；确有协议协商则保留并定义双方行为。内部缓存格式版本与HTTP参数分开判断 |
| as_of/时间字段 | 保证一致性 | 到底限制查询截止、表示采集时刻还是读取历史快照？查实际时间谓词/存储能力；只限制日期不能宣称冻结持续变动计数。按实际作用命名，明确时区、单位和边界 |
| 重复ID/摘要 | 更安全可靠 | 指出参与哪项校验；已有复合键足够关联则可合并，缺它会串客户/实例则保留。内部构建标识不因后台需要就必须返浏览器 |
| 显示名/派生值 | 能算出来所以删 | 明确哪个稳定字段和哪条规则能唯一推导；本地文案可映射，权威金额/统计不应为了少字段散落到多个客户端重算 |
| request_id/操作ID | 页面看不到所以删 | 跟踪日志、提交幂等、超时结果查询是不同用途；确有用途则保留并解释，不能按名字一律保留或删除 |

## 5. 图、参数表与非功能设计如何验收

先写整体方案和一个业务例子，再定关键流程，最后定稿API。简单单步查询可用短步骤；跨系统、并发聚合、异步/状态转换或关键失败分支使用流程图/时序图。图标清参与方、调用方向、关键条件与失败出口；关键参数放到首次决定行为的位置，其他字段留在表内，不画满整张DTO。

流程图沿用design-guide的渲染约束：使用 `graph TD`，不用 `flowchart TD`；节点文字加引号，不在标签内写字面方括号或反斜杠n。时序图使用 `sequenceDiagram`。写完实际解析/渲染并查看，不能只数图块是否存在。

请求/响应仍按design-guide完整说明路径、中文含义、类型/单位、必填/空值、默认/枚举和来源/用途。嵌套字段明确到路径或命名类型，公共外壳引用一次。JSON是联调样例，不能代替这些说明。新增/变更接口图表需与方法、字段名、处理顺序和失败行为一致。

非功能章节按 `具体场景/负载假设 → 处理措施及实现位置 → 用户可见结果 → 验证办法与通过目标` 编写。举例：“部分来源超时”要交代是否显示旧数据/局部数据、是否允许重试和如何标注完整性；“使用缓存提高性能”不足以通过。

多实例查询需核算实例数变量、最大客户/记录数、每批规模、调用总数、共享并发/排队和总截止；交代全局统计/排序/分页在哪做。缓存需说明键的权限/实例隔离、生命周期、规则变化失效和失败恢复。数值分别标已测结果、目标或工程初值；快速失败不算性能达标。已有能力可复用则引用，不强制新建本地统计表、缓存或任务进程。

**脱离对话复述检查**：审核者只依据指定设计章节，复述一个主流程和一个关键失败场景，并指出关键字段在哪起作用、调用方如何展示/恢复。若需要编写者临时补充未写下的事实，回填原章节。已经写明且能准确引用的内容不重复展开；无需为每个简单接口新派Agent。

## 6. 结果、传播与成本限制

将下列证据并入原content_gate报告；详细字段仍留在原设计章节。模板脚本只证明结构/篇幅，Schema只证明形状，二者都不能证明字段必要性或业务正确性。

| 检查对象 | 通过时应能找到的证据 | 不能通过的情况 |
|---|---|---|
| 接口集合 | 新增/变更清单、当前场景及复用取舍 | 新增接口没有当前用途，或只凭旧接口名字决定复用 |
| 外部依赖 | 风险下钻表中的实际规则/代码证据及缺失边界 | 核心过滤、标识、单位或权限仍靠猜测 |
| 字段集合 | 所有适用字段的来源、具体消费者、删除影响及取舍 | 只有“必要/提高扩展性”结论，或遗漏响应外壳/嵌套字段 |
| 可读流程 | 正常/关键失败复述、图表与契约一致 | 有图有表但说不出参数在哪起作用，失败后行为缺失 |
| 容量及传播 | 负载依据/验收目标；变更后调用方、Schema、例子、权限和缓存影响已核对 | 无依据承诺性能；只改中文说明未改机器契约或消费者 |

缺证据则记录具体未完成项，不能先填passed。影响正确性、安全或当前实现的缺口须补齐才能通过；可选润色按P2记录，不循环审核。某一项需要进一步取证时保留其他项已完成结果，不能自动扩大成全量设计重写。删除冗余字段若属于方案调整而非硬性错误，说明可编码影响，不能把所有优化都升级成产品P0。

普通字段由主Agent自审；真正的业务选择、跨团队职责变化或无法自行确认的关键缺口才向用户提问，并附具体例子及建议。用户要求逐接口讨论时每次围绕一条链路，最后汇总保留/删除/未决；不要把纯技术取证工作交给用户。

独立Agent只在风险或既有审核规则需要时使用，限定方向与文件范围。验证本指南时，可给独立Agent未附标准答案的中性需求、候选契约和最小源码，检查是否识别无用途字段、保留必要校验并找到实际语义差异；不能仅用关键字测试声称执行效果有保障。正式项目仍沿用数据库/安全审核的原预算，不新增一轮固定全量审查。
