**REQUIRED BACKGROUND:** Read `shared/design-session-engine.md` for path conventions, layer architecture, and change propagation mechanism.

## change（显式变更传播）

### change 子命令参数格式

```
# 新增变更
/design-session change "变更描述"
/design-session change "变更描述" --scope=spec      # 只传播到系统需求（P0）
/design-session change "变更描述" --scope=design    # 只传播到详细设计（P1）
/design-session change "变更描述" --scope=all       # 全量传播（默认）
/design-session change "变更描述" --scope=auto      # AI 根据当前阶段自动判断

# 处理变更追踪里已有的未完成 checkbox
/design-session change --pending                    # 处理所有未完成项
/design-session change --pending --scope=p0         # 只处理 P0 未完成项（评审前用）
/design-session change --pending --scope=p1         # 只处理 P1 未完成项（编码前用）
/design-session change --pending --scope=all        # 处理全部未完成项

# 带项目目录
/design-session <项目目录> change "变更描述" --scope=spec
/design-session <项目目录> change --pending --scope=p0
```

**--scope 说明**：

| scope 值 | 传播范围 | 典型使用时机 |
|---------|---------|------------|
| `spec` | 只更新系统需求、context.md、对接文档（P0） | 评审前 |
| `design` | 只更新详细设计（评审前=P1，评审后=P0） | 编码前 |
| `p0` | 处理变更追踪中所有 P0 未完成项 | 评审前清零 / 编码前清零（评审后详细设计升为P0） |
| `p1` | 处理变更追踪中所有 P1 未完成项 | 编码前清零 |
| `all` | 全量传播（P0+P1+P2） | 里程碑节点 |
| `auto` | AI 根据当前阶段自动判断 | 不确定时用 |

**--pending 说明**：
- 不是新变更，而是处理变更追踪里已有的未完成 checkbox
- 先读变更追踪，列出符合 scope 的未完成项，逐条确认后执行
- 每完成一个文件立即打勾，不等全部完成再更新
- **变更描述**（必填）：用引号包裹的变更内容说明

---

**目标**：用户说变更点，AI 自动完成"分析→定级→记录→传播"全流程。

**设计理念**：
- **用户只需说变更内容**，不需要关心 scope/级别/文件清单
- AI 自动：提炼变更点 → Grep 扫描影响范围 → 输出影响分析表 → 按当前阶段自动定级 → 执行 P0 传播 → 登记延后项
- **所有影响文件都记录**（含"不改"的理由），后续可追溯、可批量刷新

**项目检测逻辑**：
1. 有项目参数 → 直接用
2. 无项目参数 → 搜索工作根目录下所有 `.ai/context.md`
   - 找到 1 个 → 自动使用
   - 找到多个 → 列出让用户选
   - 找到 0 个 → 提示用户指定项目目录

**参数处理**：

- **无 --pending**（新增变更模式）：
  - 解析变更描述，走变更传播流程
  - **不再需要 --scope 参数**，AI 根据 context.md 中的当前阶段自动判断优先级
  - 用户仍可指定 `--scope=all` 强制全量传播（如里程碑刷新）

- **有 --pending**（处理已有未完成项模式）：
  - 读变更追踪，列出所有未勾选的 checkbox
  - `--scope` 控制处理范围：
    - `p0`：只列出并处理 P0 未完成项
    - `p1`：只列出并处理 P1 未完成项
    - `p2`：只列出并处理 P2 未完成项
    - `all`（默认）：列出全部未完成项
  - 列出后逐条让用户确认，确认后逐个执行更新，每完成一个立即打勾

**步骤**：

1. **确定项目目录**（按上述检测逻辑）

2. **加载上下文**
   - 读 `<项目>/.ai/context.md`（了解当前阶段和决策）
   - 读 `<项目>/架构设计/变更追踪.md`（了解已有变更，确定 CHG 编号）

3. **提炼变更点**
   - 用户输入可能是一段话、多个问题、甚至是讨论过程中的结论
   - AI 提炼出**具体变更点**（如"删除渠道禁用/删除功能"、"渠道级别和PSM关联合并到编辑接口"）
   - 如果输入包含疑问/背景/非变更内容 → 过滤掉，只留真正的变更
   - 如果不确定 → 向用户确认

   **⚡ 编码阶段快速识别：实现细节变更不走传播流程**

   提炼完变更点后，先做一次"设计文档是否感知"的判断（仅编码阶段生效）：

   | 变更特征 | 判断 | 处置 |
   |---------|------|------|
   | 涉及 API 路径/参数/返回字段 | 设计感知 | 继续走完整流程 |
   | 涉及数据库表字段增减/改名 | 设计感知 | 继续走完整流程 |
   | 涉及跨模块调用契约/错误码含义 | 设计感知 | 继续走完整流程 |
   | 函数内实现换法/算法替换/变量改名 | 仅代码 | ⚡ 快速路径（见下） |
   | 补充错误处理/日志/注释 | 仅代码 | ⚡ 快速路径（见下） |
   | 代码组织/目录微调/提取工具函数 | 仅代码 | ⚡ 快速路径（见下） |

   **⚡ 快速路径**（命中"仅代码"时直接执行，不走步骤 4-8）：
   1. 告知用户："此变更属于实现细节，设计文档不需要更新，直接改代码即可"
   2. 在变更追踪追加一行备注（不建 CHG，不建 checkbox）：`> 代码细节：<描述>（YYYY-MM-DD，不影响设计）`
   3. 结束

4. **影响分析（核心步骤）**
   - 对每个变更点，用 Grep 搜索相关关键词
   - 自动判断当前阶段（从 context.md 读取）

   **⚠️ 方案确认副作用检查**（影响分析时必执行）：
   变更点中含以下模式时，必须额外展开检查，不能只停留在"已确认"层面：
   - `"某侧加字段"` / `"调用方加字段"` → Grep 对应详细设计，检查数据模型是否已有该字段；没有 → 加入 P0 影响范围
   - `"服务零改动，由 X 侧适配"` → 检查 X 侧详细设计的数据模型/接口是否已体现适配内容
   - `"方案 X：调用方维护映射"` → 检查调用方详细设计是否有对应表结构/字段定义

   - **输出影响分析表**（先展示给用户确认，再执行）：

   ```
   ## CHG-XXX 影响分析

   **变更点**：
   1. 删除渠道禁用/删除功能
   2. 渠道级别和PSM关联合并到编辑接口
   3. 删除渠道缓存

   **当前阶段**：编码阶段（系统需求评审后）

   | 文件 | 处置 | 理由 |
   |------|------|------|
   | 详细设计/渠道管理详细设计.md | ✅ P0 立即改 | 编码事实源，删除状态机/缓存/接口 |
   | 系统需求/渠道管理-系统需求.md | 🔒 锁定 | 评审后不改，记录待刷新 |
   | 顶层设计/模块功能清单.md | ⏸️ P2 延后 | 非编码依赖 |
   | 详细设计/账号管理详细设计.md | ❌ 不涉及 | 账号模块不引用渠道状态机 |

   确认后开始执行 P0 项？
   ```

   **处置类型**：
   - `✅ P0 立即改`：当前阶段的核心文档，立即更新
   - `⏸️ P2 延后`：非核心文档，登记到变更追踪，后续 `--pending --scope=p2` 批量刷新
   - `🔒 锁定`：已交付文档（如评审后的系统需求），记录但不改，重大版本时统一刷新
   - `❌ 不涉及`：Grep 命中但分析后确认不需要改（记录理由，防止后续误判）

5. **执行 P0 传播**
   - 用户确认后，逐个更新 P0 文件
   - 优先用 offset/limit **只读需要改的段落**，不读全文
   - 每完成一个文件，在变更追踪中打勾 ✅

6. **记录变更追踪**
   - 在 `架构设计/变更追踪.md` 新增 CHG-XXX 记录
   - **完整记录所有影响文件**（含不改的），格式见下方模板
   - 文档类型与优先级对应（**随阶段变化**）：

     | 文档类型 | 评审前 | 评审后（编码阶段） |
     |---------|--------|-----------------|
     | 系统需求、context.md、对接确认清单 | P0 | 🔒 锁定 |
     | 概要设计（§6 含编码细节） | P1 | **P0**（编码单一事实源） |
     | 顶层设计、README、模块功能清单 | P2 | P2 |
     | 历史记录/分析文档 | 不改 | 不改 |

7. **更新 context.md**
   - 在讨论纪要中记录本次变更（一行摘要 + CHG 编号）
   - **同步刷新编码进展表**：变更涉及模块状态变化时（完成/阻塞解除/策略调整），立即更新对应行，不等 save

8. **输出执行摘要**
   ```
   ## CHG-XXX 执行完成

   **已更新**（P0）：
   - [x] 渠道管理详细设计.md — 删除状态机/缓存/接口，合并编辑

   **已登记延后**（P2）：
   - [ ] 顶层设计/模块功能清单.md
   → 后续执行：/design-session change --pending --scope=p2

   **已登记锁定**（评审后不改）：
   - 系统需求/渠道管理-系统需求.md
   → 下次系统需求版本刷新时处理
   ```

**示例**：

```
# 最简用法：直接说变更点，AI 自动分析+定级+传播
/design-session change "渠道管理简化：删除禁用/删除功能，级别和PSM合并到编辑接口，删除缓存"

# 多个变更点
/design-session change "1. 渠道无禁用删除 2. 级别是编辑字段 3. PSM是编辑字段 4. 不需要缓存"

# 后续批量刷新延后项
/design-session change --pending --scope=p2

# 里程碑全量刷新（含锁定项）
/design-session change --pending --scope=all
```

**与日常对话的关系**：
- 日常对话中用户提出设计变更时，AI 也自动执行上述流程（不需要显式调用 change）
- 区别：日常对话中 AI **默认只执行 P0**，延后项自动登记；显式 change 可以指定 `--scope=all` 强制全量
