## 1. 严重级别

| 级别 | 定义 | 示例性质 |
|---|---|---|
| P0 | 可能造成不可恢复错误、重复执行、数据错配或破坏核心不变量 | 错误写入对象、并发重复、无法恢复的部分提交 |
| P1 | 设计不能可靠实现、存在过度设计或缺少关键证据 | 重复事实源、字段无法解释、约束或生命周期缺失 |
| P2 | 不阻塞当前实现的可维护性问题 | 命名、说明、非关键索引优化 |

P2 不得掩盖 P0/P1，也不得触发自动复审循环。

## 2. 证据等级

| 类型 | 定义 | 处理 |
|---|---|---|
| `CODE-FACT` | 已核验的 DDL、迁移、ORM、DAL、Service、测试或运行约束 | 记录精确位置 |
| `REQ-FACT` | 已确认且仍有效的需求事实 | 记录来源 |
| `DECISION` | 当前设计决策 | 必须说明备选方案和取舍 |
| `ASSUMPTION` | 尚未确认的假设 | 影响正确性时阻塞 |

未找到不等于不存在。必须记录已检查范围，不得猜测代码或需求。

## 3. 模式决策

先确定封闭变更清单，再选择模式。禁止因为某个字段“属于数据库”就直接 full。

| 规则 ID | 条件 | 模式 |
|---|---|---|
| `M1-local-field=>quick` | 少量局部字段，未改变权威来源、基数、生命周期、事务拓扑或核心不变量 | quick，无 Agent |
| `M2-local-constraint=>quick` | 局部 NULL/CHECK/索引/说明变化且影响范围封闭 | quick，无 Agent |
| `M3-bounded-semantic-change=>delta` | 状态、恢复、迁移或高完整性语义变化，但表和事务拓扑不变 | delta，最多一个 Agent |
| `M4-table-topology-change=>full` | 表新增/删除/合并/拆分，或对象职责重新归属 | full，最多两个 Agent |
| `M5-transaction-topology-change=>full` | 写入方集合、跨表原子边界、统一锁序或未知结果恢复协议变化 | full，最多两个 Agent |
| `M6-explanation-or-format-only=>deterministic-only` | 仅解释、示例、术语、格式 | deterministic-only，无 Agent |

变更边界无法证明时返回 `needs_full`，不得自动执行 full。没有完整认证基线时，局部封闭范围仍可 quick；结论为 `scope_passed`，不冒充全局 `passed`。

## 4. 最小化门禁

### 4.1 逐表审核与删除挑战

对每张新增、修改、复用或删除表回答：

| 检查项 | 必须回答 |
|---|---|
| 一行含义 | 一行代表哪个不可混淆的事实 |
| 现有对象 | 已检索哪些现有表或外部权威来源 |
| 写入与读取 | 谁创建、谁更新、谁独立读取 |
| 生命周期 | 何时出现、如何变化、何时终止、保留多久 |
| 删除挑战 | 删除后哪个当前场景会具体失败 |
| 更小方案 | 复用、计算、关联、合并或不持久化为何不成立 |
| 冗余控制 | 若复制数据，如何同步、恢复和对账 |

逐表结论只能是：`保留 / 合并 / 扩展现有表 / 删除 / 证据不足阻塞`。

无法指出删除后的具体失败点时，默认不得保留。以下理由单独出现时一律不足：

- 方便查询；
- 方便排查；
- 便于扩展；
- 以后可能使用；
- 减少一次关联；
- 名称更符合当前功能。

### 4.2 独立最小模型

正式 full 审核的数据模型 Agent 必须先根据需求事实和现有模型提出一个最小候选，再与待审设计比较。不得直接从待审设计的表清单开始逐项合理化。

## 5. 逐表与逐字段审核

只有通过最小化门禁的对象才进入本节。

### 5.1 覆盖率

- 表覆盖率：已审核变化表 / 全部变化表；
- 字段覆盖率：已审核新增或修改字段 / 全部新增或修改字段。

full 要求两项 100%。quick/delta 只要求受影响范围 100%，并列出对象名称，不得只写百分比。

### 5.2 逐字段审核问题

| 检查项 | 必须回答 |
|---|---|
| 业务含义 | 用领域中立的事实语言说明，不重复字段名 |
| 来源 | 输入、计算、复制或生成 |
| 写入与读取 | 写入时机、写入方、读取方 |
| 权威性 | 权威事实、派生投影、快照或审计元数据 |
| 落库理由 | 为什么不能计算、关联或从不可变历史重建 |
| NULL/默认值 | 每种值的明确含义 |
| 约束 | 类型、范围、枚举、唯一性和状态组合 |
| 生命周期 | 是否可修改、何时归档或删除 |

重点质询：`last_*`、`current_*`、计数、合计、复制名称、外部标识、JSON、通用 `type/status/source/ext_info`、持久化计算值和重放元数据。

## 6. 关系、约束与索引

- 明确主键、不可变业务键、外键、基数和删除行为。
- 多态引用必须有可验证的完整性方案。
- ORM 校验不能替代数据库必须守住的唯一性和核心不变量。
- 先列真实查询，再设计索引；每个索引必须反向关联至少一个真实查询。
- 查询需给出过滤、连接、排序、分页、预估规模、频率和一致性要求。
- 冗余投影必须定义同步时机、失败恢复、延迟容忍和对账方式。

## 7. 事务、幂等与恢复

对每条变化写入路径记录：

- 事务控制方和原子提交集合；
- 锁对象、获取顺序和并发谓词；
- 稳定幂等键及唯一作用域；
- 重复请求、超时结果未知、部分成功和重放的恢复方式；
- 提交后副作用失败的重试边界；
- 可由持久化数据独立重算的不变量。

“在事务中执行”不能代替锁顺序、幂等和恢复设计。高完整性状态缺少独立重算公式时至少记为 P1。

## 8. 迁移与实现一致性

- 明确建表/加列、回填、约束收紧、切换、清理和回滚顺序。
- 说明旧数据、双版本读写和失败重试的处理。
- 验证目标数据库版本支持所用能力。
- DDL、ORM 类型/默认值/约束、DAL 返回基数、Service 事务和测试必须一致。
- 容量评估必须来自行数、增长、保留和查询模式，不得只写“可扩展”。

## 9. 基线继承

### 9.1 `object-baseline`

保存变化对象定义、直接读写路径和 diff，供 quick 使用。无需生成全库字段矩阵。

### 9.2 `complete-baseline`

保存设计/代码/证据摘要、表字段分母、覆盖明细、独立输出和主裁决。passed 或 failed 均可作为后续 delta 的继承来源。

### 9.3 `coverage-inheritance`

delta 报告必须列出基线对象、未变化对象、受影响对象和合并后覆盖率。只有摘要可验证且未被变更清单命中的结论可以继承。
