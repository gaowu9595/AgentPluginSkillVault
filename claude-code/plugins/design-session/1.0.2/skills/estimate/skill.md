# estimate（工作量评估与资源决策）

**参数**：`$ARGUMENTS` = `<项目目录>` [--mode=rough|precise]

**REQUIRED BACKGROUND:** Read `shared/design-session-engine.md` for path conventions.

## 定位

**资源决策工具**——不只是估工时，而是帮助在有限资源/时间下决策：
- 需要多少人力？当前够不够？差多少？
- 迭代怎么拆？哪些需求可以下车？
- 关键路径在哪？哪些可以并行？

## 两阶段模式

| 模式 | 触发条件 | 输入 | 精度 |
|------|---------|------|------|
| 粗估 | 只有需求/总设，无概设 | 功能点清单 或 总设模块清单 | ±30-50% |
| 精估 | 概设已完成 | 概设 §6.x.6 工作量 + 函数列表 | ±10-20% |

AI 自动判断：有概设 → 精估，只有需求/总设 → 粗估。用户可通过 `--mode` 显式指定。

## 执行流程

```
步骤1 收集约束 → 步骤2 探测信息 → 步骤3 工作量分解 → 步骤4 依赖分析 → 步骤5 资源匹配 → 步骤6 排期建议 → 步骤7 输出JSON → 步骤8 生成产物(md+xmind)
```

### 步骤 1：收集约束（询问用户）

询问以下信息（用户不提供的项跳过，只输出纯工作量）：

- 团队配置：前端几人、后端几人、测试几人
- 时间约束：截止日期 或 迭代周期（如 2 周/Sprint）
- 可选：需求优先级排序（哪些必须做，哪些可以下车）

如果用户不提供任何约束 → 只输出工作量汇总表，不做资源匹配和排期。

### 步骤 2：探测可用信息

自动探测当前可用的信息层级：

| Level | 条件 | 精度 | 估算方式 |
|-------|------|------|---------|
| 0 | 只有需求描述/功能点 | ±50% | 功能点复杂度 × 技术栈经验值 |
| 1 | + 设计文档（总设/概设模块清单） | ±30% | 模块数 × 接口数 × 函数列表 |
| 2 | + 知识库（`knowledge/仓库手册/`） | ±20% | 判断"改现有"vs"新写"，参考类似模块 |
| 3 | + 实际代码（`repos/`） | ±10-15% | 看具体要改哪些文件、改动量 |

探测逻辑：
- 概设文档存在（`架构设计/概要设计/` 或 `doc/design/`）→ Level 1+
- `knowledge/仓库手册/<仓库>/` 存在 → Level 2
- `repos/<仓库>/` 存在 → Level 3

告知用户："当前信息层级 Level X，预期精度 ±Y%"

每个模块可能处于不同 Level（有的有代码，有的没有），分别标注。

### 步骤 3：工作量分解

对每个模块/功能点：
- 按 **前端 / 后端 / 联调测试** 三维度拆分
- 给出**区间估计**（乐观/正常/悲观），正常值作为主估计
- 标注：复杂度（高/中/低）、风险等级（高/中/低）
- 标注：置信度（Level N ±X%）、估算依据（一句话说明怎么估的）

**估算依据示例**：
- "有概设函数列表，共 8 个函数，按 0.5d/函数估" → Level 1
- "知识库显示现有 CRUD 模板可复用，只需改字段" → Level 2
- "读代码确认改动 3 个文件约 200 行" → Level 3
- "纯基于需求描述，参考类似模块经验" → Level 0

### 步骤 4：依赖分析

- 识别模块间依赖（数据依赖、接口依赖、部署依赖）
- 计算**关键路径**（最长串行链路）
- 识别**可并行**的模块组
- 标注哪些模块在关键路径上（延期会影响整体）

### 步骤 5：资源匹配（如果用户提供了团队信息）

- 计算：总工作量（人天）vs 可用人力（人数 × 天数）
- 按角色分析：前端够不够？后端够不够？测试够不够？
- 识别瓶颈角色
- 量化缺口：差几人天，需要加几人 或 砍几个功能

如果用户未提供团队信息 → 跳过本步骤。

### 步骤 6：排期建议（如果用户提供了时间约束）

- 基于依赖关系 + 可用人力，按 Sprint 拆分任务
- 标注超期风险的 Sprint（工作量 > 可用人力）
- 如果总体超期：
  - 按优先级排序，给出"砍需求"建议
  - 每个可砍项标注：节省多少人天、影响范围
  - 给出砍后的新排期

如果用户未提供时间约束 → 跳过本步骤。

### 步骤 7：输出结构化数据

**落盘 JSON**：`.ai/工作量评估-data.json`

这是所有输出产物的唯一数据源。AI 完成步骤 1-6 的分析后，将结果写入此 JSON。后续 markdown 和 xmind 均从此 JSON 生成。

**JSON Schema**：

```json
{
  "title": "迭代X 全量工作量",
  "summary": "后端Xd + 前端Yd + 测试Zd = Nd",
  "eval_date": "YYYY-MM-DD",
  "mode": "rough|precise",
  "level": "Level 0-3",
  "team": {"be": 1, "fe": 1, "test": 1, "notes": "同事0.5人力负责XX"},
  "modules": [
    {
      "name": "模块名",
      "be_total": 10,
      "fe_total": 6,
      "test_total": 4,
      "owner": "用户|同事|其他",
      "complexity": "高|中|低",
      "risk": "高|中|低",
      "items": [
        {
          "id": "BILL-01",
          "title": "功能点名称",
          "be": 3,
          "fe": 0,
          "notes": "工作内容概述（作为工作量理由展示）"
        }
      ]
    }
  ],
  "dependencies": [
    {"from": "PM-05", "to": "BILL-05", "reason": "还款依赖repay接口"}
  ],
  "risks": [
    {"item": "风险描述", "probability": "高|中|低", "impact": "高|中|低", "mitigation": "缓解措施"}
  ],
  "schedule": {
    "coding_window": {"start": "M/D", "end": "M/D", "days": 8},
    "phases": [
      {"name": "阶段名", "start": "M/D", "end": "M/D", "days": 2, "notes": "说明"}
    ]
  }
}
```

**字段填写规则**：
- `items[].notes`：写清楚"为什么要这么多天"，这是跟 PM 博弈时的理由
- `items[].be` / `items[].fe`：只填有工作量的维度，为 0 则不填或填 0
- `modules[].owner`：标注谁负责，默认"用户"，其他人负责的单独标注
- `dependencies`：只记关键依赖（影响排期的），不记所有调用关系
- `risks`：只记需要跟 PM 沟通的风险，不记技术实现细节

### 步骤 8：生成产物

从 JSON 生成两个产物：

**8a. Markdown 评估报告**：`.ai/工作量评估-<日期>.md`

按下方模板从 JSON 数据填充生成（人读的完整分析报告，含资源匹配、排期建议等步骤 5-6 的分析结论）。

**8b. XMind 思维导图**：`.ai/工作量评估.xmind`

调用 `shared/scripts/gen_estimate_xmind.py` 生成：

```bash
python <plugin_dir>/shared/scripts/gen_estimate_xmind.py \
  "<项目>/.ai/工作量评估-data.json" \
  "<项目>/.ai/工作量评估.xmind"
```

**依赖检查**：脚本内部自动检查 `xmind` Python 包，缺失时自动安装。

**输出确认**：告知用户
```
产物已生成：
- .ai/工作量评估-data.json（结构化数据，可重复生成产物）
- .ai/工作量评估-<日期>.md（完整分析报告）
- .ai/工作量评估.xmind（XMind 思维导图，可编辑，用于跟 PM 沟通）
```

## 与 design-session 工作流的关系

- 在 `write` 或 `write-overall` 完成后自然衔接（由 `next` 建议）
- 也可独立调用（只要有需求/设计文档）
- 落盘的评估文件会被 `save` 扫描到并记录到 context.md
- `archive` 时归档到迭代目录
- JSON 数据文件支持增量更新：用户修改了 xmind 后可手动同步回 JSON，或重新执行 estimate 覆盖

## 外部依赖

> 见 `shared/external-resources.md` 工具依赖表

- `xmind` Python 包：生成 XMind 文件。脚本内自动安装，无需用户手动处理。
- Python 3.8+：运行生成脚本。
