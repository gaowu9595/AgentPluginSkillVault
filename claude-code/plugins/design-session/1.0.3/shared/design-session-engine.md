## 核心设计原则：分层恢复

> **AI 的上下文窗口是有限的。恢复上下文的目标不是"读完所有文件"，而是"用最少的读取量达到能正确工作的状态"。**

### 三层架构

```
第 1 层（恢复层）：README.md + context.md + corrections.md  ← resume 必读
    目标：知道全貌 + 知道去哪找细节 + 知道当前待办 + 知道不要重蹈覆辙

第 2 层（工作层）：具体设计文档 + 资料摘要 + 变更追踪.md ← 用户说了任务后按需读
    目标：获取完成当前任务所需的细节

第 3 层（参考层）：代码分析 + 原始资料 + history.md + .ai/iterations/  ← 编码/深度分析/回溯历史时才读
    目标：获取代码级实现细节 / 追溯历史决策过程
```

### Layer 1 体量管理

> **核心原则：不设硬行数上限，靠结构化分区 + 条数归档控制增长。**
>
> 之前的 ≤300 行硬约束导致每次 save 都要反复压缩，效率很低且治标不治本。
> 真正的问题是讨论纪要持续增长，其他区域（决策、概要、资料状态）都有天花板。

**控制策略**：

| 区域 | 控制方式 | 说明 |
|------|---------|------|
| context.md 索引区 | 自然增长，保持精简 | 决策带否决理由（一句话），不依赖纪要回忆 |
| context.md 纪要区 | **保留最近 5 条**，超出归档 | 按条数而非行数触发，可预测 |
| README.md | 自然增长 | 结构稳定后基本不变 |
| corrections.md | 超 30 天未再犯的归档 | 定期维护，不阻塞 save |

**纪要归档规则**（save 时自动执行）：
1. 统计讨论纪要条数（每个 `####` 开头的是一条）
2. **超过 5 条时**：将最早的纪要**原文移动**到 `.ai/history.md`，直到剩 5 条
3. context.md 留指针：`> 更早的纪要已归档到 history.md（截至 YYYY-MM-DD）`
4. history.md 按日期**倒序**排列

**决策条目写法**（防止纪要归档后丢失"为什么"）：
```
# 以前（依赖纪要回忆为什么）：
16. mss-auth 开发策略（2026-03-16 确认）：feature-certification 分支直接开发

# 现在（决策自带否决理由）：
16. mss-auth 开发策略（2026-03-16 确认）：feature-certification 分支直接开发
    （否决独立分支：仅 1 处配置冲突，cherry-pick 成本不值得）
```

### 关键规则

1. **resume 只读第 1 层**，不读设计文档全文
2. **等用户说了任务后，再按需加载第 2 层**（参考 README.md 的"恢复指引"和"模块依赖图"）
3. **第 3 层只在编码/深度分析时读**
4. **README.md 是路由器**，告诉 AI "不同场景该读什么"
5. **context.md 是索引**，只存结论和指针，不重复设计文档内容
6. **history.md 是归档**，不进入 resume 流程，需要回溯时按需读取特定日期段

## 设计变更响应规则（日常对话中始终生效）

> 不需要用户调用子命令。只要用户在对话中提出设计变更，AI 必须自动执行。
> **核心原则：传播时可以轻量，检查时必须严格。**
> **日常对话与 change 子命令执行相同的流程**，区别仅在于日常对话默认只执行 P0。

**触发条件**：用户提出以下任何一种变更：
- 需求细化（如"角色层级补充 1:N"）
- 决策变更（如"改为共享集群"）
- 字段/数据模型调整
- 纠正设计错误
- 接口/流程简化

#### 变更分级（自动判断）

**分级判断方法**：Grep 搜索变更相关关键词，根据命中文件数自动判断：

| 命中文件数 | 级别 | 传播策略 |
|-----------|------|---------|
| ≥4 个文件 | **L1 架构级** | 输出影响分析表 → 执行 P0 → 登记延后项 |
| 2~3 个文件 | **L2 模块级** | 输出影响分析表 → 执行 P0 → 登记延后项 |
| ≤1 个文件 | **L3 局部** | 直接改当前文件 + 简要记录变更追踪 |

**L1/L2 统一执行流程**（与 change 子命令相同）：
1. Grep 搜索影响范围
2. 输出影响分析表（文件 | 处置 | 理由）
3. 根据当前阶段自动定级（P0/P2/锁定/不涉及）
4. 执行 P0 项
5. 登记延后项和锁定项到变更追踪
6. 更新 context.md 讨论纪要

**L3 局部**（最小传播）：
1. 只改当前文件
2. 记录变更追踪（一条简短记录）
3. 更新 context.md（如果涉及决策变更）

#### 延迟传播的兜底机制

> 传播可以延迟，但**不能遗忘**。以下安全网确保最终一致性：

1. **变更追踪 checkbox** — 未勾选的 P2/锁定项一眼可见
2. **save 时检查** — 每次 save 自动检查未完成项，按优先级分级提醒
3. **`--pending` 批量刷新** — `change --pending --scope=p2` 批量处理延后项
4. **/design-session:check consistency** — 里程碑节点全量验证

## context.md 结构模板

> context.md 是**索引和速记**，不是设计文档的副本。详细内容应在设计文档中，context.md 只保留结论和指针。

```markdown
# 全局上下文

## 项目
<一句话>

## 名称澄清
## 平台关系
## 品牌-数据中心映射

## 关键决策
<编号列表。各模块详细决策用"详见 xxx 详细设计"指针>

## 业务概要
<速记 + 指针，不展开详细数据模型/流程>

## 现有代码参考
<表格：参考对象 → 分析文件路径>

## 需求资料理解状态
<资料→摘要路径→状态表格>
<设计文档未覆盖的关键补充（≤10 条）>

## 讨论纪要
<按日期倒序，每条 1-2 行>

## 当前进展
<已完成 / 待确认 / 下一步>
```

**体量管理**：不设硬行数上限。索引区（决策+概要+资料+进展）保持精简，纪要区按条数归档（保留最近 5 条）。

> README.md 告诉新 session 的 AI "不同场景该读什么文件"。与 context.md 一起构成第 1 层。
> **体量管理**：结构稳定后基本不增长，不设硬行数上限。

## 资料理解落盘规则

> **核心原则：有摘要才算理解过。**

1. 每份资料有对应摘要文件，落盘到 `.ai/<资料简称>-摘要.md`
2. context.md 引用摘要文件路径，不使用纯状态标记
3. **有摘要 = 已理解；无摘要 = 未理解**
4. save 时检查未落盘的摘要

### 摘要文件模板

```markdown
# <资料名称> 关键摘要

> 原始文件：`资料/<文件名>`
> 摘要时间：YYYY-MM-DD
> 文档性质：<一句话>

## 一、<章节 1>
## 二、<章节 2>
## 对架构设计的影响
```

## 纠错记忆机制（防重蹈覆辙）

> **核心原则：用户纠正过一次的错误，不能再犯第二次。**
> 借鉴人脑的"错误驱动学习"——犯过的错比普通知识记得更牢。

### corrections.md 结构

```markdown
# 纠错记忆

> AI 在本项目中犯过的错误和用户的纠正。resume 时必读。

## 高频/严重（每次 resume 必须回顾）
- ❌ <错误行为> → <正确做法> — <简短原因> <!-- added: YYYY-MM-DD -->

## 普通（按需回顾）
- <较轻的纠正条目> <!-- added: YYYY-MM-DD -->
```

### 写入时机

| 时机 | 动作 |
|------|------|
| **用户纠正 AI 时** | **立即**追加到 corrections.md（不等 save），附 `<!-- added: YYYY-MM-DD -->` |
| **save 时** | 检查本轮对话是否有遗漏的纠正 |
| **跨项目通用的纠正** | 同步写入 MEMORY.md |

### 条目管理

- 按严重性排序，不按时间
- 每条 1-2 行，只记结论，附日期注释
- **过期归档**：超过 30 天未再犯的条目 → 移到 `history.md` 的"纠错归档"部分，从 corrections.md 移除
- 不设硬行数上限，保持精简即可
- 过期归档在 save 时顺手检查，不作为阻塞步骤

## 对话分段提醒（防崩溃机制）

AI 在以下时机**必须主动提醒**保存：

| 时机 | 提醒 |
|------|------|
| 完成一个模块设计 | 建议 save + 开新会话 |
| 累计读取 ≥5 个大文件 | 建议 save + 开新会话 |
| 用户说结束语 | 自动执行 save |
| 一轮讨论多个决策 | 建议 save |

## 设计变更传播机制

> **核心问题**：设计过程中会不断出现需求细化、决策变更、资料补充。如果只更新当前文档而不全局同步，会导致文档间矛盾，进而传导到开发阶段。
> **核心原则**：
> 1. **用户只说变更点**，AI 自动完成分析→定级→记录→传播
> 2. **传播时可以轻量**：只改 P0，延后项登记不执行
> 3. **记录时必须完整**：所有影响文件都记录（含"不改"的理由），可追溯可回溯
> 4. **省 token 不省质量**：不做全量扫描全量传播，但保证编码事实源（详细设计）始终正确

### 统一工作流

```
用户说变更点
  │
  ├──→ 1. 提炼变更点（过滤噪音/疑问/背景信息）
  │
  ├──→ 2. Grep 搜索关键词 → 自动定级（L1/L2/L3）
  │
  ├──→ 3. 输出影响分析表（文件 | 处置 | 理由）
  │       处置根据当前阶段自动判断：
  │       ✅ P0 立即改 — 编码事实源（详细设计）
  │       ⏸️ P2 延后   — 非编码依赖（顶层设计、模块清单）
  │       🔒 锁定      — 已交付文档（评审后的系统需求）
  │       ❌ 不涉及    — 命中但确认不影响
  │
  ├──→ 4. 用户确认后执行 P0 项
  │
  ├──→ 5. 记录变更追踪（含完整影响分析表）
  │
  └──→ 6. 更新 context.md + 输出执行摘要
```

### 关键规则

1. **编码阶段只改详细设计（P0）**——编码依赖的是详细设计，顶层设计/系统需求延后到里程碑刷新
2. **所有影响文件都记录**——包括"不涉及"的文件及理由，防止后续误判或遗漏
3. **延后项可批量刷新**——`change --pending --scope=p2` 一键处理所有延后项
4. **锁定项版本刷新**——`change --pending --scope=all` 在里程碑节点刷新已交付文档
5. **变更追踪.md 不替代 context.md 的讨论纪要**——讨论纪要记"发生了什么"，变更追踪记"哪些文件要改"
6. **读文件时按需读取**——用 offset/limit 只读需要改的段落，不强制读全文

### `架构设计/变更追踪.md` 模板

```markdown
# <项目名> 设计变更追踪

> **维护规则**：每次设计变更时新增一条记录，更新完一个文件就勾一个 checkbox
> **延后项回溯**：`/design-session change --pending --scope=p2` 批量处理延后项

## 变更日志

### CHG-XXX：<变更标题>（YYYY-MM-DD）

**变更点**：
1. <变更点 1>
2. <变更点 2>

**影响分析**（当前阶段：<阶段名>）：

| 文件 | 处置 | 理由 |
|------|------|------|
| `详细设计/xxx.md` | ✅ P0 立即改 | <理由> |
| `系统需求/xxx.md` | 🔒 锁定 | 评审后不改 |
| `顶层设计/xxx.md` | ⏸️ P2 延后 | 非编码依赖 |
| `详细设计/yyy.md` | ❌ 不涉及 | <理由> |

**执行清单**：

- [x] P0 `详细设计/xxx.md` — <具体改动说明>
- [ ] P2 `顶层设计/xxx.md` — <具体改动说明>（延后）
- 🔒 `系统需求/xxx.md` — 锁定，下次版本刷新时处理
```
