## analyze（需求理解）

**目标**：系统化地分析原始资料，逐个读取、落盘摘要，输出需求理解报告。

**步骤**：

1. **确认资料目录**
   - 默认 `<项目>/资料/`，不存在则询问
   - `<项目>/资料/` 只应放**当前活跃迭代**的新输入；历史资料应冻结到 `.ai/iterations/<iter-id>/01-raw-input/`
   - `ls` 列出全部文件

2. **检查已有摘要**
   - `ls <项目>/.ai/*-摘要.md`
   - 对比资料文件与摘要，识别新增/未分析的
   - 告知："共 N 份资料，M 份已有摘要，K 份待分析"

2.5. **检测 Figma 资料**
   - 检查 `<项目>/资料/figma-links.md` 是否存在
   - IF 存在 → 解析 fileKey 和页面清单表格（格式参考 `references/figma-links-template.md`）
   - 检查已有 Figma 摘要（`.ai/*交互稿-摘要.md`）的 lastModified 元数据
   - 告知："检测到 Figma 交互稿（fileKey=xxx），共 N 个模块待解析"
   - Figma 资料走步骤 3F（Figma 专用流程），其他资料继续走步骤 3

3. **逐个读取并落盘摘要**
   - 每读完一份**立即**落盘到 `.ai/<资料简称>-摘要.md`
   - 遵循"资料理解落盘规则"的模板
   - 解析失败要明确告知，不跳过
   - **Figma 资料走步骤 3F**（见下方），其他资料继续本步骤
   - **含截图/标注的 PDF 走步骤 3P**（见下方）

3P. **PDF 多模态分析流程**（含截图、箭头标注、手写注释的 PDF）

   > **根因**：纯文本提取会丢失截图中的字段映射关系、箭头标注、红色注释等关键信息。
   > 这些信息往往是产品/架构师手动标注的字段对应关系和决策说明，遗漏会导致后续设计缺失。

   **触发条件**：PDF 中包含截图、界面截图+箭头标注、红色/彩色注释文字、手绘流程图等非纯文本内容。

   **步骤**：

   1. **页面渲染**：将 PDF 每页渲染为图片（pymupdf 2x 或 pdftoppm），存储到 `.ai/tmp_pdf_rendered/page_N.png`
   2. **文本层提取**：用 pypdf/pymupdf 提取纯文本（作为基础骨架）
   3. **逐页多模态分析**：对每页渲染图片用 Read 工具做多模态分析，重点关注：

   | 检查项 | 说明 | 常见遗漏 |
   |--------|------|---------|
   | **箭头/连线标注** | 截图之间的箭头表示字段映射关系（A 字段 → B 字段） | 箭头指向的目标字段 |
   | **红色/彩色注释文字** | 产品/架构师的手写说明，通常是关键决策或映射规则 | 字体小、密集的注释行 |
   | **截图中的表单字段** | 界面截图中的输入框、下拉菜单、必填标记（*） | 截图分辨率低时的字段名 |
   | **编号标记** | 如 ①②③ 或 ⑩⑪⑫ 标注在截图上的序号，对应说明文字 | 编号与说明文字的对应关系 |
   | **对比布局** | 左右对照截图（如 "系统A → 系统B" 的字段映射） | 右侧截图的详细字段 |

   4. **标注文字逐行枚举**：对每页中的所有标注文字（红色/手写/注释/气泡），逐行提取并记录。**不跳过任何一行**，即使看起来不重要。格式：

   ```
   ## Page N 标注文字清单

   | 序号 | 位置 | 颜色 | 内容 | 影响 |
   |------|------|------|------|------|
   | 1 | 右侧截图旁 | 红色 | "直接用当PSM主推销售的信息" | 项目销售字段来源 |
   | 2 | 箭头旁 | 红色 | "名称：{customer name} - {approval ID}" | 项目名称生成规则 |
   ```

   5. **交叉验证**：将多模态分析结果与文本层提取结果交叉比对，标注"仅图片层可见"的信息（文本提取无法获取的）

   **落盘要求**：摘要中必须包含以下章节：
   - "标注文字完整清单"（逐行，不省略）
   - "字段映射关系"（从箭头标注提取）
   - "精度说明"（每页的识别置信度）

   **质量自检**：落盘前检查 — 每页截图中的标注文字数量是否合理？如果某页截图明显有很多标注但只提取了 1-2 条，说明遗漏了，需要重新分析。

3F. **Figma 解析流程**（仅当检测到 figma-links.md 时执行）

   > 四阶段解析 + 增量更新。目标：输出结构化交互稿摘要，供系统需求→设计→编码使用。
   > **健壮性原则**：MCP 工具可能断连或部分不可用，所有步骤必须有 REST API fallback，确保一次性完成。

   **前置：获取 Figma Token**（所有步骤共用）
   - 优先级：`$FIGMA_API_KEY` 环境变量 → MCP 配置中的 token（通过 `claude mcp get figma` 读取）
   - 获取方式：
     ```bash
     # 尝试环境变量
     TOKEN=$FIGMA_API_KEY
     # 如果为空，从 MCP 配置提取
     if [ -z "$TOKEN" ]; then
       TOKEN=$(claude mcp get figma 2>/dev/null | grep FIGMA_API_KEY | awk -F= '{print $2}')
     fi
     ```
   - Token 获取失败 → 告知用户设置 `FIGMA_API_KEY` 环境变量，中止 Figma 解析

   **增量检测**（每次执行先检查）：
   - 读取已有摘要文件头部的 `lastModified` 元数据
   - 通过 REST API 获取文件修改时间（**不依赖 MCP**）：
     ```bash
     curl -sH "X-Figma-Token: $TOKEN" "https://api.figma.com/v1/files/{fileKey}?depth=1"
     ```
   - IF 未变化 → 告知"交互稿无更新（上次解析: YYYY-MM-DD）"，跳过
   - IF 有变化 → 获取版本历史（`/v1/files/{fileKey}/versions`），列出变更描述，继续下方流程
   - IF 无已有摘要 → 全量解析

   **阶段 1: 结构拉取（文本层）**

   工具选择（按优先级尝试）：
   1. **MCP 可用时**：调用 `mcp__figma__get_figma_data(fileKey, nodeId, depth=3)`
   2. **MCP 不可用时（fallback）**：通过 REST API + Python 脚本提取
      ```python
      import urllib.request, json, sys
      sys.stdout.reconfigure(encoding='utf-8')  # 解决 Windows 中文编码问题

      req = urllib.request.Request(
          f'https://api.figma.com/v1/files/{file_key}/nodes?ids={node_id}&depth=5',
          headers={'X-Figma-Token': token}
      )
      with urllib.request.urlopen(req, timeout=60) as resp:
          data = json.loads(resp.read().decode('utf-8'))

      # 递归提取所有 TEXT 节点的 characters 字段
      def extract_texts(node):
          results = []
          if node.get('type') == 'TEXT' and node.get('characters'):
              results.append(node['characters'].strip())
          for child in node.get('children', []):
              results.extend(extract_texts(child))
          return results
      ```

   **中文编码处理规则**（Windows 环境必须遵守）：
   - ❌ 不要用 Bash `print` 直接输出中文（控制台 cp936 会乱码）
   - ✅ Python 脚本开头加 `sys.stdout.reconfigure(encoding='utf-8')`
   - ✅ 或者写入文件后用 Read 工具读取（最可靠）
   - ✅ 大量文本提取结果必须写入 `.ai/tmp_*.txt` 临时文件，再用 Read 读取

   产出：每个模块的页面骨架（Frame 层级 + 所有文本内容）

   **阶段 1.5: 评论拉取**
   - 通过 REST API 获取评论（**不依赖 MCP**）：
     ```bash
     curl -sH "X-Figma-Token: $TOKEN" "https://api.figma.com/v1/files/{fileKey}/comments"
     ```
   - 按节点 ID 关联到对应页面/模块
   - 分类：设计意图→业务规则 / 未resolved→待确认 / 已resolved→决策记录 / 修改建议→潜在变更

   **阶段 2: 视觉拉取（图片层）**

   > **核心原则：全量预下载 + 质量门禁**
   > 首次成功连接时，一次性导出该模块**所有 Section** 的图片到本地缓存。后续分析全部使用本地图片，不再依赖实时 API。
   > 如果缓存图片经多模态评估精度不足（模糊/不可辨认），不强行使用，必须重试连接获取更高质量版本。

   **步骤 2a：全量预下载**

   目标：将 figma-links.md 中列出的**每个模块的每个 Section** 都导出为图片，不遗漏。

   工具选择（按优先级尝试）：
   1. **MCP `download_figma_images` 可用时**：直接调用
   2. **MCP 不可用时（fallback）**：通过 REST API 导出 + curl 下载
      ```python
      # Step 1: 获取图片 URL
      req = urllib.request.Request(
          f'https://api.figma.com/v1/images/{file_key}?ids={node_ids}&scale=2&format=png',
          headers={'X-Figma-Token': token}
      )
      # Step 2: 下载到本地
      # curl -sL "{image_url}" -o "{local_path}/{filename}.png"
      ```

   **全量预下载策略**：
   - 从 figma-links.md 解析出每个模块的所有 Section nodeId
   - 对每个 Section 逐一导出整页图（scale=2）
   - 导出成功 → 记录到 `<项目>/.ai/figma-cache-manifest.md`（nodeId → 本地路径 → 导出时间 → 尺寸）
   - 导出失败 → 记录失败 Section，**不跳过**，先重试 1 次（间隔 5s），仍失败则标记为"待补全"

   **自适应策略**（单张图片）：
   - 先尝试整页导出（scale=2）
   - 文件 > 2MB → 获取页面子 Frame 列表，按 Section 拆分导出
   - 仍 > 2MB → 降 scale=1 或按更细粒度拆分
   - 导出失败 → 记录失败节点，继续其他节点

   **步骤 2b：质量门禁**

   对每张已下载的图片做快速质量评估：
   1. 检查文件大小（< 10KB 可能是空白/错误图片）→ 标记"疑似无效"
   2. 用 PIL 检查尺寸（宽或高 < 100px）→ 标记"疑似无效"
   3. 对"疑似无效"图片：重试下载 1 次，仍无效 → 标记为"待补全"，**不使用该图片进行分析**

   **步骤 2c：连接失败处理**

   IF 全量预下载阶段 API 完全不可用（所有请求超时/拒绝）：
   1. 检查本地是否有**历史缓存**（上一轮 v(N-1) 的图片）
   2. IF 有历史缓存 → 使用历史缓存继续分析，但在摘要头部标注 `> ⚠️ 本轮使用历史缓存图片（v<N-1>），未获取最新版本`
   3. IF 无历史缓存 → **中止图片相关分析**，仅依赖文本层，明确告知用户：
      ```
      ⚠️ Figma API 不可用，以下 Section 无图片缓存，视觉层分析跳过：
      - Section 5（客户列表页/详情页）— 影响：字段布局、状态变体无法视觉验证
      - ...
      建议：API 恢复后执行 `analyze --complete` 补全缺失图片。
      ```
   4. **绝不使用精度不足的图片强行分析**——宁可标注"视觉层未验证"，也不输出错误结论

   **图片存储路径与证据集规范**：

   存储基准目录：`<项目>/原始输入/交互/图片/<模块名>-v<N>/`
   - `<N>` 为解析轮次（首次 v1，增量更新 v2、v3…），保留历史版本目录不删除
   - 摘要头部元数据中标注当前证据集版本，如 `> 证据图片：原始输入/交互/图片/02账单管理-v2/`

   命名规则：
   | 文件类型 | 命名模式 | 示例 |
   |---------|---------|------|
   | 整页图 | `<模块简称>-page.png` | `billing-page.png` |
   | 局部切片 | `<NN>-<描述性名称>.png`（NN 从 00 起按页面从左到右/从上到下编号） | `00-requirements-analysis.png`、`03-push-modal-and-bcc.png` |

   **路径归一化规则**（防重复拼接）：
   - MCP `download_figma_images` 的 `localPath` 参数已经是相对于项目根的路径，**不要再 prepend 项目根目录**
   - REST API fallback 下载时，用**绝对路径**写入，但摘要中引用时用**相对于项目根的路径**
   - 落盘前检查：目标路径不应包含重复的 `<项目>/原始输入/交互/图片/<项目>/原始输入/交互/图片/` 片段

   **阶段 2.5: 多模态质量评估与局部切片**

   > **核心发现**：宽幅 Figma 页面（如 12000+×2600px）的整页图在多模态分析时会丢失细节（术语错误、区域遗漏、样式误判）。局部切片可显著提升分析精度。

   **触发条件**（满足任一即触发切片）：
   - 图片宽度 > 8000px **或** 高宽比 < 1:3（极端横幅）
   - 整页多模态初扫发现 ≥2 处"无法辨认"/"模糊"/"不确定"区域
   - 页面包含 ≥3 个功能区域（列表+弹窗+抽屉+说明区等混合布局）

   **切片策略**：
   1. 用 PIL 对已下载的整页图进行水平分段裁切
   2. 每片宽度 2000-2500px，相邻切片**重叠 200px**（防边界信息丢失）
   3. 裁切前先用整页图做一次快速多模态扫描，识别各功能区域的大致像素范围
   4. 按功能区域边界（而非等宽）调整裁切位置，尽量让每片包含完整的功能区域
   5. 切片保存到证据集目录，命名 `<NN>-<描述性名称>.png`

   **PIL 裁切参考代码**：
   ```python
   from PIL import Image
   import os

   img = Image.open(full_page_path)
   w, h = img.size
   slices = [
       (0, 0, 1200, h, "00-requirements-analysis"),
       (1150, 0, 3700, h, "01-vendor-list-and-partner-list"),
       # ... 按功能区域定义，注意 ~200px 重叠
   ]
   for x1, y1, x2, y2, name in slices:
       crop = img.crop((x1, y1, min(x2, w), min(y2, h)))
       crop.save(os.path.join(output_dir, f"{name}.png"))
   ```

   **切片后处理**：
   - 对每张切片用 Read 工具做多模态分析（Claude 原生多模态，优先于 MCP 工具）
   - 将各切片分析结果与整页初扫结果**对比合并**：切片发现优先（精度更高）
   - 记录"切片新发现 vs 整页遗漏"的差异，作为摘要富化依据

   **不触发切片的情况**：
   - 页面仅包含单一功能区域（如只有一个表单）
   - 图片尺寸 < 8000px 且功能区域 ≤ 2 个
   - 整页多模态初扫结果已足够清晰（无模糊/不确定标记）

   **阶段 3: 融合分析**
   - 对每个模块/页面：文本层骨架 + 图片多模态分析 + 评论
   - 文本层提供：组件树结构、字段名、按钮文案、布局方向
   - 视觉层补充：实际布局关系、状态变化、视觉层级、遗漏细节
   - 评论层补充：设计意图、业务规则、待确认项
   - 冲突处理：视觉层 > 文本层（文本层可能失真）
   - 自适应升级：如某区域细节不清 → 单独导出该区域高分辨率切片重新分析（参考阶段 2.5 切片策略）
   - **具体示例数据**：必须记录 ID 格式（如 `AUTH-YYYY-NNN`）、数值示例（如 `255/300`）、枚举值完整列表
   - **实体推断**：从字段表格反推数据实体和关系，输出到 §十
   - **架构影响**：识别数据源依赖（如"来源于MSSW"）、跨模块联动、安全约束，输出到 §十一
   - **多模态分析工具选择**：
     1. Read 工具直接读取图片（Claude 原生多模态，推荐）
     2. `mcp__zai-mcp-server__analyze_image`（如可用）
     3. 两者都不可用 → 仅依赖文本层，标注"视觉层未验证"

   **阶段 3.5: 交互规则显式提取**（防遗漏）

   > **核心原则**：交互稿中的规则分为"显式规则"（文本注释写明）和"隐含规则"（只在视觉层体现）。两者都必须提取到摘要中，否则后续系统需求会遗漏。

   对每个弹窗/表单/列表页，逐一检查并记录：

   | 检查维度 | 检查方法 | 输出格式 |
   |---------|---------|---------|
   | 默认值/自动行为 | 文本层搜索"默认""自动""填充"；视觉层检查预填内容 | `默认行为：[描述]` |
   | 不可操作规则 | 视觉层检查：哪些元素没有删除/编辑按钮？哪些是灰色/禁用态？ | `不可操作：[元素] — [原因]` |
   | 条件可见性 | 文本层搜索"隐藏""展示""仅"；视觉层对比不同状态的页面 | `条件可见：[元素] — [条件]` |
   | 角色差异 | 文本层搜索"仅厂商""仅渠道""PSM""渠道"；对比不同角色页面 | `角色差异：[内容] — [角色]` |
   | 操作-状态关联 | 文本层搜索"状态""操作"；检查按钮在不同状态下的可见性 | `操作规则：[操作] — [可见条件]` |
   | 双品牌差异 | 文本层搜索"Forenova""Sangfor""欧洲""东南亚" | `品牌差异：[内容] — [品牌]` |
   | 快捷操作 | 视觉层检查：文字按钮、一键填入、批量操作 | `快捷操作：[描述]` |
   | 枚举值/选项 | 文本层搜索下拉选项、状态标签、类型标签；视觉层检查 Tag/Badge | `枚举：[字段] = [值1/值2/...]` |
   | ID格式/编号规则 | 文本层搜索示例 ID（如 AUTH-xxx、AP-xxx）；视觉层检查列表数据 | `ID格式：[实体] = [模式]` |

   **隐含规则的处理**：
