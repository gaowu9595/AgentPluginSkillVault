# 总体设计编写指南

> **用途**：AI / 设计人员编写总体设计时的方法论参考 + 执行流程指南
> **适用模板**：SFRD-TS-01-4.3（V4.3），即 `总体设计模板.md`
> **核心原则**：站在架构师评审视角写设计 — 回答"为什么这样设计"比"设计了什么"更重要
> **目标读者**：AI 助手、系统架构师、开发经理

---

## Part 1: 方法论参考（业界最佳实践精华）

> 本部分是"武器库"，不是强制流程。写总设时按需取用，最终产出必须符合模板结构。

### 1.1 4+1 视图模型

**核心理念**：用五个视图从不同角度描述同一个系统，每个视图回答一个核心问题。

| 视图 | 核心问题 | 对应模板章节 | 典型产出 |
|------|---------|-------------|---------|
| 逻辑视图 | 系统功能如何分解？ | §4.1.1 | 模块划分、职责关系、分层结构 |
| 过程视图 | 运行时如何协作？ | §4.1.2 | 进程/线程模型、同步/异步关系、关键调用链 |
| 开发视图 | 代码如何组织？ | §4.1.3 | 仓库划分、模块依赖、公共库 |
| 物理视图 | 如何部署运行？ | §4.1.4 | 部署拓扑、节点分布、扩缩容方式 |
| 场景视图 | 如何验证以上四个视图？ | §4.1.5 | 典型业务场景端到端串联 |

**使用要点**：

- 不是每个视图都要画完整 UML，关键是回答该视图的核心问题
- 场景视图是"胶水"——用 1-2 个典型场景串起其他四个视图，验证架构自洽
- 如果某个视图对当前版本不重要（如纯软件项目的物理视图），写清楚"不涉及"及原因

**常见误区**：

- ❌ 把所有内容塞进逻辑视图，其他视图空白
- ❌ 画了架构图但不解释"为什么这样分"
- ❌ 过程视图只画正常流程，不考虑异常和并发

### 1.2 C4 Model — 分层架构表达

**核心理念**：用四个抽象层级（Context → Container → Component → Code）逐步放大系统细节。

| 层级 | 关注点 | 总设中的应用 | 概设中的应用 |
|------|--------|-------------|-------------|
| Context | 系统与外部世界的关系 | §4.1.5 场景视图 + §4.5 模块边界 | — |
| Container | 可独立部署的运行单元 | §4.1.1 逻辑视图 + §4.1.4 物理视图 | — |
| Component | 运行单元内部的模块 | §4.5 模块设计（概要） | §4.3 静态结构 |
| Code | 具体类/函数 | — | §6 流程设计 |

**总设与概设的边界**：

- **总设止于 Container + Component 概要层**：说清楚有哪些服务/进程、它们之间怎么通信、每个服务内部有哪些核心模块
- **概设展开 Component 详细层**：每个模块内部的接口、数据结构、函数列表

**使用要点**：

- Context 图回答"系统边界在哪"——评审最常追问的问题之一
- Container 图回答"有几个可独立部署的东西"——直接影响部署和运维设计
- 总设中不需要画到 Code 层，那是概设的事

### 1.3 arc42 — 约束驱动设计

**核心理念**：架构决策应该从约束和质量属性出发，而不是先画架构再补约束。

**质量属性场景化**（与模板 §5 DFX 的映射）：

arc42 要求每个质量属性写成可验证的场景，格式为：

```
刺激源 → 刺激 → 制品 → 环境 → 响应 → 度量
```

**映射到模板 §5 的写法**：

| arc42 要素 | 模板 §5 对应写法 | 示例 |
|-----------|-----------------|------|
| 刺激源 | 触发条件 | "100 个租户同时发起告警查询" |
| 制品 | 涉及模块/接口 | "告警查询接口 /api/alerts" |
| 环境 | 运行条件 | "正常负载下" |
| 响应 | 设计机制 | "查询走 ES 索引，结果分页返回" |
| 度量 | 目标值 + 验证方式 | "P99 < 3s，通过压测验证" |

**使用要点**：

- DFX 章节不是填表，是描述"在什么条件下，系统如何响应，达到什么指标"
- 约束清单（性能约束、部署约束、兼容性约束）应该在写架构之前整理好，驱动架构决策
- 如果发现约束之间有冲突（如"高性能"vs"低成本"），必须在方案选型中说明取舍

### 1.4 ADR — 架构决策记录

**核心理念**：每个重要的架构决策都应该记录 Context（为什么要决策）、Decision（决定了什么）、Consequences（带来什么后果）。

**ADR 结构与模板 §1.x.6 方案选型的融合**：

| ADR 要素 | 模板对应位置 | 写什么 |
|---------|-------------|--------|
| Title | §1.x.6 标题 | "[方案主题] 的方案选型" |
| Context | §1.x.6.1 业务场景关键问题 | 为什么需要做这个决策？业务特征是什么？ |
| Options | §1.x.6.3-5 方案1/2/3 | 每个备选方案的描述、优势、风险 |
| Decision | §1.x.6.6 方案选型决策 | 评估准则 + 打分 + 最终选择 |
| Consequences | §1.x.6.7 方案对业务的约束 | 选了这个方案，对业务有什么限制？ |

**决策矩阵构建方法**：

1. **准则从业务特征导出**：不是拍脑袋列"性能/成本/可维护性"，而是从 §1.x.6.1 的技术特征推导
2. **权重有依据**：权重来自业务优先级，不是平均分配
3. **评估方法明确**：每个准则说明是"实测数据"还是"专家判断"还是"对标分析"
4. **给分有说明**：不能只有分数没有理由

**常见误区**：

- ❌ 只有最终方案，没有备选比较（评审必问"为什么不选 X？"）
- ❌ 评估准则是万能词（"性能好""成本低""易维护"）
- ❌ 所有准则权重相同（说明没有认真分析业务优先级）
- ❌ 方案对业务的约束没写（评审必问"这个选择会限制什么？"）

## Part 2: 各章节写作要点（对齐模板章节号）

> 每章按统一格式展开：本章目标 → 评审追问点 → 写作要点 → 常见反模式 → 方法论映射。
> 所有章节号严格对齐 `总体设计模板.md`，不引入模板没有的章节。

### 2.0 总体原则

1. **评审追问的本质**：为什么 > 是什么 > 怎么做。架构师不关心你画了什么图，关心你为什么这样画。
2. **量化优于定性**：目标写数值不写形容词，验证写方法不写"测试验证"。
3. **不偏离模板**：模板有的章节必须覆盖（不涉及写原因），模板没有的不自创。
4. **场景优于泛泛**：每个设计决策都要能追溯到具体业务场景。
5. **约束先于方案**：先整理约束清单，再做架构决策。约束变了，方案才需要变。

---

### 2.1 §0 引言

| 维度 | 内容 |
|------|------|
| **本章目标** | 2-4 句话说清问题域、读者对象、文档定位 |
| **评审追问点** | "这个总设覆盖什么范围？""谁来评审？" |
| **写作要点** | §0.1 目的简洁明了；§0.2 适用范围对照表判断是否需要总设；§0.4 参考文档列全 |
| **常见反模式** | ❌ 复制粘贴需求文档摘要当目的；❌ 参考文档只列名称不列章节 |
| **方法论映射** | — |

---

### 2.2 §1 技术需求设计（重点章节）

| 维度 | 内容 |
|------|------|
| **本章目标** | 回答"需求为什么导出当前设计"，不是复述需求 |
| **评审追问点** | "为什么不选方案B？""评估准则从哪来？""方案边界是什么？""长期演进考虑了吗？" |
| **方法论映射** | ADR（§1.4） |

**§1.1 vs §1.2 选择策略**：

| 本版本重点 | 主写章节 | 说明 |
|-----------|---------|------|
| 架构变化、平台底座、跨模块重构 | §1.1 架构技术需求 | 从架构现状→挑战→方案思路展开 |
| 业务能力、特性实现 | §1.2 特性技术需求 | 从用户场景→问题→方案思路展开 |
| 两者兼有 | 两章都写 | 明确边界，避免重复 |

**方案选型写作要点**（§1.x.6）：

1. **必须有备选**：至少 2 个方案比较，不能只有"最终方案"
2. **准则从业务导出**：§1.x.6.1 的技术特征 → §1.x.6.6 的评估准则，有因果关系
3. **约束必须写**：§1.x.6.7 方案对业务的约束，评审必问
4. **预研有结论**：§1.x.5 预研结论要有证据（数据/文档），不能只写"已完成"

**常见反模式**：

- ❌ 只有最终方案没有比较（"我们选择 Kafka"——为什么不选 RabbitMQ？）
- ❌ 准则是万能词（"性能好""成本低""易维护"——对任何方案都适用）
- ❌ 所有准则权重相同（说明没分析业务优先级）
- ❌ 需求分析只列需求不分析（复制需求文档 ≠ 需求分析）
- ❌ 长期演进只写"预留扩展点"（具体预留什么？不预留的风险是什么？）

### 2.3 §2 设计目标

| 维度 | 内容 |
|------|------|
| **本章目标** | 量化目标 + 设定依据 + 验证方式 + 承接章节，四要素缺一不可 |
| **评审追问点** | "目标值怎么来的？""怎么验证？""哪个章节承接这个目标？" |
| **方法论映射** | arc42 质量场景（§1.3） |

**写作要点**：

- 每个目标项必须有：目标值（数值）、设定依据（需求/基线/竞品）、验证方式（压测/实测/评审）、承接章节
- 目标值来源优先级：需求文档明确要求 > 历史基线数据 > 竞品对标 > 专家经验
- 验证方式要具体：不是"测试验证"，而是"通过 XX 工具在 YY 环境下压测，持续 ZZ 分钟"

**常见反模式**：

- ❌ 目标只有名词没有值（"高性能""高可靠"）
- ❌ 验证方式写"测试验证"（什么测试？怎么验证？）
- ❌ 目标与后续章节脱节（§2 写了"P99<3s"，§5.2 可靠性章节完全没提）
- ❌ 所有目标都是"高/中/低"定性描述

### 2.4 §3 硬件方案

| 维度 | 内容 |
|------|------|
| **本章目标** | 明确硬件平台要求和特殊依赖 |
| **评审追问点** | "有没有特殊硬件依赖？""对部署环境有什么要求？" |
| **方法论映射** | — |

**写作要点**：

- 纯软件项目：写"不涉及，本版本为纯软件方案，无特殊硬件依赖"
- 有硬件依赖：列清楚平台要求（CPU/内存/磁盘）、专用芯片、驱动版本
- SaaS 项目：写清楚云平台要求和资源规格

### 2.5 §4 软件方案（重点章节）

| 维度 | 内容 |
|------|------|
| **本章目标** | 输出架构视图、主流程、数据结构、模块边界 |
| **评审追问点** | "模块边界在哪？""数据归谁？""流程异常怎么办？""为什么这样分模块？" |
| **方法论映射** | 4+1 视图（§1.1）+ C4 Model（§1.2） |

**§4.1 软件总体架构**：

- 用 4+1 视图组织，每个视图回答一个核心问题（见 Part 1 §1.1）
- 逻辑视图：模块划分的依据是什么？（按业务域/按技术层/按部署单元）
- 过程视图：关键路径上有哪些同步/异步调用？性能瓶颈在哪？
- 开发视图：代码仓库怎么划分？公共库依赖关系？
- 物理视图：部署几个节点？怎么扩缩容？
- 场景视图：用 1-2 个典型场景串起来验证

**§4.2 系统主流程**：

- 必须导出模块接口（§4.2.x.3），不能只画流程不落接口
- 每条主流程对应需求编号，可追溯
- 异常场景必须标注（不能只有 happy path）

**§4.4 数据结构**：

- 关键数据的生命周期（创建→使用→归档→删除）
- 一致性要求（强一致/最终一致/无要求）
- 数据归属（哪个服务是 owner）

**§4.5 模块设计**：

- 重点是职责边界，不是内部细节（内部细节是概设的事）
- 必须写"模块不负责什么"——边界比职责更重要
- 风险识别要具体（触发条件+影响+对策）

**常见反模式**：

- ❌ 架构图只有框没有箭头（不知道谁调用谁）
- ❌ 模块设计写成代码设计（函数列表不该出现在总设）
- ❌ 主流程只有正常路径（评审必问"如果 XX 失败怎么办？"）
- ❌ 数据结构只列字段不说生命周期和一致性要求

### 2.6 §5 关键特性设计（重点章节）

| 维度 | 内容 |
|------|------|
| **本章目标** | 每个 DFX 特性都要有：目标 → 场景/风险 → 设计机制 → 验证方式 → 残余风险 |
| **评审追问点** | "目标值怎么来的？""故障场景覆盖全了吗？""措施能验证吗？""残余风险可接受吗？" |
| **方法论映射** | arc42 质量场景（§1.3）+ STRIDE + FMEA |

**§5.1 安全性设计 — 威胁建模四要素**：

每条安全设计必须包含：

| 要素 | 说明 | 示例 |
|------|------|------|
| 资产/接口 | 被保护的对象 | "告警查询接口 /api/alerts" |
| 威胁场景 | STRIDE 视角下的具体威胁 | "未授权用户通过伪造 JWT 访问其他租户告警" |
| 安全措施 | 具体的防护机制 | "JWT 签名验证 + 租户 ID 从 token 提取（不信任请求参数）" |
| 残余风险 | 措施实施后仍存在的风险 | "token 泄露场景依赖 token 过期机制（30min TTL）" |

**§5.2 可靠性设计 — 三层结构**：

```
第一层：目标定义（§5.2.1）
  → 故障检测率、自动恢复率、业务中断时间等量化指标

第二层：故障场景分析（§5.2.2）
  → 具体故障类型、触发条件、当前能力、目标能力、差距

第三层：实现方案（§5.2.4）
  → 冗余设计、故障管理、升级不中断、应急恢复
```

**§5.3-§5.9 其他 DFX — 四要素**：

每项必须有：

| 要素 | 说明 |
|------|------|
| 目标 | 量化指标（如"故障定位时间 < 15min"） |
| 场景 | 具体的使用/故障场景 |
| 机制 | 设计措施（具体到模块/工具） |
| 验证 | 怎么证明机制有效 |

**常见反模式**：

- ❌ 安全性只写"通过认证鉴权保护"（什么认证？保护什么？）
- ❌ 可靠性只写"主备切换"（什么故障触发切换？切换时间多长？数据丢不丢？）
- ❌ 可测试性写"支持自动化测试"（什么级别的自动化？覆盖率目标？）
- ❌ 可运维性写"支持监控告警"（监控什么指标？告警阈值？谁收到？）
- ❌ DFX 章节互相复制粘贴，换个标题就交差

### 2.7 §6-§8 总结 / 变更 / 修订

| 维度 | 内容 |
|------|------|
| **本章目标** | 收口风险、遗留问题、变更影响 |
| **评审追问点** | "最大风险是什么？""遗留问题什么时候解决？""设计变化影响了谁？" |
| **方法论映射** | — |

**§6.1 设计变化**：

- 必须说明变化原因（不是"优化"，而是"因为 XX 约束导致原方案不可行"）
- 必须说明影响范围（影响哪些模块、哪些接口、哪些团队）
- 没有变化时写"无重大设计变化"，不留空

**§6.2 风险问题**：

- 每个风险必须有规避措施（不能只列风险不给对策）
- 措施要具体可执行（不是"加强测试"，而是"增加 XX 场景的集成测试用例"）

**§6.3 遗留问题**：

- 必须有计划解决时间和责任人
- 如果影响当前版本交付，必须标注优先级

**§7 变更控制**：

- 每次变更记录：变更章节 + 内容 + 原因 + 对老功能的影响
- 评审后的修改必须在这里体现

## Part 3: AI 执行流程

> 本部分是 AI 编写总体设计的分步执行指南。配合 `/design-session:write-overall` 使用。
> 核心原则：先思考再动笔 — 把不确定性暴露在写之前，不是写完再改。

### 3.1 输入就绪检查（写之前必须完成）

> 动笔前检查，缺一不可。缺少的标注为"阻塞项"，等补齐或标注待确认后再写。

| 检查项 | 来源 | 缺失影响 |
|--------|------|---------|
| 用户需求设计 / 技术规划文档 | 项目输入文档 | 阻塞：§1 需求分析无法展开 |
| DFX 基线和版本 DFX 需求 | 质量管理 / 安全团队 | 阻塞：§2 目标无法量化，§5 无基准 |
| 安全需求输入 | 安全经理 | 阻塞：§5.1 安全性设计无法展开 |
| 前期预研结论（如有） | 预研文档 / 测试数据 | 影响：§1.x.5 预研结论无证据 |
| context.md 上下文 | `.ai/context.md` | 影响：决策一致性 |
| Figma 交互稿（如有） | `资料/figma-links.md` | 影响：§4 软件方案的流程设计缺少交互依据 |

**检查方式**：

1. 读 `.ai/context.md` — 确认当前阶段（应为"阶段2 总体设计"）、关键决策、待确认项
2. `ls <项目>/架构设计/` 或 `ls <项目>/doc/` — 确认需求/规划文档存在
3. 确认 DFX 基线文档或安全需求文档可获取
4. 如有预研，确认预研结论文档存在
5. 如有 Figma 交互稿，确认 `资料/figma-links.md` 存在且 fileKey/nodeId 已填写

---

### 3.2 写作范围确认

询问用户三个问题：

| 问题 | 选项 | 影响 |
|------|------|------|
| 主写 §1.1 还是 §1.2？ | 架构需求 / 特性需求 / 两者都写 | 决定第一章的展开方式 |
| DCP 阶段？ | DCP2（部分设计）/ DCP3（完整设计） | DCP2 重点写 §1+§2，DCP3 全章节 |
| 哪些模块纳入范围？ | 用户指定 | 决定 §4.5 模块设计的范围 |

### 3.3 Gap Analysis（总设级）

> **目标**：读完输入文档后，输出"待决策清单"，让用户在写之前解决不确定性。
> **不要跳过这一步直接写。** 总设级的隐含问题比概设更危险——一个架构决策错误会影响所有下游模块。

**执行方法**：

读完需求/规划文档后，对每个核心设计点自问四个问题：

| 自问 | 对应章节 | 典型隐患 |
|------|---------|---------|
| 架构边界确定了吗？ | §4.1 + §4.5 | 哪些服务在范围内？哪些作为外部依赖？边界模糊导致职责不清 |
| 方案选型有备选吗？ | §1.x.6 | 只有一个方案 = 没有做选型，评审必打回 |
| DFX 目标量化了吗？ | §2 + §5 | 只有定性描述无法验证，评审追问"怎么证明达标？" |
| 长期演进考虑了吗？ | §1.x.1.2-3 | 只看当前版本，下个版本就要推翻重来 |

**输出待决策清单**（分三级）：

```
## [版本/项目名] 总体设计 — 待决策清单

### 🔴 阻塞设计（必须先定，影响架构方向）
1. [问题描述]
   → 影响：§X.X [具体章节]
   → AI 建议：[方案 + 理由]
   → 需要你确认：[具体决策点]

### 🟡 可用兜底方案（先按兜底写，后续可调）
2. [问题描述]
   → 兜底方案：[具体方案]
   → 后续调整条件：[什么时候需要改]

### 🟢 不影响设计（记录但不阻塞）
3. [问题描述]
   → 原因：[为什么不影响当前设计]
```

**判断标准**：

- **🔴 阻塞**：如果按不同答案来设计，§4.1 架构图或 §1.x.6 方案选型会不一样
- **🟡 兜底**：有一个合理的默认方案，后续调整只改局部
- **🟢 不影响**：纯实现细节或延后迭代的内容

**等待用户逐条过** — 不要自行假设答案。

---

### 3.4 决策会话（用户确认）

> AI 辅助分析利弊，但**决策权在用户**。

对每条 🔴 阻塞项：
- 用户当场能定 → 记录决策结论
- 用户需要外部确认 → 确定兜底方案 + 标注"TBD，兜底方案=XXX"
- 用户说跳过 → 标注"未决，§X.X 暂不展开"

对每条 🟡 兜底项：
- 用户同意兜底 → 确认
- 用户有更好方案 → 更新

**输出决策表**（写进设计文档 §6.3 遗留问题）：

| 问题 | 决策 | 状态 | 影响章节 |
|------|------|------|---------|
| [问题1] | [结论] | ✅ 已定 | §4.1, §1.1.6 |
| [问题2] | [兜底方案] | ⚠️ TBD | §5.2 |
| [问题3] | 暂不展开 | ❌ 未决 | §4.5.2 |

---

### 3.5 推荐写作顺序（避免返工）

> **核心洞察**：§2 目标定清楚后，§1 的方案选型才有评判标准；§4 架构定了，§5 DFX 才有具体对象。

```
推荐顺序                          原因
──────────                        ──────
步骤1: §2 设计目标                先定"要达到什么"，后续章节有评判标准
步骤2: §1 技术需求+方案选型       核心决策先定，架构方向明确
步骤3: §4.1 软件总体架构          五视图，整体蓝图
步骤4: §4.2-§4.3 系统流程         主流程+辅助流程，导出模块接口
步骤5: §4.4-§4.5 数据+模块设计    数据归属和模块边界
步骤6: §5 关键特性设计（DFX）     对照具体模块和流程填写
步骤7: §0 引言 + §3 硬件方案      此时全貌清晰，写起来准确
步骤8: §6-§8 总结+变更+修订       收口
```

**关键检查点**：

- 步骤 2 完成后，**必须回查 §2**：方案选型的评估准则是否与设计目标对齐？
- 步骤 5 完成后，**必须回查 §4.2**：主流程导出的接口是否与模块设计一致？
- 步骤 6 完成后，**必须回查 §2**：DFX 设计是否覆盖了所有目标项？

**TBD 处理规则**：

- 状态 ⚠️ TBD 的 → 按兜底方案写，文档内标注 `<!-- TBD: 待确认后可能调整 -->`
- 状态 ❌ 未决的 → 该章节写骨架框架，标注"待补充"，不编造内容

### 3.6 DFX 防套话规则（总设级）

> 总设的 DFX 比概设更宏观，但同样不能写套话。区别在于：总设写"系统级目标和策略"，概设写"模块级实现细节"。

**§5.1 安全性 — 每条必须有四要素**：

| 要素 | 禁止写法 | 正确写法 |
|------|---------|---------|
| 资产 | "系统数据" | "租户告警数据（含 IP、域名等敏感信息）" |
| 威胁 | "未授权访问" | "攻击者通过伪造 JWT 跨租户查询告警" |
| 措施 | "认证鉴权" | "JWT 签名验证 + 租户 ID 从 token 提取，查询强制注入租户条件" |
| 残余风险 | 不写 | "token 泄露依赖 30min TTL 过期机制" |

**§5.2 可靠性 — 必须有三层**：

| 层级 | 禁止写法 | 正确写法 |
|------|---------|---------|
| 目标 | "高可靠" | "故障检测率 ≥ 95%，自动恢复率 ≥ 80%，业务中断 < 10s" |
| 故障场景 | "服务异常" | "MongoDB 主节点宕机，写入请求失败，影响告警入库" |
| 实现方案 | "主备切换" | "MongoDB 副本集自动选主（election timeout 10s）+ 应用层重试（3次，间隔 1s）" |

**§5.3-§5.9 其他 DFX — 每项必须有四要素**：

| 要素 | 示例（可运维性） |
|------|----------------|
| 目标 | "故障定位时间 < 15min" |
| 场景 | "用户报告查询超时，需定位是网络/服务/数据库问题" |
| 机制 | "分布式链路追踪（trace_id 贯穿全链路）+ Grafana 仪表盘（按服务分层）" |
| 验证 | "故障注入演练，验证 15min 内可定位根因" |

---

### 3.7 自检清单（写完后执行）

> 对照清单逐项过，红线项不通过则不提交评审。

**步骤**：

1. **需求承接检查**：每个关键需求都能在总设中找到承接章节？
2. **目标量化检查**：§2 的每个目标项都有数值 + 验证方式？
3. **方案选型检查**：至少一个核心设计点有备选方案比较？准则来自业务特征？
4. **架构完整性检查**：§4.1 五个视图都覆盖了（不涉及的写了原因）？
5. **DFX 红线检查**：§5.1 安全性和 §5.2 可靠性不是空泛描述？
6. **流程导出检查**：§4.2 主流程都导出了模块接口？
7. **风险收口检查**：§6.2 风险都有规避措施？§6.3 遗留问题有时间和责任人？
8. **TBD 复查**：所有 TBD 兜底方案自洽？未决项标注了"待补充"？
9. **章节完整性**：没有留空章节（不涉及的写了原因）？

**常见遗漏**：

| 遗漏类型 | 检查方法 |
|---------|---------|
| 方案选型无备选 | 检查 §1.x.6 是否至少有 2 个方案 |
| 目标无验证方式 | 检查 §2.1 表格"验证方式"列是否为空 |
| DFX 无量化指标 | 检查 §5 各节是否有具体数值 |
| 模块边界不清 | 检查 §4.5 是否写了"模块不负责什么" |
| 遗留问题无责任人 | 检查 §6.3 表格"责任人"列是否为空 |
| 决策表未同步 | §6.3 是否包含步骤 4 决策表的全部 TBD + 未决项 |

### 3.8 画图工具选择指引

> 总设中的图按类型选择工具，不要所有图都用同一种方式。

| 图类型 | 工具 | 输出 | 说明 |
|--------|------|------|------|

| 数据流图（§4.4） | draw.io | .drawio + PNG | 需要箭头样式区分同步/异步 |

**修改策略**：

- Mermaid 图修改时，直接编辑代码块

## Part 4: 评审门禁（架构师视角）

> 本部分从 TMG 架构评审的视角，定义总设的质量标准。目标：提交评审前自检通过，减少打回次数。

### 4.1 红线项（6 项，不通过直接打回）

| 编号 | 红线项 | 要求 | 不通过判定 |
|------|--------|------|-----------|
| R1 | 需求承接 | 需求文档的关键需求必须在总设中有承接章节 | 存在关键需求找不到对应设计章节 |
| R2 | 章节完整 | 除 §1.1/§1.2 二选一外，其他章节不得留空 | 有章节留空且未写"不涉及"原因 |
| R3 | 方案选型 | 核心设计点必须有备选方案比较 | 只有最终方案，无备选比较和评估依据 |
| R4 | 目标量化 | 性能/可靠性等目标必须有数值和验证方式 | 目标只有定性描述（"高性能""高可靠"） |
| R5 | DFX 落地 | 安全性/可靠性章节必须有具体场景和机制 | DFX 章节是空泛的模板套话 |
| R6 | 业务边界 | 必须明确设计对业务的约束 | 方案选型无 §1.x.6.7（对业务的约束） |

---

### 4.2 评分维度与权重

> 权重为建议值，实际以公司 TMG 评审标准为准。

| 维度 | 权重 | 评分要点 | 典型扣分项 |
|------|------|---------|-----------|
| 需求承接 | 15% | 需求覆盖率、需求可追溯性 | 需求遗漏、需求与设计脱节 |
| 方案选型 | 20% | 备选方案完整性、评估准则合理性、决策有据 | 无备选、准则拍脑袋、无约束说明 |
| 架构清晰度 | 20% | 视图完整、模块边界清晰、流程可追溯 | 架构图无箭头、模块职责重叠、流程无异常处理 |
| DFX 落地 | 20% | 目标量化、场景具体、机制可验证 | 套话、无量化、无验证方式 |
| 风险可控 | 10% | 风险识别全面、措施具体可执行 | 只列风险无对策、措施空泛 |
| 文档规范 | 15% | 章节完整、格式规范、表格对齐 | 留空章节、占位符未替换、格式混乱 |

**评级标准**：

| 评级 | 条件 |
|------|------|
| A（优秀） | 红线项全通过 + 总分 ≥ 85% + 无维度低于 60% |
| B+（良好） | 红线项全通过 + 总分 ≥ 75% |
| B（合格） | 红线项全通过 + 总分 ≥ 60% |
| C（不合格） | 任一红线项不通过，或总分 < 60% |

### 4.4 常见评审意见及应对

| 评审意见 | 根因 | 应对方法 |
|---------|------|---------|
| "为什么不选方案 X？" | §1.x.6 缺少备选比较 | 补充备选方案 + 评估矩阵 + 不选原因 |
| "目标值怎么来的？" | §2 目标无设定依据 | 补充来源（需求文档/历史基线/竞品数据） |
| "可靠性怎么保证？" | §5.2 只有目标没有方案 | 补充故障场景分析 + 具体实现方案 |
| "模块边界在哪？" | §4.5 只写了职责没写边界 | 补充"模块不负责什么" + 与其他模块的交互方式 |
| "这个设计对业务有什么限制？" | §1.x.6.7 缺失 | 补充方案对业务的约束 + 需要谁达成一致 |
| "长期怎么演进？" | §1.x.1.2-3 缺失或空泛 | 补充长期需求分析 + 当前需预留的能力 |
| "故障场景覆盖全了吗？" | §5.2.2 故障类型不全 | 按进程/网络/数据/人因四类逐一分析 |
| "怎么验证设计目标达成？" | §2 验证方式空泛 | 补充具体验证方法（工具/环境/持续时间/通过标准） |

## 与 design-session 的协作

本指南在 `/design-session:write-overall` 子命令中自动加载。典型流程：

```
/design-session:resume <项目目录>          # 恢复上下文
用户: "写本版本总体设计"                     # 明确任务
/design-session:write-overall <项目目录>   # 进入总设写作模式
```
