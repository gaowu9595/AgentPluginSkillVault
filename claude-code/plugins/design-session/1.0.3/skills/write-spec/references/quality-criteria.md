# 系统需求质量评估标准

> **版本**：v1.0
> **来源**：IEEE 830-1998 + INCOSE GTWR v4 + 项目实践
> **用途**：系统需求卡片评审打分依据，`/spec-check` agent 的评分规则

---

## 1. 评估维度（8 维度，加权 10 分制）

| # | 维度 | 权重 | 定义 | 达标线 |
|---|------|------|------|--------|
| 1 | **完整性** | 20% | 功能点全覆盖（正常+异常场景）、DFX 全覆盖、依赖明确 | ≥7 |
| 2 | **可验证性** | 20% | 每个功能点能写出测试用例、有明确验收标准 | ≥7 |
| 3 | **无歧义** | 15% | 状态机/枚举/字段有明确定义、无模糊用语 | ≥7 |
| 4 | **一致性** | 15% | 卡片间不矛盾、与已有决策不冲突、术语统一 | ≥7 |
| 5 | **可追溯** | 10% | 每条需求标注来源、待确认项标注来源和影响 | ≥6 |
| 6 | **可排序** | 5% | 功能点有优先级、问题有 P0/P1/P2 分级 | ≥6 |
| 7 | **可修改** | 5% | 模块化结构、编号清晰、交叉引用明确 | ≥6 |
| 8 | **正确性** | 10% | 与用户真实需求一致（代码验证/Figma 确认/用户确认） | ≥7 |

**总分计算**：加权平均，满分 10 分。**≥7.5 分可进入概要设计，<7.0 需补充后重新评审。**

---

## 2. 各维度评分细则

### 2.1 完整性（20%）

| 分数 | 标准 |
|------|------|
| 9-10 | 所有功能点有正常+异常场景步骤表；DFX 全覆盖（性能/可靠/安全/可测试）；依赖表完整；工作量评估合理 |
| 7-8 | 主要功能点有步骤表；DFX 覆盖 3/4 维度；依赖表有但部分待确认；工作量有估算 |
| 5-6 | 部分功能点缺步骤表或异常场景；DFX 仅覆盖 1-2 维度；依赖不完整 |
| 3-4 | 多数功能点仅有描述无步骤表；缺 DFX；无依赖分析 |
| 1-2 | 仅有功能列表，无场景展开 |

**扣分项**：
- 功能点缺正常场景步骤表：-2/处
- 功能点缺异常场景：-1/处
- 缺 DFX 某维度：-1/维度
- 无工作量评估：-1
- 无依赖与风险表：-1

### 2.2 可验证性（20%）

| 分数 | 标准 |
|------|------|
| 9-10 | 每个功能点有对应测试验收场景；验收标准含具体数值（RT/TPS）；异常场景有明确预期结果 |
| 7-8 | 主要功能点有验收场景；有性能指标但部分为估算；异常场景有预期 |
| 5-6 | 部分功能点有验收场景；性能指标模糊（"快速"/"及时"） |
| 3-4 | 仅有笼统验收标准；无具体数值 |
| 1-2 | 无验收场景 |

**扣分项**：
- 无测试验收场景章节：-3
- 功能点无法写出测试用例（描述过于模糊）：-2/处
- 性能指标用模糊词（"快速"/"合理"）：-1/处

### 2.3 无歧义（15%）

| 分数 | 标准 |
|------|------|
| 9-10 | 状态机有完整枚举+转换条件；字段有类型+约束；无"等"/"可能"/"适当"/"相关" |
| 7-8 | 状态机有枚举；字段有类型；偶有模糊词但不影响理解 |
| 5-6 | 状态机不完整；部分字段缺类型；有多处模糊词 |
| 3-4 | 关键概念无明确定义；大量模糊词 |
| 1-2 | 多处可做不同解释 |

**扣分项**：
- 使用"等"/"可能"/"适当"/"相关"/"必要时"：-1/处（上限 -3）
- 状态机无明确枚举值：-2
- 关键字段无类型定义：-1/处
- 同一概念用不同名称：-1/处

### 2.4 一致性（15%）

| 分数 | 标准 |
|------|------|
| 9-10 | 卡片间术语统一；与 context.md 决策一致；与迭代1 不冲突；数据模型字段名跨卡片一致 |
| 7-8 | 基本一致，偶有术语不统一但不影响理解 |
| 5-6 | 有 2-3 处矛盾或术语混用 |
| 3-4 | 多处矛盾，需要大量澄清 |
| 1-2 | 严重矛盾，无法作为开发依据 |

**扣分项**：
- 与其他卡片矛盾：-2/处
- 与 context.md 已有决策冲突：-3/处
- 同一实体不同卡片字段名不一致：-1/处

### 2.5 可追溯（10%）

| 分数 | 标准 |
|------|------|
| 9-10 | 每条需求标注来源（Figma/PDF/代码/用户确认）；待确认项标注来源+影响卡片；有交互原型引用 |
| 7-8 | 主要需求有来源标注；待确认项有来源 |
| 5-6 | 部分需求无来源；待确认项来源不清 |
| 3-4 | 大部分需求无来源标注 |
| 1-2 | 完全无来源信息 |

### 2.6 可排序（5%）

| 分数 | 标准 |
|------|------|
| 9-10 | 功能点有明确优先级标注；待确认项有 P0/P1/P2 分级；依赖有先后顺序 |
| 7-8 | 有优先级但不够细；待确认项有分级 |
| 5-6 | 部分有优先级标注 |
| 1-4 | 无优先级信息 |

### 2.7 可修改（5%）

| 分数 | 标准 |
|------|------|
| 9-10 | 功能点独立编号（BILL-01/CUST-02）；章节结构清晰；修改一处不影响其他 |
| 7-8 | 有编号；结构基本清晰 |
| 5-6 | 编号不完整；部分内容耦合 |
| 1-4 | 无编号；内容混杂 |

### 2.8 正确性（10%）

| 分数 | 标准 |
|------|------|
| 9-10 | 所有需求经代码验证/Figma 确认/用户签字；无臆想内容 |
| 7-8 | 主要需求有验证来源；少量推断已标注"需验证" |
| 5-6 | 部分需求为推断且未标注 |
| 3-4 | 大量未验证的假设 |
| 1-2 | 明显与现实不符 |

**扣分项**：
- 编造不存在的接口/表名/字段名：-3/处（严重，违反 CLAUDE.md §4）
- 推断未标注"需验证"：-1/处
- 与代码现状矛盾：-2/处

## 3. 评估流程

### 3.1 自动评估（agent 执行）

```
1. 读取目标系统需求卡片
2. 逐维度检查（按扣分项清单）
3. 输出评分表 + 具体扣分点 + 改进建议
4. 如有跨卡片一致性问题，标注冲突位置
```

### 3.2 人工评审（评审会）

```
1. 过 agent 评估报告，确认扣分是否合理
2. 重点讨论"正确性"维度（需用户确认）
3. 逐项过待确认问题（§5）
4. 确认总分 ≥7.5 后签字放行
```

### 3.3 评估输出格式

```markdown
## 系统需求质量评估报告

**卡片**：<卡片名称>
**评估时间**：YYYY-MM-DD
**总分**：X.X / 10（加权）
**结论**：✅ 可进入概要设计 / ⚠️ 需补充后重评 / ❌ 不达标

### 各维度得分

| 维度 | 得分 | 扣分项 |
|------|------|--------|
| 完整性 | X/10 | <具体扣分点> |
| ... | ... | ... |

### 关键问题（必须修复）
1. <问题描述 + 位置 + 建议修复方式>

### 改进建议（可选）
1. <建议>

### 跨卡片一致性检查
- <冲突点 + 涉及卡片>
```
