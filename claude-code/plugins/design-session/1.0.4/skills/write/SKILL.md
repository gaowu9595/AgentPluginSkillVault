# write（设计文档编写）

**参数**：`$ARGUMENTS` = `<项目目录>`

**REQUIRED BACKGROUND:** Read `shared/design-session-engine.md` for path conventions.

阶段推进与完成统一使用 `shared/workflow.md` 和生成的 `shared/workflow-flowchart.md`。写作前核验输入/澄清/系统需求三项证据；写作后串行登记实际完成的模板、数据库、安全和内容检查，运行 `workflow_gate.py evaluate <项目>`。已有有效审查直接复用。微型设计使用轻量模板自检与当前范围的数据库 scope_passed，不升级为全量审查。

涉及新增/变更API、内部调用或消息契约时，完整读取 [接口必要性与源码下钻规则](references/interface-review.md)，在步骤3.5核实来源、步骤6定稿前执行接口/字段取舍、步骤8.1核对证据。已有明确授权和决策直接沿用；普通技术字段先自行查证，不重复逐条向用户索取确认。

## 前置条件

当前阶段应为"阶段3 概要设计"或更后。如不确定，先执行 `/design-session:status`。

## 执行流程

```
步骤1 输入就绪 → 步骤2 模板判断 → 步骤3 写作范围 → [概设/总设] 步骤3.5 已有代码覆盖度 → 步骤4 Gap Analysis → 步骤5 决策会话 → 步骤6 编写 → 步骤7 DFX → 步骤8 自检 → 步骤9 完成
                                                    → [微设] 步骤4M 编写 → 步骤5M 自检 → 步骤6M 完成
```

> **核心原则：先思考再动笔。** Gap Analysis 是关键 — 把不确定性暴露在写之前，不是写完再改。

### 步骤 1：输入就绪检查

1. 读 `<项目>/.ai/context.md` — 确认当前阶段和关键决策
2. `ls <项目>/架构设计/系统需求/` — 确认对应系统需求卡片存在
3. `ls <项目>/.ai/*-摘要.md` — 确认交互稿摘要已落盘
4. 读代码仓库编码规范 — 确认目录结构和命名规范
5. 检查阶段状态：`spec_status` 至少为 `locked` 或明确记录了暂用兜底；`input_status`、`journey_status` 和 `p0_status` 不得为未知/未完成。
6. 记录本次设计使用的输入指纹；若输入或代码基线变化，不能沿用旧的设计审查 `passed` 标记。

缺少阻塞项 → 暂停，告知用户需要先补齐。

### 步骤 2：模板类型自动判断

读取系统需求卡片，分析以下信号：

| 信号 | → 模板类型 |
|------|-----------|
| 全新模块 + 新增功能点 ≥ 3 + 有新数据模型 | **概要设计** |
| 已有模块 + 变更点 ≤ 3 + 无新表/新服务 | **微型设计** |
| 跨模块架构变更 / 新增基础设施 / 新增外部集成 | **总体设计**（极少触发） |

**判断依据**（按优先级）：
1. 系统需求功能点分类表中"新增"数量
2. 是否引入新的数据表或新的服务模块
3. 是否涉及跨模块数据流变更
4. 变更是否局限于单一层（如纯前端 UI 调整）

**输出判断结果给用户确认**：

```
## 模板类型判断

基于系统需求分析：
- 新增功能点：N 个
- 新增数据表：M 张
- 涉及模块：[列表]
- 变更层次：[前端/后端/全栈]

→ 推荐模板：**概要设计** / **微型设计** / **总体设计**
→ 原因：[一句话]

确认使用此模板？
```

用户确认后，概设/总设走步骤 3~9，微设走步骤 3→4M~6M。

### 步骤 2.5：模板锁定（强制）

1. 编写前必须完整读取 `skills/write/references/design-template.md` 和 `skills/write/references/design-guide.md`，建立“模板章节 → 现有内容/新增内容”的映射表。
2. 概要设计必须使用模板的固定骨架：`## 1`~`## 10`、`4.1`~`4.7`、`4.6.1` 安全性设计、`4.6.2` 可靠性设计、`## 附录：设计 Checklist 自检`。不得因为已有文档使用了自定义标题，就把内容直接堆到相邻章节或另起一套编号。
3. 历史文档重构先保留基线（提交、复制或明确备份），先做章节映射再改标题；禁止依据摘要重写、先删后补或用“AI 需要细节”代替内容保全。
4. 单独记录四类状态：`content_gate`（内容覆盖）、`template_gate`（模板结构）、`database_gate`（数据库审核）、`security_gate`（安全审核）。内容完整不等于模板通过，Agent 审核通过也不等于结构门禁通过。
5. 初始状态写入工作记录：`template_check=not_run`。在确定性脚本通过前，不得写成 `passed`。

### 步骤 3：确认写作范围

询问用户：
- 哪个模块的设计？
- 从哪一章开始？（续写 vs 全新）
- 哪些系统需求卡片作为输入？

## 概要设计流程（步骤 3.5~9）

### 步骤 3.5：已有代码覆盖度检查（写之前必须完成）

> **目标**：对照已有代码，确认系统需求中每个功能点的实现状态，避免重复设计已有功能。
> **不要跳过这一步。** 概要设计假设所有功能从零开始是最常见的浪费来源。

**执行方法**：

1. 定位代码仓库（`<项目>/src/` 或 `repos/` 下对应仓库）
2. 对系统需求中每个功能点，搜索已有代码：
   - Controller 层：是否已有对应路由/接口？
   - Service 层：是否已有对应业务逻辑？
   - DAL/DB 层：是否已有对应表和 CRUD？
   - 公共能力：加密/权限/枚举等是否已实现？
3. 判断实现状态：
   - **✅ 已有**：功能完整实现，本迭代无需改动
   - **🔧 已有+增量**：基础已有，本迭代需扩展（如加字段、加后置动作）
   - **🆕 全新**：完全没有，需从零设计

4. **输出覆盖度表**：

```
## 已有代码覆盖度检查

| 功能点 | 实现状态 | 已有代码位置 | 迭代N 增量 |
|--------|---------|-------------|-----------|
| XXX-01 | ✅ 已有 | `controller/web/xxx/xxx_controller.py` | 无变更 |
| XXX-02 | 🔧 已有+增量 | `service/xxx/imp/xxx_service_imp.py` | 增加 YYY 字段/后置动作 |
| XXX-03 | 🆕 全新 | — | 完整设计 |
```

5. **对后续步骤的影响**：
   - ✅ 已有 → §3 接口部分仅列参考表（路径+方法），不重新定义参数/返回值
   - 🔧 已有+增量 → §3 只描述增量部分，标注"基于已有接口扩展"
   - 🆕 全新 → 正常走完整设计流程
   - §6 子模块工作量只计算增量，不含已有功能
   - 文档头部增加"迭代N 增量说明"表格

6. **等待用户确认覆盖度表** — 用户可能知道某些"已有"代码需要重构或废弃

外部系统涉及统计口径、权限、多实例、公共功能或陌生模块时，按interface-review.md §3沿实际调用链下钻。引用Service/DAL/转换规则说明旧能力能否复用，区分本轮新增与迭代前已有；不能只看路由或函数名。具体证据写回对应设计章节，不新增一套外部调查报告。

### 步骤 4：Gap Analysis（写之前必须完成）

> **目标**：读完系统需求 + 摘要后，输出"待决策清单"，让用户在写之前解决不确定性。
> **不要跳过这一步直接写。** 即使输入看起来完整，也要做 Gap Analysis — 隐含问题比显式 ❓ 更危险。

**执行方法**：

1. 读系统需求卡片的 §5 待确认问题 + §2 各功能点的约束条件
2. 读交互稿摘要的"待确认项"部分
3. 读 context.md 的待确认问题索引
4. 对每个功能点，自问：
   - 数据模型确定了吗？（字段、类型、约束、关联关系）
   - 状态机确定了吗？（状态枚举、流转条件、终态）
   - 外部依赖明确了吗？（接口协议、参数、超时、降级）
   - 双品牌差异处理了吗？（Sangfor vs Fornova 逻辑分支）

5. **输出待决策清单**（分三级）：

```
## <模块名> 概要设计 — 待决策清单

### 🔴 阻塞设计（必须先定，影响多个章节）
1. [问题描述]
   → 影响：§X.X [具体章节]
   → AI 建议：[方案 + 理由]
   → 需要你确认：[具体决策点]

### 🟡 可用兜底方案（先按兜底写，后续可调）
2. [问题描述]
   → 兜底方案：[具体方案]
   → 后续调整条件：[什么时候需要改]

### 🟢 不影响设计（记录但不阻塞）
3. [问题描述]
   → 原因：[为什么不影响当前设计]
```

6. **等待用户逐条过** — 不要自行假设答案

### 步骤 5：决策会话

> 用户逐条确认待决策清单。AI 辅助分析利弊，但**决策权在用户**。

对每条 🔴 阻塞项：
- 用户当场能定 → 记录决策结论
- 用户需要外部确认 → 确定兜底方案 + 标注"TBD，兜底方案=XXX，确认后可能调整"
- 用户说跳过 → 标注"未决，§X.X 暂不展开，后续补充"

对每条 🟡 兜底项：
- 用户同意兜底 → 确认
- 用户有更好方案 → 更新

**输出决策表**（写进设计文档 §7.2 遗留问题）：

| 问题 | 决策 | 状态 | 影响章节 |
|------|------|------|---------|
| [问题1] | [结论] | ✅ 已定 | §4.5, §6.1 |
| [问题2] | [兜底方案] | ⚠️ TBD | §5.2 |
| [问题3] | 暂不展开 | ❌ 未决 | §6.3 |

### 步骤 6：按推荐顺序编写

**基于步骤 5 的决策表动笔。** 不要按章节号线性推进。推荐顺序：

1. §2 需求跟踪表（自检列留空）
2. §4.2 方案选型（核心决策点 — 来自步骤 5 已定的 🔴 项）
3. §4.3 静态结构草图
4. §4.5 概要流程（Mermaid 时序图）
5. §5 数据结构（DDL + 字段说明）
6. §6 流程设计 + 函数列表
7. §3 对外接口：根据§5/§6，按interface-review.md §2/4先比较接口复用方案，再逐字段核对来源、使用步骤、删除影响及兼容取舍；之后定稿请求/返回/异常。检查公共外壳及嵌套字段，不只精简请求参数
8. §4.1 背景 + §4.4 架构影响
9. §7~§10（§7.2 遗留问题从决策表填充）

**模板骨架要求：**

- §1 必须包含目的、定义、参考、目标/验收、输入状态和范围边界。
- §2 必须包含需求跟踪和模块整体目标，且每条需求有后续章节回指。
- §3 必须声明 API、消息接口是否涉及；不涉及的接口类型写明原因，不留空白。
- §4 必须按“背景 → 方案选型 → 静态结构 → 架构影响 → 概要流程 → 关键特性 → 风险”组织，不能把方案对比放在架构影响章节。
- §5 必须包含配置、全局数据结构、字段/关系/不变量、迁移和 CRUD 边界。
- §6 每个新增子模块至少写职责、流程、函数族、输入/输出、前后置条件、测试性和工作量；已有功能只保留引用和增量。
- §7 必须写关联分析和遗留问题；§8~§10 必须分别覆盖测试、变更控制、评审门禁/修订记录。
- 必须有独立的 `## 附录：设计 Checklist 自检`，且清单状态不能替代门禁状态。

**TBD 处理规则**：
- 状态 ⚠️ TBD 的 → 按兜底方案写，文档内标注 `<!-- TBD: 待确认后可能调整 -->`
- 状态 ❌ 未决的 → 该章节写骨架框架，标注"待补充"，不编造内容

### 步骤 6.5：评审主文档与编码附件分层

概要设计及其职责附件共同服务人工评审和编码。可读说明整合到现有设计，按职责与篇幅拆分；具体规则唯一来源为 `references/design-guide.md` 的“可读接口与唯一维护位置”，本步骤和content_gate均按该节执行。

1. **评审主文档**：保留模板 §1~§10、Checklist、整体方案、用户旅程、关键接口、表职责/关系、资金与状态不变量、函数族、DFX、代表性测试和发布门禁。评审者不读附件也必须能说明“做什么、为什么、怎么落地、风险在哪里”。
2. **职责附件**：完整DTO/错误码/权限/页面状态、DDL/函数定义、测试矩阵按已有系统/模块职责归位。附件本身也须解释用途、流程和含义；每个契约只指定一个详细维护位置，主文保留摘要及链接。附件不增加主文未有的需求，不另建与现有附件重复的“人读版”。
3. **方案选型结论先行**：§4.2 固定按“采用的整体方案 → 整体备选对比 → 用户旅程中的局部决策 → 方案边界”组织，禁止直接堆零散技术选择。
4. **触发拆分**：主文档超过 60,000 非空白字符或同类概设中位数 1.5 倍、正文段落超过 500 字符、单代码块超过 150 行时，必须拆附件；超过 300 字符的正文优先改为小节或表格。
5. **无损顺序**：已有大文档重构时先提交/备份基线，先复制完整合同到附件并校验，再压缩主文档。禁止先删后补、凭摘要重写完整字段或只用“AI 需要细节”拒绝分层。
6. **确定性门禁**：运行 `shared/scripts/validate_design_readability.ps1`；有基线时同时传 `-BaselineDocument` 与全部 `-Attachments`。任何强制章节、长段落、超长代码块、本地链接或基线合同检查失败都不得进入步骤 7。

### 步骤 7：DFX 防套话

- STRIDE 每条必须有：具体威胁 + 涉及组件名 + 具体措施
- FMEA 只覆盖真正会出错的场景，改进措施要有检测+恢复+预防
- 不要用 `flowchart TD`（Typora 显示异常），用 `graph TD`
- 性能/缓存/限流/降级按interface-review.md §5写具体场景、负载假设、实现位置、用户结果和验证目标；多实例核算批次数/共享并发/总截止。工程初值不写成已验证性能。

### 步骤 8：自检（强制，不可跳过）

#### 8.0 模板结构门禁（优先于语义审查）

先运行 `shared/scripts/validate_design_readability.ps1`，检查固定章节、方案选型顺序、段落/代码块体量、本地链接和（如有）基线附件合同。脚本失败时，`template_gate=failed`，必须先修复并重跑；不得先启动 Agent 语义审查，也不得用“内容已覆盖”“附件已存在”“Agent 已看过”或字数下降代替结构通过。只有脚本退出码为 0 才能记录 `template_gate=passed`。

#### 8.1 基础对齐检查

1. §2.1 自检列回填
2. 接口 ↔ 函数列表对齐
3. 数据结构 ↔ 接口对齐
4. 红线项检查（安全+可靠性不缺失）
5. 测试用例覆盖
6. **TBD 项复查**：所有 TBD 兜底方案是否自洽？未决项是否标注了"待补充"？
7. **反向追溯检查（防臆造接口）**：每个新增接口关联当前需求/交互场景；技术辅助接口也须说明服务哪条业务链、删除后具体失败场景及已有能力缺口。没有当前用途就删去拟新增项或记录不做，不能仅用“扩展性”证明必要。不能用未确认的业务选择冒充已定需求；已授权的技术方案按已记录决策执行。
8. **文档内函数签名一致性**：对 §6 函数列表中的同类写操作，检查事务参数（session）、错误返回模式、前后置条件描述粒度是否一致。有的传 session 有的不传、有的写了事务边界有的只写"无" → 修正为一致。
9. **已有功能残留扫描（逐章）**：对文档每一个章节（§1~§10），检查是否包含纯属已有迭代功能的详细设计（完整流程图、函数列表、DDL、测试用例等）。判断标准：如果步骤 3.5 覆盖度表中标记为"✅ 已有"的功能点，其详细设计不应出现在本迭代文档中。已有内容 → 精简为一句引用（"已有，见代码 `path`"）或直接删除。**不要凭直觉挑章节检查，必须逐章扫描。**
10. **接口职责与数量检查**：按业务动作、权限、生命周期、兼容和调用成本判断合并/拆分，说明删除或合并后对当前场景的影响。不得用字段重叠率机械新增接口；同一业务资源的合法响应变体不自动拆分，权限或副作用明显不同也不能只为少一个接口而合并。
11. **文档可读性检查**：运行 `validate_design_readability.ps1`。主文档必须通过模板、体量、方案选型、段落、代码块和链接门禁；拆附件时还必须通过基线合同无损检查。详细合同存在附件不等于可以清空主文档，主文档仍须保留关键字段、核心不变量和函数族。

12. **接口必要性与可读契约核对**：按 `references/interface-review.md` §6和design-guide核对表逐项覆盖当前接口/字段，检查复用取舍、外部实际规则、字段消费者/删除影响、正常及关键失败复述、唯一维护位置和Schema一致性；结论并入content_gate报告。缺证据列出具体对象，不接受一句“已精简”；Schema或模板脚本通过不能代替本项。

#### 8.2 前置依赖接口扫描（防遗漏辅助接口）

> **根因**：主接口（CRUD/业务操作）容易写全，但 UI 交互点的前置数据接口（枚举、初始化、预览、下载）容易遗漏。
> 这些接口在编码阶段才发现缺失时，会导致返工和设计补丁。

**对每个已定义的页面/弹窗/表单，逐一检查**：

| UI 交互点 | 检查问题 | 常见遗漏 |
|-----------|---------|---------|
| 列表页 | 筛选项的枚举数据从哪来？ | 状态枚举接口、类型枚举接口 |
| 列表页 | 有导出功能吗？ | 导出接口（异步/同步） |
| 编辑表单 | 哪些字段是下拉/选择？数据源是什么？ | 字段枚举接口、关联数据查询 |
| 弹窗 | 打开时需要预加载什么数据？ | 初始化/详情接口（如还款弹窗需要未还清账单列表） |
| 文件操作 | 有上传/下载吗？ | 通用上传接口、文件下载接口 |
| 操作确认 | 需要预览/计算吗？ | 前端能算→确认数据源接口返回了所需字段；需后端算→预览接口 |
| 批量操作 | 有全选/批量处理吗？ | 批量接口 vs 循环调用单条 |
| 状态变更 | 变更后需要刷新哪些数据？ | 是否需要额外的状态查询接口 |

**输出扫描结果**：

```
## 前置依赖接口扫描

| 页面/弹窗 | 交互点 | 需要的数据 | 对应接口 | 状态 |
|-----------|--------|-----------|---------|------|
| 账单列表 | 状态筛选 | 状态枚举 | 前端硬编码（4 态固定） | ✅ 无需接口 |
| 推送弹窗 | 打开 | 上次推送配置 | GET /invoice/{id}/push-config | ✅ 已定义 |
| 还款弹窗 | 打开 | 未还清账单+余额 | GET /invoice/repay-init | ✅ 已定义 |
| ... | ... | ... | ... | ... |

遗漏项：N 个
```

**遗漏项 > 0 → 必须补充接口定义 + 函数列表后才能进入步骤 9**

#### 8.3 权限设计检查（按需触发）

> **根因**：接口功能设计容易写全，但权限注册（谁能访问）、数据权限（能看到哪些数据）、越权防护（不能越界操作）容易遗漏。
> 编码阶段才发现权限未设计时，会导致安全漏洞或返工。

<!-- permission-evidence-gate:start -->
在设计接口权限前，先读取项目指令、权限架构说明、路由注册、策略初始化和后端授权代码，输出“权限事实源”表。每个新增或变更接口必须说明权限是“复用或新增”，并给出文件、符号或现有接口的代码证据。未证明现有权限模型前，禁止创造新角色、权限码或授权层；找不到权威来源时标记为设计阻塞。项目提供确定性的权限校验工具时，必须记录项目校验命令及执行结果。
<!-- permission-evidence-gate:end -->

**触发条件**：本模块是否包含需鉴权的用户 HTTP 接口？

- **否**（纯后台进程/定时任务/消息消费者/内部 RPC）→ 标注"本模块无用户接口，不涉及权限设计"，跳过
- **是** → 执行以下检查

**步骤**：

1. **发现项目事实源**：按项目指令优先查找权限架构说明、路由注册、策略初始化、后端授权、数据范围和前端可见性代码；不得只从设计模板推断权限结构
2. **输出权限事实源表**：至少列出事实层、权威文件或符号、现有规则、本迭代是复用还是新增；缺少任何适用层时写明不适用的代码证据或阻塞原因
3. **对 §3 中每个对外接口，逐一填写权限矩阵**：

| 接口 | auth 级别 | 允许角色 | 数据权限范围 | 越权防护点 |
|------|----------|---------|------------|-----------|
| `POST /xxx` | 仅登录 / 需功能权限 | [角色列表] | 全量 / 渠道维度 / 创建人维度 | [校验逻辑，如"目标资源必须属于操作者渠道"] |

4. **越权场景分析**（对写操作重点检查）：

| 操作 | 水平越权风险 | 防护措施 | 垂直越权风险 | 防护措施 |
|------|------------|---------|------------|---------|
| [操作名] | [风险描述] | [校验逻辑] | [风险描述] | [校验逻辑] |

5. **权限注册清单**（如项目有注册机制）：逐接口写明复用或新增、对应代码证据、数据范围检查和前后端职责边界，供编码阶段直接使用
6. **执行项目门禁**：项目提供权限校验命令时必须执行；未执行、失败或只有人工推断时不得宣称权限设计完整

**输出位置**：写入设计文档 §4.6.1.3 安全设计 的"权限控制"部分，或独立为 §4.6.1.5 接口权限矩阵（视篇幅决定）。

**遗漏项 > 0 → 必须补充权限设计后才能进入步骤 9**

#### 8.4 数据库设计强制审核（有持久化变更时不可跳过）

规则标识：`database-review-auto-route`、`database-review-no-force-full`。

**触发条件**：新增、删除或合并表，修改持久化字段、主键、外键、唯一约束、CHECK、索引、ORM、Entity、DAL、migration、事务边界、锁、幂等、资金、Credit、账单、库存或配额模型。

1. **探测变更**：核对本设计的 DDL、数据结构、ORM/DAL、写入流程和迁移章节，不得只搜索 `CREATE TABLE`。
2. **无持久化变更**：在自检结果中写明代码和设计证据，结果记为 `not_applicable`。
3. **有持久化变更**：完整读取 `../database-review/SKILL.md`，由该 Skill 根据影响自动选择 `quick/delta/full/deterministic-only`；本文件不得强制 full，也不得复制或简化数据库审核标准。
4. **执行分级门禁**：局部封闭变更按 `scope_passed` 处理；需要恢复全局正式认证时才要求 `passed`。存在 P0/P1、证据缺口或结果为 `needs_delta/needs_full/blocked/stale` 时，不得宣称数据库审核完成。
5. **按影响重跑**：字段、约束或索引的局部变化只检查受影响对象；只有表拓扑或事务拓扑变化且用户确认 full 后，才执行完整审核。
6. **验证标记**：只有设计中的 `database-review: passed` 标记与当前设计摘要、证据包和报告一致，才可进入安全设计深审。

#### 8.5 安全设计质量自检（自动，不可跳过）

> **根因**：模板 §4.6.1 定义了安全章节格式，但 AI 容易套话（"通过 JWT 鉴权"一笔带过）。
> 本步骤强制验证安全章节的**具体性**，而非仅检查"有没有写"。

**触发条件**：与 8.3 相同 — 本模块有用户 HTTP 接口时触发，否则跳过。

**Phase 1：快检（3 条硬性规则，不通过直接打回修改）**

1. **STRIDE 具体性**：每条威胁必须同时包含 ①具体威胁描述 ②涉及的组件/接口名 ③具体防护措施。任一条只有泛泛描述（如"通过鉴权防止未授权访问"）→ 不通过
2. **安全兜底表无空泛项**：§4.6.1.1 每个"是"的行，"本模块设计"列必须写出具体实现方式（函数名/中间件名/配置项），不能只写"已实现"/"已支持"
3. **权限矩阵完整性**：8.3 产出的权限矩阵中，所有写操作必须有越权防护点，不能留空

**Phase 2：深度审查（spawn subagent 自动执行）**

首次设计或身份/权限/信任边界变化，快检通过后spawn一个subagent执行 `check:security` 五维审查（SEC-1~SEC-5）。已有有效审查且只是说明补充/重排时，核对语义不变后复用；接口语义局部变化只审影响面。

```
subagent 输入：设计文档 §4.6.1 安全性设计全文 + §3 接口列表 + 8.3 权限矩阵
subagent 执行：check:security 的 Step 2 五维度审查（STRIDE 具体性 / 安全兜底完整性 / 权限矩阵完整性 / 攻击面遗漏 / 越权场景覆盖）
subagent 输出：通过/不通过 + 具体改进建议列表（精确到章节+行）
```

**subagent返回“不通过”→记录具体问题，修复后只复核问题及关联影响；无未关闭P0/P1即收口，P2不触发循环。同一阻塞重复或证据不足时保存缺口并说明所需输入，不盲目重跑全量。**
**subagent 返回"通过"→ 进入步骤 8.6。**

#### 8.6 关键决策解释与交接

检查接口拆分、外部复用、数据职责及重要取舍的理由是否已写在对应设计章节；遗漏时直接补回该处。对话可给短速览并链接原文，不另建决策复述文档，不要求凑满固定条数。读者离开聊天记录仍能理解为什么这样设计。

### 步骤 9：完成提醒

先登记各项证据并运行 `python <插件根>/shared/scripts/workflow_gate.py evaluate <项目>`。只有返回 ready=true 且当前范围无未关闭 P0/P1 才能输出“可进入编码”；数据库有变更需有效审核，无变更需有依据的不适用记录。旧 passed 注释或手填 design_status 不能代替该结果。

概要设计未通过 `validate_design_readability.ps1` 时，禁止输出“可评审”“设计完成”或同义结论；不得用附件数量、总字数或 Agent 已审核代替可读性与无损验证。

完成状态必须按门禁分别报告：

| 状态 | 只有满足以下条件才能标记通过 |
|---|---|
| `template_gate` | 确定性可读性脚本退出码为 0；章节骨架和基线无损检查通过 |
| `content_gate` | 需求/旅程/数据/流程/前端/测试覆盖；本次接口有复用取舍、适用源码下钻、字段来源/消费者/删除影响、正常及失败复述、异常/唯一维护位置及一致性证据；无未关闭P0/P1 |
| `database_gate` | 无持久化变更则有代码证据并标 `not_applicable`；有变更则按 database-review 分级门禁通过 |
| `security_gate` | 有用户接口时完成权限事实源、STRIDE、兜底表和安全审查；无用户接口才标 `not_applicable` |
| `design_status=ready` | 上述适用门禁全部通过，且不存在 P0/P1 或 `blocked/stale` |

任何一个适用门禁为 `failed/pending/blocked/stale`，只能报告 `draft` 或 `blocked`，不能报告“设计完成”或“可进入编码”。

建议执行 `/design-session:save` 落盘进展。

## 微型设计流程（步骤 4M~6M）

> 微型设计适用于：已有模块的小范围变更、纯前端调整、已有接口的参数扩展等。
> 不需要完整的 Gap Analysis / DFX / FMEA，但仍需自检。

### 步骤 4M：编写

**微型设计模板**（内嵌，不需要额外加载）：

```markdown

|------|------|------|
```

### 步骤 5M：自检（轻量版）

1. 变更点 ↔ 系统需求对齐（是否覆盖所有功能点）
2. **前置依赖与契约快检**：涉及UI是否有对应数据源；新增/扩展接口按interface-review.md检查当前变动字段及直接消费者，复用公共定义与准确旧契约；微型变更不扩成全量接口矩阵，纯排版无需源码下钻。
3. 影响范围是否完整（有没有漏掉的关联文件/接口）
4. 后端零改动的变更是否真的零改动（确认现有接口参数满足需求）
5. **权限快速检查**：如有新增/变更的用户接口 → 确认权限注册方式（auth 级别 + 角色策略 + 数据权限范围），在变更详情中标注；无用户接口则跳过
6. **数据库分级审核**：如有 DDL diff、ORM/DAL、持久化字段、约束、索引、事务或幂等变更 → 完整读取 `../database-review/SKILL.md` 并按影响选择模式；微型局部变更取得 `scope_passed` 即可继续，只有需要全局正式认证时才要求 `database-review: passed`

### 步骤 6M：完成提醒

微型设计含数据库变更但没有当前变更范围的 `scope_passed`，或正式认证要求下没有有效 `database-review: passed` 标记时，禁止宣称设计完成或可进入编码。

建议执行 `/design-session:save` 落盘进展。
