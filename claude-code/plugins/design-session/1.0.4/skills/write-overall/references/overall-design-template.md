# 总体设计说明书模板（评审实用版）

> **来源**：`SFRD-TS-01-4.3_XXX版本总体设计说明书.pdf`
> **用途**：供 AI / 设计人员生成可用于内部评审的总体设计初稿
> **说明**：本模板不是对 PDF 的逐字转写，而是保留原模板章节骨架后，补强了评审最常卡住的论证点、量化项、约束项和自检项
> **适用场景**：新产品、新架构、跨模块协同、多模块联动、影响架构边界或 DFX 特性的需求版本

## 使用规则

### 文档定位

- 本模板面向“能送评审”的总设初稿，而不是文控级逐字还原版。
- 写作目标不是把章节填满，而是回答清楚“为什么这样设计、如何验证设计成立、设计边界在哪里”。
- 如果后续还需要严格对齐原 PDF 版式，可在本模板基础上再做格式映射。

### 红线约束

| 红线项 | 要求 |
|---|---|
| 需求承接 | 需求文档里出现的关键需求，必须能在总设中找到承接章节 |
| 章节完整性 | 除 `1.1` / `1.2` 的选择关系外，其它章节原则上不得留空；不涉及时必须写原因 |
| 方案选型 | 不能只有“最终方案”，必须说明备选方案、比较依据、为什么不选其它方案 |
| 目标量化 | 性能、可靠性、可运维性、可测试性等目标尽量量化，并写验证方式 |
| DFX 特性 | 安全性、可靠性章节不能空泛；至少要有目标、场景、机制、验证四类内容 |
| 业务边界 | 必须明确设计对业务的约束，否则评审容易追问边界失控 |

### 1.1 与 1.2 的使用建议

- PDF 原文口径为“`1.1` 与 `1.2` 二选一填写”。
- 实操上更稳妥的做法是：
  - 如果本次版本重点是架构变化、平台底座、跨模块重构，主写 `1.1`。
  - 如果本次版本重点是业务能力 / 特性实现，主写 `1.2`。
  - 如果版本同时存在明显的架构改造和特性设计，建议两章都写，但要明确边界，避免重复。

### DCP 阶段输入 / 输出

| 阶段 | 输入 | 输出 |
|---|---|---|
| DCP2 立项阶段 | 用户需求设计、技术规划、DFX 基线和版本 DFX 需求、安全需求、质量问题需求、其它需求输入 | 部分设计，重点是技术需求设计、设计目标 |
| DCP3 计划阶段 | 系统需求文档、版本方案草图、前期预研结论 | 完整总体设计，包含章节化设计、流程、DFX、风险和变更控制 |

### AI 填写顺序建议

1. 先写第 2 章，把“目标是什么、怎么验收”定清楚。
2. 再写第 1 章，把“为什么这么设计、为什么不这么设计”讲清楚。
3. 然后写第 4 章，固化系统架构、流程、模块和数据结构。
4. 再写第 5 章，把安全、可靠性、可运维等 DFX 设计补全。
5. 最后写第 6 到第 8 章，收口风险、遗留问题、变更和修订记录。
