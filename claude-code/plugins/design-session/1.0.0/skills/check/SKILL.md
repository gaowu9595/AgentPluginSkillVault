# check（设计文档规范检查）

**REQUIRED BACKGROUND:** Read `shared/design-session-engine.md` for path conventions.

设计文档规范检查 — 支持四种模式：**内部一致性检查**、**外部规范对照**、**系统需求质量评估**和**安全设计审查**。

## 使用方法

```
/design-session:check consistency <项目目录>               # 内部一致性检查
/design-session:check quality <系统需求卡片路径>            # 单张卡片质量评估
/design-session:check quality <项目目录>                   # 批量评估项目下所有系统需求卡片
/design-session:check security <概要设计文档路径>           # 安全设计审查（单文档）
/design-session:check security <项目目录>                  # 安全设计审查（批量）
/design-session:check <规范文档路径>                        # 外部规范对照（原有功能）
/design-session:check <规范文档路径> <项目上下文路径>         # 外部规范对照，指定项目上下文
/design-session:check resume <输出文件路径>                  # 从上次中断处继续
/design-session:check                                      # 交互式，提示选择模式
```

## 参数解析

根据第一个参数判断模式：
- `consistency` → 模式 1（内部一致性）
- `quality` → 模式 3（质量评估）
- `security` → 模式 4（安全设计审查）
- `resume` → 恢复中断的分析
- 其他（文件路径）→ 模式 2（外部规范对照）
- 无参数 → **智能路由**（见下方）

### 无参数智能路由

当用户只输入 `/design-session:check` 不带参数时，基于可观测信号自动推荐：

**路由规则（按优先级顺序匹配）**：

| 信号（可观测） | 推荐模式 | 理由 |
|--------------|---------|------|
| context.md 当前阶段含"系统需求" AND 存在未评估的 `迭代*-*-系统需求.md` | quality | 进概设前确认需求质量 |
| 最近 git diff 涉及 ≥2 个 `架构设计/` 下的设计文档 | consistency | 多文档改动后检查一致性 |
| 存在概要设计文档 AND 文档内无 `<!-- security-check: passed -->` 标记 | security | 概设完成但未通过安全审查 |
| 参数是文件路径 AND 文件扩展名为 .xlsx/.pdf/.md 且内容为规范/基线类 | baseline | 合规对照 |
| 以上均不匹配 | 列出所有可选模式 + 标注推荐 | 兜底 |

**执行流程**：
1. 读 `<项目>/.ai/context.md` 获取当前阶段
2. 执行 `git diff --name-only HEAD~5` 获取最近改动文件
3. Glob `<项目>/架构设计/概要设计/*.md` 检查 security 标记
4. 匹配规则 → 输出推荐（含理由）→ 用户确认后执行

**输出格式**：
```
## 检查推荐

基于当前项目状态：
- 当前阶段：<阶段>
- 最近改动：<N 个设计文档>

→ 推荐执行：**<模式名>**
→ 原因：<一句话>

确认执行？或选择其他模式：consistency / quality / security / baseline
```

**审查通过标记**：security 模式审查通过后，在设计文档末尾追加：
```html
<!-- security-check: passed YYYY-MM-DD -->
```
下次智能路由时识别此标记，不再重复推荐。

## 核心原则

### 1. 禁止想当然断言 — "不确定就说不确定"

- ❌ 没有看到代码/配置/文档证据就写"满足"、"已覆盖"
- ❌ 假设公司有某个流程而不验证
- ❌ 把"设计方案里提到了"等同于"已实现已验证"
- ✅ 能自己查代码/文档确认的，先查再下结论
- ✅ 查不到的，标"待确认"并说明缺什么信息
- ✅ 区分"设计层面有方案"和"已落地已验证"

**状态标签规范**：

| 状态 | 含义 | 何时使用 |
|------|------|---------|
| **设计已覆盖** | 架构设计中有明确方案 | 有文档证据 |
| **设计待落地** | 方向已确认，具体实现方案未完成 | 有方向没细节 |
| **需纳入设计** | 当前设计中未体现 | 设计盲区 |
| **待确认** | 需要找人确认 | 信息缺失 |
| **不涉及** | 不适用于当前项目 | 明确不适用 |

### 2. 资料要读完整 — "先确认范围再开始"

### 3. 合规文档是设计的输入，不是验收报告

## 模式 1：内部一致性检查（consistency）

扫描项目设计文档，提取关键概念的所有出现位置，交叉比对是否一致。

### 扫描范围

| 目录/文件 | 说明 |
|----------|------|
| `<项目>/架构设计/**/*.md` | 所有设计文档 |
| `<项目>/.ai/context.md` | 全局上下文索引 |
| `<项目>/架构设计/变更追踪.md` | 变更记录 |

**不扫描**：`.ai/*-摘要.md`、`.ai/*-analysis.md`、`资料/`

### 检查维度

#### DIM-1：角色定义一致性

**提取目标**：角色名称、role_code、角色层级关系、数据权限描述
**搜索关键词**：`角色`、`role`、`soc_admin`、`psm`、`channel_admin`、`channel_sub`、`层级`、`数据权限`
**检查规则**：
1. 所有文档中的角色列表必须一致（名称、code、数量）
2. 角色层级树必须一致（父子关系、1:N 基数）
3. 数据权限描述必须一致

#### DIM-2：数据模型字段一致性

**提取目标**：表/集合名称、关键字段名、字段类型
**搜索关键词**：`字段`、`field`、`表`、`集合`、`schema`、`数据模型`
**检查规则**：
1. 同一实体在不同文档中的字段列表一致
2. 字段命名风格一致（snake_case，与 D365 对齐）
3. 字段类型不矛盾

#### DIM-3：技术决策引用一致性

**提取目标**：ADR 编号、决策结论、技术选型
**搜索关键词**：`ADR-`、`决策`、`技术栈`、`Sanic`、`Flask`、`MongoDB`、`PostgreSQL`
**检查规则**：
1. 引用的 ADR 编号在架构决策记录中存在
2. 引用的决策结论与 ADR 原文一致
3. 技术栈描述一致

#### DIM-4：仓库/服务命名一致性

**提取目标**：仓库名、服务注册名
**搜索关键词**：`mdr-`、`mssp-`、`lb://`、`仓库`、`服务`
**检查规则**：
1. 仓库名前缀一致
2. 服务注册名 `lb://xxx` 引用正确
3. 同一服务在不同文档中名称一致

#### DIM-5：待确认项状态同步

**提取目标**：待确认问题编号、确认状态
**搜索关键词**：`待确认`、`已确认`、`R-`、`D-NEW-`、`ARCH-`
**检查规则**：
1. 标记"已确认"的项在设计文档中是否已更新
2. context.md 与待确认问题.md 状态一致
3. 没有"已确认但设计文档未同步"的情况

#### DIM-6：变更追踪完整性

**提取目标**：变更追踪.md 中的 checkbox 状态
**检查规则**：
1. 所有变更记录的 checkbox 是否全部完成
2. 未完成的 checkbox 对应文件是否确实未更新

### 执行流程

**Step 1**：收集文档清单（Glob `<项目>/架构设计/**/*.md`）
**Step 2**：按维度搜索（Grep 关键词 + 读取上下文）
**Step 3**：交叉比对（分组 → 对比 → 标记不一致）
**Step 4**：输出报告
**Step 5**：询问是否自动修复

### 输出格式

```markdown
# [项目名] 设计一致性检查报告

> 检查时间：YYYY-MM-DD
> 扫描范围：N 个文件，共 M 行
> 检查维度：6 个

## 检查结果概览

| 维度 | 状态 | 不一致数 |
|------|------|---------|
| DIM-1 角色定义 | ✅/⚠️ | 0/N |
| ... | ... | ... |

## 不一致详情

### DIM-X: [维度名]

#### 问题 1: [简述]

| 文件 | 行号 | 当前内容 |
|------|------|---------|
| `文件A.md` | L42 | `内容A` |
| `文件B.md` | L88 | `内容B`（不一致） |

**建议**：以 [权威源] 为准，修改 [目标文件]

## 变更追踪检查

- CHG-001: ✅ 全部完成
- CHG-002: ⚠️ 有 N 项未完成

## 建议操作

1. [修复建议]
```

### 注意事项

1. 不修改文档，只输出报告（除非用户要求自动修复）
2. 区分"确实不一致"和"详略不同"
3. context.md 是索引，比设计文档简略是正常的
4. 关注实质矛盾，忽略表述差异

## 模式 2：外部规范对照（baseline）

将外部规范/基线/需求文档逐条转化为设计约束和待确认项。

### 执行流程

**Phase 1: 准备**
1. 探测文档结构（Sheet 名称、章节标题、总行数）
2. 读取项目上下文（`.ai/context.md`）
3. 制定分批计划（每批 30-50 条）
4. 确认输出位置

**Phase 2: 分批执行**（对每一批）
5. 读取本批原文（offset/limit）
6. 快速初筛（涉及/不涉及）
7. 逐条分析涉及的条目
8. 本批结果立即写入输出文件

**Phase 3: 汇总**
9. 生成汇总章节（统计 + 待确认清单 + 设计输入汇总）
10. 更新项目文件（待确认问题.md、context.md）

### Resume 机制

使用 `/design-session:check resume <输出文件路径>` 时：
1. 读取输出文件，查找进度标记 `<!-- 进度：已完成批次 X/Y -->`
2. 从下一个未完成的批次继续

### 输出模板

```markdown
# [项目名] [规范名称] 合规对照表

> 基线来源：[文件名]
> 对照范围：从 N 条中筛选出 M 条与本项目相关
> 编制时间：YYYY-MM-DD

<!-- 进度：已完成批次 0/N -->

## 批次 1: [维度名称]

| 编号 | 要求概述 | 优先级 | 状态 | 证据/举措 | 设计输入 |
|------|---------|--------|------|----------|---------|

## 待确认清单

| # | 条目 | 问题 | 找谁确认 |
|---|------|------|---------|

## 设计输入汇总（按模块）

### [模块名]
- [ ] [约束条件]（来源：R编号）
```

## 模式 3：系统需求质量评估（quality）

按 IEEE 830 + INCOSE GTWR 标准，对系统需求卡片进行 8 维度量化评估。

**评分标准**：`skills/check/references/quality-criteria.md`（插件自带，按需 Read 加载）

### 执行流程

**Step 1**：确定评估范围（单文件 or 项目目录 Glob `迭代*-*-系统需求.md`）
**Step 2**：加载评分标准
**Step 3**：加载上下文（context.md + 其他卡片实体定义）
**Step 4**：逐维度评估（8 维度）
**Step 5**：计算总分（加权）
**Step 6**：输出评估报告
**Step 7**：批量评估汇总（项目目录模式）

### 8 维度检查清单

| 维度 | 权重 | 检查要点 |
|------|------|---------|
| 完整性 | 20% | §2 功能需求 + §3 非功能 + §4.2 测试场景 + §4.3 工作量 + 依赖风险表 |
| 可验证性 | 20% | 测试场景 + 性能数值 + 步骤表具体度 + 无模糊验收标准 |
| 无歧义 | 15% | Grep 模糊词（等/可能/适当/合理/及时）+ 状态机枚举完整 + 字段有类型 |
| 一致性 | 15% | 与 context.md 决策对比 + 跨卡片实体/字段名对比 + 术语统一 |
| 可追溯 | 10% | 交互原型来源标注 + 待确认项来源 + 功能点追溯到 NR/DR 编号 |
| 可排序 | 5% | 功能点有编号 + 待确认项有 P0/P1/P2 分级 |
| 可修改 | 5% | 功能点独立编号 + 章节结构清晰 + 修改不连锁 |
| 正确性 | 10% | 代码验证标注 + 无未标注推断 + 引用的接口/表名存在 |

### 输出格式

```markdown
## 系统需求质量评估报告

**卡片**：<卡片名称>
**总分**：X.X / 10
**结论**：✅ 可进入概要设计（≥7.5）/ ⚠️ 需补充（7.0~7.4）/ ❌ 不达标（<7.0）

### 各维度得分

| 维度 | 权重 | 得分 | 扣分项 |
|------|------|------|--------|
| 完整性 | 20% | X/10 | <具体扣分点> |
| ... | ... | ... | ... |

### 关键问题（必须修复）
1. <问题 + 位置 + 建议>

### 改进建议（可选）
1. <建议>
```

## 模式 4：安全设计审查（security）

对概要设计文档的安全章节（§4.6.1）进行深度质量审查，验证安全设计的**具体性和完整性**。

> **定位**：write 流程步骤 8.4 会自动 spawn subagent 执行本审查。本命令供独立使用（评审前复查、审查他人设计）。

### 触发条件

本模块包含面向用户的 HTTP 接口。纯后台进程/定时任务/消息消费者 → 输出"不适用"并结束。

### 执行流程

**Step 1**：加载输入
- 读取概要设计文档 §4.6.1 安全性设计全文
- 读取 §3 对外接口列表
- 搜索文档中的权限矩阵（8.3 产出，可能在 §4.6.1.3 或 §4.6.1.5）
- 如有项目权限架构参考（知识库/代码仓库），加载作为对照基线

**Step 2**：5 维度审查

#### SEC-1：STRIDE 具体性

**检查规则**：
| 检查项 | 通过标准 | 不通过示例 |
|--------|---------|-----------|
| 威胁描述 | 指明具体攻击方式 + 攻击入口 | "可能被未授权访问" |
| 涉及组件 | 写出具体接口/模块/数据表名 | "本系统"、"相关接口" |
| 防护措施 | 写出具体实现方式（函数/中间件/配置） | "通过鉴权机制防护"、"已实现" |
| 威胁真实性 | 该威胁在本模块确实存在（非凑数） | 对纯读接口写"篡改数据"威胁 |

**评分**：每条 STRIDE 逐一判定 通过/不通过，统计通过率。

#### SEC-2：安全兜底表完整性

**检查规则**：
1. 对照 §3 接口列表，检查是否有遗漏的安全兜底项
2. 每个"是"的行，"本模块设计"列必须有具体实现描述（函数名/中间件名/配置项）
3. 涉及敏感数据的接口（含个人信息/密码/密钥）必须有对应的加密/脱敏措施

#### SEC-3：权限矩阵完整性

**检查规则**：
1. §3 中所有接口是否都出现在权限矩阵中
2. 所有写操作（POST/PUT/DELETE）是否都有越权防护点
3. 数据权限范围是否与角色层级一致（高角色 ⊇ 低角色）
4. 是否有接口遗漏了 auth 级别标注

#### SEC-4：攻击面遗漏检查

**逐一检查以下常见遗漏**：
| 攻击面 | 检查方法 | 常见遗漏 |
|--------|---------|---------|
| 批量接口 | §3 中有批量操作吗？ | 未限速/未限量 |
| 文件上传 | §3 中有文件上传吗？ | 未校验类型/大小/内容 |
| 敏感操作 | 有删除/角色变更/密码重置吗？ | 未记录审计日志 |
| 导出接口 | 有数据导出吗？ | 未限制导出量/未脱敏 |
| 定时任务 | 有定时触发的操作吗？ | 未防重入/未限并发 |
| 外部回调 | 有接收外部系统回调吗？ | 未验证来源签名 |

#### SEC-5：越权场景覆盖

**检查规则**：
1. 水平越权：所有涉及 `{id}` 路径参数的接口，是否校验资源归属
2. 垂直越权：角色相关操作是否有转换矩阵/等级约束
3. 间接越权：通过关联资源间接访问（如通过客户 ID 反查渠道信息）是否有防护

**Step 3**：输出审查报告

```markdown
## 安全设计审查报告

**文档**：<概要设计文档名>
**审查时间**：YYYY-MM-DD
**结论**：✅ 通过 / ⚠️ 需补充 / ❌ 不达标

### 各维度结果

| 维度 | 状态 | 问题数 | 说明 |
|------|------|--------|------|
| SEC-1 STRIDE 具体性 | ✅/⚠️/❌ | N | [通过率 X%] |
| SEC-2 安全兜底完整性 | ✅/⚠️/❌ | N | |
| SEC-3 权限矩阵完整性 | ✅/⚠️/❌ | N | |
| SEC-4 攻击面遗漏 | ✅/⚠️/❌ | N | |
| SEC-5 越权场景覆盖 | ✅/⚠️/❌ | N | |

### 必须修复（不通过项）

1. **[SEC-X]** [具体问题] — 位置：§X.X.X 第 N 行
   → 建议：[具体修改建议]

### 改进建议（可选）

1. [建议]
```

### 判定标准

| 结论 | 条件 |
|------|------|
| ✅ 通过 | 5 维度全部无"必须修复"项 |
| ⚠️ 需补充 | 有 1-3 个"必须修复"项，均为补充性质（加描述/加措施） |
| ❌ 不达标 | 有 >3 个"必须修复"项，或存在结构性缺失（如完全没有权限矩阵） |

### 注意事项

1. 审查是只读操作，不修改设计文档（除非用户要求修复）
2. 区分"设计层面有方案"和"已落地已验证"— 本审查只检查设计完整性
3. 如项目有权限架构参考文档，以其为基线判断权限注册是否完整
4. 不要因为模板有安全章节就假设内容充分 — 逐条验证具体性

## 注意事项

1. **大文件处理**：绝不一次性读取全文，按批次 offset/limit 读取
2. **增量更新**：已有对照文档时在现有基础上增量更新
3. **关联已有文档**：发现的问题同步更新 `待确认问题.md`
4. **不要过度解读**：基线条目的适用范围严格按原文判断
5. **批间连贯性**：后面的批次可能引用前面批次的结论
6. **评估是只读操作**：不修改卡片内容，只输出报告（除非用户要求修复）
7. **正确性维度需人工确认**：agent 只能检查"是否有验证标注"
