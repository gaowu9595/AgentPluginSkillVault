# Requirements Clarify Output Templates

代码核查较多或产品读者不需要内部证据时，输出“内部事实基线”和“产品确认清单”两份文档。内容不完整时保留“待确认”，不要用猜测填充。

## 模板 A：内部事实基线

```markdown
# <功能名称> 事实基线与澄清记录（内部版）

> 版本：V0.1
> 状态：待产品确认 / 已具备系统需求输入
> 证据范围：<原始材料、摘要、代码模块>

## 一、当前有效范围

| 候选事项 | 用户旅程 | 区域/对象 | 是否独立需求 | 与本次关系 | 依据 |
|---|---|---|---|---|---|

## 二、这次要解决什么问题

### 2.1 一句话目标
### 2.2 用户、触发场景和完成效果

## 三、现有系统事实基线

| 主题 | 已确认行为 | 证据 | 本次是否改变 |
|---|---|---|---|

## 四、用户旅程

| 步骤 | 角色 | 用户做什么 | 系统做什么 | 用户看到什么 | 业务效果 |
|---|---|---|---|---|---|

## 五、材料交叉验证

| 主题 | 材料 A | 材料 B | 代码事实 | 结论 |
|---|---|---|---|---|

## 六、候选问题处置

| 候选问题 | 处置 | 理由/证据 | 是否进入产品清单 |
|---|---|---|---|

处置枚举：已由代码确定 / 已由产品确认 / 拆至相邻需求 / 转系统设计 / 视觉细节由开发设计 / 保留为产品 P0。

## 七、进入系统需求的条件

- [ ] 主流程闭合
- [ ] 范围和相邻需求已拆分
- [ ] 资金、状态、数据来源和服务结果已闭合
- [ ] 所有产品 P0 已回答

**结论**：尚不可写系统需求 / 已具备系统需求输入。
```

## 模板 B：产品确认清单

```markdown
# <功能名称> 产品规划确认清单

> 版本：V0.1
> 状态：以下问题确认后可编写系统需求

## 一、这次要做什么

<一句话目标>

| 事项 | 区域/对象 | 与本次关系 |
|---|---|---|

## 二、用户旅程

1. <用户发起什么>
2. <系统如何处理>
3. <审批或外部协作>
4. <完成后的业务结果>

## 三、无需再确认的现有事实

- <代码已确定且本次沿用的行为>
- <已明确拆出的相邻需求>

## 四、需要确认的关键问题

### Q-01（P0）：<一个具体业务决策>

<旅程事件 + 当前事实/冲突 + 为什么产生不同业务结果>

开发建议：<建议及理由>

请确认：□ <方案 A>  □ <方案 B>

## 五、确认后的下一步

收到全部 P0 答案后，开发回写用户需求基线，再编写系统需求和前后端交互设计。
```

## 抽象问题改写示例

不推荐：

> 外部数据契约是什么？

推荐：

> 本期费用可以按申请时填写的席位数，也可以按外部平台期末实际活跃席位数计算；两者会产生不同费用。请确认采用哪一种。若采用外部数据，请指定数据负责人，接口字段和重试协议由开发继续对接。
