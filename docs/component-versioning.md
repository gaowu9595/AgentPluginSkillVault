# 离线组件版本管理

## 两套台账

- [artifacts.json](../registry/artifacts.json)：现有 Skill、插件和 MCP 源码快照，保持原格式。
- [components.json](../registry/components.json)：可安装离线发行物目录，指向每个版本的记录。
- `registry/releases/<组件>/<版本>/<平台>.json`：固定 ZIP 的字节数、SHA256、包内清单哈希、
  上游与依赖版本、来源及验证记录。正式分发后身份、版本、大小、哈希和依赖字段不可覆盖，
  修正这些字段须发布新版本。真实下载地址和新增验证证据可以追加，保留 Git 变更历史。

当前没有离线发行物的源码快照，不能因为收录进 Git 就记为已发布组件。

## 各版本的含义

| 字段 | 含义 | Impeccable 首包 |
| --- | --- | --- |
| `upstream.version` | 上游 Skill/项目版本 | `4.8.2` |
| `engine.version` | 实际审查引擎版本 | `0.1.22` |
| `componentVersion` | Vault 安装包及适配版本 | `1.0.0` |
| `schemaVersion` | 包内 manifest 结构版本 | `1` |
| `protocolVersion` | 管理命令结果协议版本 | `1` |

组件版本使用 SemVer。PATCH 用于兼容修复或重新打包；MINOR 用于兼容的新能力；
MAJOR 用于不兼容的安装、配置或数据变更。上游版本升级也须评估兼容性，不能直接当作
Vault 版本。任意已发布文件、引擎、依赖、安装逻辑变化，都产生新的组件版本和哈希。
平台不同可以共享组件版本，但发行记录和校验值分开。

打包源码的换行规则通过 `.gitattributes` 固定；上游快照保留原始字节，不顺手清理空白。
新增组件时同步覆盖这些规则，并从 Git 检出副本重新构建验证，避免 Windows 换行转换改变哈希。

## 一次升级的步骤

1. 保留上一个发行记录；新增版本目录，记录来源、精确版本和许可证。
2. 同时检查 Claude Code/Codex 的发现、目录、权限及配置差异，不适用项说明原因。
3. 生成完整运行包，记录逐文件哈希。独立、重复构建核对 ZIP 哈希。
4. 在临时目录验证安装、原版本升级、失败保护、自检和卸载；记录哪些检查未做。
5. 写入该版本发行记录及变更说明，更新组件目录的推荐版本和 `docs/update-log.md`。
6. 通过发布检查后才上传 ZIP，再添加确实可访问的地址；内网可使用相同 ZIP 和哈希。
7. 宿主只提供兼容范围内经过验证的更新。Vault 发布新版不强制升级 SwitchAI 或用户安装。

不得在没有可用旧运行包或数据兼容性证据时承诺“一键回滚”。首包升级会输出前一份安装的
备份位置；备份不放入原生 Skill 扫描目录。具体恢复方式见组件说明。
